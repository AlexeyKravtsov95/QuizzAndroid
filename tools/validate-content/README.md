# tools/validate-content — валидатор контентного пакета

Автономный инструмент на Python 3.12: JSON Schema Draft 2020-12, двадцать одно
правило `CONTENT_MODEL.md` §8 и правила уровня пакета `M01`–`M10`. Android-кода не
содержит, Gradle не требует, в сеть не ходит и читает только тот каталог, который
ему передали.

Проект и обоснования — `docs/ITERATION_4_DESIGN.md` (решение **I4-D8**, разделы 4–7).

## Запуск

```bash
python3 tools/validate-content/validate.py <каталог-пакета>
```

| Ключ | Что делает |
| --- | --- |
| `--validation-date YYYY-MM-DD` | дата, относительно которой ISO-даты контента считаются будущими (`R04B`). По умолчанию — сегодняшняя |
| `--format human\|json` | формат вывода; находки и их порядок в обоих одинаковы |
| `--sync-manifest` | пересчитать `sha256`, `setCount` и `puzzleCount` в манифесте |
| `--expect-sets N` / `--expect-puzzles N` | критерий объёма пакета (`M10`) |

Коды выхода:

| Код | Значение |
| --- | --- |
| `0` | нарушений нет |
| `1` | пакет прочитан, найдено хотя бы одно нарушение |
| `2` | инструмент **не смог** выполнить проверку: каталога нет, нет прав, повреждена схема, внутренняя ошибка |

Разделение `1` и `2` обязательно: без него «контент плохой» и «валидатор сломан»
выглядят в CI одинаково, и второе чинят как первое. Ожидаемая пользовательская
ошибка печатает одну строку и никогда — traceback.

## Установка зависимостей

Только через lock-файл, и в CI, и локально:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r tools/validate-content/requirements.txt
.venv/bin/python -m pytest tools/validate-content/tests -q
```

`requirements.txt` фиксирует точные версии и все sha256 их дистрибутивов; `>=`,
диапазонов и непинованных строк в нём быть не может — `--require-hashes` отвергает
такой файл целиком. Версии, первичные источники и даты проверки — `docs/VERSIONS.md`.

## Как читать диагностику

```
R06_ORDER_MISMATCH puzzles-001.json#/puzzles/12/correctOrder — записан [...], вычислен [...]
```

Стабильны **код, файл, JSON pointer и порядок находок**. Текст сообщения контрактом
не является: он пишется для человека и меняется без правки тестов.

Порядок находок детерминирован и не зависит ни от порядка ключей во входном JSON, ни
от версии интерпретатора:

1. файл — в порядке отображения `manifest.json` → `puzzles-NNN.json` → `daily-sets-NNN.json`
   (он совпадает с направлением ссылок и **не обязан** совпадать с порядком чтения);
2. JSON pointer — посегментно, индексы массивов **численно**: `/puzzles/2` раньше `/puzzles/10`;
3. код правила — лексикографически.

| `contentval/shuffle.py` | порт `DeterministicShuffler` для правила 10 |
| `contentval/rules_schema.py` | JSON Schema и отображение её ошибок в коды `R01`–`R04`, `R11`, `R17` |
| `contentval/rules_manifest.py` | `M01`–`M10`, `R21` |

## Владение кодами: почему одна ошибка не даёт двух находок

Строгая схема и специализированные пакетные правила пересекаются, и без явного
разделения одно нарушение давало бы и точный код, и бессодержательный `R01`.
Подавление **точечное — по вопросу, а не по месту**:

- в массиве `manifest.files` `M03` владеет составом списка (число элементов,
  уникальность) и именем файла, `M06` — **значением** хеша, включая регистр. Всё
  остальное внутри `/files` — форма документа, и её владелец схема: элемент без
  обязательного `sha256`, `sha256` не строкой и лишнее поле в элементе дают `R01`.
  Ни `M03`, ни `M06` их не ловят — первый смотрит только на `path`, второй сравнивает
  хеш лишь тогда, когда тот уже является строкой, — поэтому подавление по всему
  поддереву `/files` означало бы, что строгая схема манифеста не действует вовсе;
- верхняя граница `schemaVersion` принадлежит `M01`, поэтому в схеме её нет;
- при сработавшем `M03` список файлов недостоверен, поэтому `M04`, `M06` и `M08` не
  выполняются: сверять каталог не с чем;
- файл, не прошедший схему, не проверяется семантическими правилами: считать
  разрывы и порядок в документе, который не собрался по форме, значит выдавать
  каскад мусора вместо одной точной находки;
- значение, названное кодом `R07`, `R08D` или `R08E`, исключается из проверки
  разрыва **попарно**: разрыв — свойство пары, и пара, не содержащая ни одного
  диагностированного значения, остаётся самостоятельным нарушением `R08`
  (в `[100, 100, 200, 202]` дубликат даёт `R07`, а пара 200/202 — `R08`);
- находки, совпадающие по файлу, указателю и коду, схлопываются в одну.

`M02` проверяется двумя независимыми предикатами, и оба принадлежат CLI:
расхождение `packId` между файлами пакета и расхождение манифеста с **активным
пакетом приложения**. Идентификатор активного пакета известен инструменту так же,
как известна поддерживаемая версия формата — это константа проекта
(`units.ACTIVE_PACK_ID`), а не аргумент запуска.

Пять правил `CONTENT_MODEL.md` §8 выражаются схемой полностью, но обязаны
называться своими кодами, а не `R01`: отсутствие `correctOrder` (`R02`), длина
текста (`R03`), отсутствие `verifiedAt`/`verifiedBy` (`R04`), пустой `sourceIds`
(`R11`), отсутствие локатора у источника (`R17`).

## Даты: почему `--validation-date`, а не системные часы

`format` в Draft 2020-12 по умолчанию — аннотация, поэтому `FormatChecker`
включается явно, а календарная корректность и «не в будущем» дополнительно
проверяются правилами `R04A` и `R04B`: `pattern` пропускает `2026-13-45`, а
зависеть от того, что реализация включила `format`, — значит зависеть от настройки,
которую легко потерять.

«Будущее» задаётся параметром: тест, сравнивающий дату фикстуры с календарём машины,
зелен сегодня и красен через год — то есть не тест, а таймер. Системная дата
читается **ровно в одном месте** — как значение по умолчанию аргумента на границе
CLI; все правила получают её аргументом. Это проверяется тестом.

## Фикстуры

```
fixtures/
    valid/               8 наборов / 25 головоломок (24 активные + 1 отозванная вне наборов)
    valid-minimal/       1 набор / 3 головоломки
    invalid/<код>/       по пакету на каждое правило и каждый подкод
    expectations.json    единственный источник ожидаемых кодов
    shuffle-vectors.json общие векторы правила 10
    rebuild.py           пересборка каталога из спецификации
```

**Фикстуры синтетические и не являются продуктовым контентом.** Тексты, значения и
источники (домен `example.invalid` зарезервирован RFC 6761 и никогда не резолвится)
придуманы ради проверки правил и ничего не утверждают о мире. Настоящий контент
приходит батчами 4C-1…4C-5 по редакторскому протоколу `CONTENT_MODEL.md` §8 с
заполненным `docs/CONTENT_REVIEW_CHECKLIST.md`.

Пересборка:

```bash
python3 tools/validate-content/fixtures/rebuild.py
```

Скрипт механически проставляет **производные** значения — `sha256` и счётчики — по
фактическим байтам файлов и **не «чинит» фикстуры, намеренно нарушающие манифест,
хеш или счётчики**: их повреждение объявлено в спецификации и применяется после
автозаполнения. Список таких фикстур — `rebuild.DELIBERATE`, и отдельный тест
проверяет, что после пересборки они по-прежнему падают.

`expectations.json` — единственный источник ожидаемых кодов. Колонка `cli`
проверяется тестами этого PR; колонка `runtime` предназначена полному пути
`ContentPackReader → ContentValidator` и заполняется в PR 4B (там, где она совпала бы
с `cli`, её опускают).

## Чего валидатор не проверяет

Зелёный валидатор — **необходимое, но не достаточное** условие мержа контента. Он не
может открыть ссылку, убедиться, что страница существует и содержит указанное
значение, что `kind` соответствует характеру издания и что разрыв больше реальной
погрешности измерения. Это проверяет человек по `docs/CONTENT_REVIEW_CHECKLIST.md`, и
никакая автоматика этого не заменит.

## Протокол правки контента

```bash
# 1. дописать головоломки и наборы в конец массивов
# 2. привести производные значения манифеста в соответствие
python3 tools/validate-content/validate.py app/src/main/assets/content --sync-manifest
# 3. проверить пакет целиком, включая ожидаемый объём батча
python3 tools/validate-content/validate.py app/src/main/assets/content \
    --expect-sets 14 --expect-puzzles 42
```

Шаг 2 обязателен: без него приложение не увидит изменений, а CI не пропустит PR.

`--sync-manifest` применяет тот же закрытый allow-list имён, что и правило `M03`, **до
любого обращения к диску**: режим получает имена файлов из данных, а не из кода, и
обычная валидация объявила бы `M03` уже после чтения. «Прочитали, но потом сообщили»
защитой не является — инструмент успел бы взять байты файла за пределами каталога
пакета и записать его `sha256` в манифест.

Замена значений не привязана к конкретному форматированию манифеста: минифицированный
`"sha256":"…"` — такой же валидный JSON, как `"sha256": "…"`. Инструмент печатает и
считает только те замены, которые действительно произошли; если значение в тексте не
найдено, он говорит об этом прямо, а не отчитывается об изменении, которого не сделал.

При `--format json` отчёт синхронизации уходит в stderr, чтобы stdout оставался
разбираемым целиком.
