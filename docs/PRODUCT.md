# PRODUCT.md — «По порядку!»

Продуктовый документ MVP. Статус: черновик на утверждение. Код не пишется до утверждения.

---

## 1. Проблема и ценность

### Проблема

Ежедневные головоломки (Wordle-формат) заняли нишу «две минуты умного досуга»: короткая сессия, один общий для всех результат, повод поделиться. В русскоязычном сегменте эта ниша почти пуста:

- крупные ежедневные головоломки либо англоязычны, либо построены на английской лексике и непереводимы;
- русскоязычные викторины в магазинах приложений в основном сделаны в эстетике телешоу или казино: таймеры, «жизни», агрессивная монетизация, требование регистрации;
- у пользователя нет спокойного ежедневного ритуала на русском, который даёт ощущение «я что-то узнал», а не «я потратил время».

### Ценность

«По порядку!» даёт **короткий ежедневный ритуал с ощутимым интеллектуальным результатом**:

| Что получает пользователь | Как это обеспечивается |
| --- | --- |
| Ритм: одно и то же время, одинаковая длительность | 3 головоломки, 2–4 минуты, ровно один набор в день |
| Ощущение честного результата | Один зафиксированный ответ на задание, без переигрывания |
| Новое знание, а не просто очки | Короткое объяснение и проверенные источники после каждой попытки |
| Повод поделиться без порчи впечатления | Карточка результата без спойлеров |
| Отсутствие трения | Ни регистрации, ни интернета, ни onboarding-туннеля |

### Почему именно упорядочивание

Механика «расставь четыре карточки по признаку» выбрана осознанно:

- **однозначность** — у порядка есть проверяемый ответ (дата, высота, расстояние, широта), в отличие от «угадай ассоциацию»;
- **частичный успех** — пользователь почти никогда не получает 0: баллы даются за пары карточек, стоящие в правильном относительном порядке (0–6 за головоломку), поэтому одна перепутанная пара не обнуляет попытку;
- **низкий языковой барьер** — не нужно вводить текст, не нужна раскладка, работает одной рукой;
- **дешёвый контент** — головоломку можно составить и проверить по источникам за минуты, что критично для соло-разработчика;
- **естественная сложность** — она регулируется близостью значений, а не жестокостью формулировки.

## 2. Аудитория

### Ядро

Взрослые 20–45 лет, русскоязычные, «любители фактов»: смотрят научпоп, играют в викторины в компании, читают Википедию по ссылкам. Они не считают себя геймерами.

**Что для них важно:** уважительный тон, отсутствие давления, корректные факты, аккуратный внешний вид, возможность закрыть приложение и не чувствовать вины.

**Что их отталкивает:** таймеры обратного отсчёта, «энергия»/жизни, обязательный вход, реклама до игры, инфантильный визуальный язык, спорные или устаревшие факты.

### Сценарий использования

Утро или обеденный перерыв. Пользователь открывает приложение по привычке или по уведомлению, проходит три задания, читает объяснения, закрывает. Возврат в тот же день — за просмотром итога или архива, не за повтором игры.

### Вторичная аудитория

- 45+ — та же механика, но выше требования к размеру шрифта и контрасту (учтено в требованиях к доступности);
- подростки 14–19 — приходят через шеринг результатов; специально под них MVP не оптимизируется.

### Явно не наша аудитория

Игроки, которым нужны соревнование в реальном времени, рейтинги, кланы, прогрессия и коллекционирование.

## 3. Границы MVP

### Входит в MVP

1. Три головоломки в день, по четыре карточки, перетаскивание для смены порядка.
2. Неограниченные перестановки до нажатия «Проверить»; после проверки попытка фиксируется.
3. Показ правильного порядка и короткого объяснения после проверки.
4. Подсчёт баллов по парам: у четырёх карточек шесть уникальных пар, 1 балл за каждую пару в правильном относительном порядке. Максимум 6 за головоломку и 18 за день.
5. Серия дней (streak) — засчитывается за завершение всех трёх заданий, независимо от результата.
6. Итог дня и карточка результата для отправки без спойлеров.
7. Архив пройденных дней и базовая статистика.
8. Настройки: звук, вибрация, уведомление-напоминание, тема, «о приложении», источники.
9. Последовательная выдача наборов: каждый пользователь получает наборы по порядку от первого, независимо от даты установки. Пропущенный день не расходует контент. За одну локальную календарную дату выдаётся не более одного нового набора.
10. Контентный пакет: 105 проверенных головоломок = 35 наборов, поставляется вместе с приложением. Этого объёма достаточно **для альфы**, но не для публичного релиза — см. «Объём контента» ниже.
11. Полная работоспособность офлайн и без регистрации.
12. Контекстные подсказки при первом запуске (не отдельный onboarding-экран).
13. Доступность: альтернатива перетаскиванию, поддержка TalkBack, увеличенного шрифта, тёмной темы.
14. Действие «Сообщить о неточности» — `mailto`-письмо с предзаполненным `puzzleId`, версией приложения и версией контента. Сети не требует: письмо отправляет сам пользователь из своего почтового клиента.

### Явно исключено из MVP

| Исключено | Причина |
| --- | --- |
| Рейтинги, лидерборды, PvP, дуэли | Требуют backend и аккаунтов; противоречат спокойному тону |
| Чаты, комментарии, друзья, соцсеть | То же + модерация, непосильная для соло-проекта |
| Пользовательский контент, редактор головоломок | Модерация и юридические риски |
| Аккаунты, авторизация, облачная синхронизация | Прямо запрещены техническими ограничениями; прогресс локальный |
| Backend любого вида, серверная доставка контента | Контент едет в APK; обновление — через обновление приложения |
| Глобальный общий набор дня (challenge of the day) | Требует жёсткой привязки набора к календарной дате для всех пользователей сразу. С последовательной выдачей несовместимо; осмысленно возвращать только вместе с backend и сравнением результатов. **Явно вне MVP** |
| Реализация рекламы и покупок | Только архитектурные границы, без SDK. В будущем это два независимых поставщика: покупки — RuStore Pay SDK, показ рекламы — SDK отдельной рекламной сети |
| Тренировочный режим по архивным наборам | Потребовал бы второй модели прогресса — баллов, не влияющих на статистику и серию, — и объяснения, зачем в приложении два вида результатов. **Решено не делать в MVP**; способ «поиграть ещё» даёт выпуск новых пакетов |
| Аналитика с внешним SDK | Только интерфейс и локальная реализация-заглушка |
| Splash-экран, многошаговый onboarding | Прямо исключены требованиями |
| Таймеры, ограничение времени на ответ | Противоречит позиционированию «спокойная игра» |
| Подсказки в бесплатном контуре | Подсказка зарезервирована под rewarded-рекламу; в MVP не реализуется |
| Повторное прохождение сегодняшнего дня | Ломает честность дневного результата |
| Локализация на другие языки | Продукт русскоязычный по определению; строки всё равно выносятся в ресурсы |
| Планшетные и складные раскладки как отдельный дизайн | Достаточно адаптивной вёрстки; отдельный layout не проектируется |
| Виджеты, Wear OS, Android Auto | За пределами ценности MVP |

### Спорные решения, зафиксированные волевым порядком

Требования не содержат ответа на несколько вопросов; ниже — рекомендуемые варианты, принятые для проектирования. Их можно изменить до старта реализации.

1. **Прошлые дни в архиве играть нельзя.** Архив только для просмотра результата и объяснений. Иначе понятие «серия» и «дневной результат» размывается, а 35 наборов расходуются за неделю. Тренировочный набор (practice) вынесен в rewarded-контур и в MVP не реализуется.
2. **Пропущенный день полностью обнуляет текущую серию; лучшая серия сохраняется.** Решение окончательное. Никаких «заморозок», исключений вида «один пропуск в неделю» и платных восстановлений — это механика удержания из free-to-play, чужеродная продукту. «Лучшая серия» показывается рядом с текущей, чтобы обнуление не читалось как потеря всего достигнутого. Смягчающее обстоятельство уже встроено в продукт иначе: при последовательной выдаче пропуск не отнимает контент, поэтому цена пропуска и так невелика.
3. **Незавершённый день не переносится.** Если пользователь прошёл 2 из 3 головоломок и наступил новый день, вчерашний день остаётся незавершённым, серия прерывается, доигрывать нельзя. Прогресс по пройденным головоломкам сохраняется в архиве.
4. **Наборы выдаются последовательно, а не по календарю.** Первый запуск даёт набор №1 кому угодно и когда угодно. Пропущенный день не тратит набор. За одну локальную дату выдаётся не более одного нового набора, и назначение `localDate → setIndex` фиксируется в момент начала сессии. Следствие: 105 головоломок дают каждому пользователю ровно 35 активных дней независимо от даты установки.
5. **Цена этого решения — потеря сравнимости, и это главный компромисс MVP.** У двух человек в одну и ту же дату разные задания, поэтому карточка результата больше не приглашает сравнить себя с другими: она остаётся личной отметкой прогресса. Принято сознательно, потому что альтернатива — жёсткая привязка к календарю — наказывает каждого, кто установил приложение позже первого дня, то есть подавляющее большинство аудитории. Восстановить сравнимость можно только вместе с глобальным набором дня, что вынесено за пределы MVP.
6. **День определяется по локальной дате устройства.** Без сверки с сервером (сервера нет). Подробности и защита от перевода часов — в `UX_FLOW.md`.

### Объём контента: альфа против публичного релиза

105 головоломок (35 наборов) — это объём **для альфы**: закрытого теста на ограниченном круге людей, где задача — проверить механику, тон и качество объяснений, а не удержание.

При последовательной выдаче все пользователи упираются в конец контента одинаково — ровно на 36-й активный день, независимо от даты установки. Публичный релиз с таким запасом означает, что весь первый набор аудитории упрётся в тупик в пределах пяти-шести недель.

**Условие публичного релиза — выполнено хотя бы одно:**

- в приложении не менее **60 активных дней** контента (180 проверенных головоломок), либо
- следующий пакет **полностью готов**: написан, проверен по редакторскому протоколу, прошёл валидатор и собран в билд, ожидающий публикации.

Смысл требования: к моменту, когда первые пользователи дойдут до конца, продолжение уже должно существовать, а не планироваться. Подготовка контента — самая длинная задача проекта, и она не ускоряется под давлением сроков релиза.

## 4. Основной игровой цикл

### Дневной цикл (2–4 минуты)

```
Открыть приложение
      │
      ▼
Главный экран: «Задание дня», серия, короткая статистика
      │  «Играть»  ──▶  фиксируется назначение localDate → setIndex
      ▼
Головоломка 1 из 3
  ├─ формулировка + направление сортировки
  ├─ 4 карточки в перемешанном порядке
  ├─ пользователь меняет порядок (перетаскивание / кнопки ↑↓)
  └─ «Проверить»  ──▶  попытка зафиксирована, изменения запрещены
      │
      ▼
Результат головоломки
  ├─ правильный порядок со значениями карточек
  ├─ баллы 0–6 (по шести парам) и перечень перепутанных пар
  ├─ короткое объяснение
  └─ «Дальше»
      │
      ├──▶ Головоломка 2  ──▶ Результат
      └──▶ Головоломка 3  ──▶ Результат
                                  │
                                  ▼
                          Итог дня: N из 18, серия, карточка для отправки
                                  │
                                  ▼
                      Главный экран (состояние «день завершён»)
```

### Долгий цикл (недели)

```
Уведомление  ──▶  дневная сессия  ──▶  серия +1  ──▶  повод вернуться завтра
     ▲                                                          │
     └──────────────────────────────────────────────────────────┘
                             архив и статистика
                       (сколько дней, средний балл, лучшая серия)
```

### Что удерживает

- **Серия** — основной, но мягкий крючок: она про присутствие, а не про качество результата.
- **Объяснение** — то, ради чего игру запоминают: пользователь уходит с фактом, а не с числом.
- **Уведомление** — единственный внешний триггер, одно в день, отключаемое, без «ты теряешь серию!»-давления.

### Чего в цикле сознательно нет

Нет наград за скорость, нет комбо-множителей, нет ежедневных «сундуков», нет возврата за просмотр рекламы. Цикл должен быть скучным по структуре и интересным по содержанию.

## 5. Продуктовые риски

| ID | Риск | Вероятность / влияние | Признак | Ответ |
| --- | --- | --- | --- | --- |
| R-1 | Контент кончается на 36-й активный день. При последовательной выдаче в тупик упираются **все** пользователи одинаково, а не только ранние | Высокая / высокое | `setIndex` достиг последнего набора | Два уровня защиты. Продуктовый: 105 головоломок — объём для альфы, публичный релиз только при ≥60 активных днях контента или полностью готовом следующем пакете. Технический: заранее спроектированное состояние `ContentExhausted` — честный экран «новые задания готовятся», сохранение архива, статистики и **лучшей** серии, доступ к архиву через кнопку «Открыть архив». Текущая серия при этом не замораживается и прервётся: обещать паузу, а потом показать обнулённую серию, хуже, чем не обещать. Обновление самого приложения через RuStore идёт обычным системным механизмом (магазин, а не приложение, уведомляет об обновлении) — выделенной ссылки на обновление именно на этом экране в MVP нет |
| R-2 | Головоломка оказывается неоднозначной (два допустимых порядка) — прямой удар по доверию, а исправить без обновления нельзя | Средняя / очень высокое | Жалобы, споры, письма «Сообщить о неточности» | Жёсткий редакторский протокол и проверка однозначности до сборки (см. `CONTENT_MODEL.md`), запрет на «примерно равные» значения, обязательные источники на каждую карточку, автоматическая валидация контента в CI. Плюс канал раннего обнаружения: действие «Сообщить о неточности» с предзаполненным `puzzleId` — узнать об ошибке от первого внимательного пользователя дешевле, чем от тридцатого через оценку «2 звезды» |
| R-3 | Факт устаревает после релиза (население, рекорд, «самый высокий») | Средняя / высокое | Тихая ошибка | Правило «только стабильные во времени признаки», поле `volatility` у головоломки, запрет на изменчивые величины без привязки к дате |
| R-4 | Слишком легко → скучно; слишком сложно → фрустрация | Средняя / среднее | Средний дневной балл держится у 18 или около 9 | У парного подсчёта есть полезное свойство: случайный порядок даёт в среднем ровно 3 из 6 за головоломку и 9 из 18 за день. Результат около 9 — это статистически «угадывание», и это готовая точка отсчёта. Целевой средний дневной результат для вовлечённого игрока — 13–15 из 18; сложность регулируется близостью значений; перед релизом — ручная калибровка наборов |
| R-5 | Перетаскивание четырёх карточек ощущается неуклюжим (мелкие цели, лаги, конфликт со скроллом) | Средняя / высокое | Отказы на первом задании | Экран без вертикальной прокрутки на типичном телефоне, крупные карточки, длинное нажатие не требуется, всегда доступны кнопки перемещения, обязательный тест на слабом устройстве |
| R-6 | Шеринг почти не даёт роста: без общего набора дня карточка не приглашает к сравнению | Высокая / среднее | Мало отправок | Риск сознательно принят вместе с последовательной выдачей (раздел 3, пункт 5). Смягчение: карточка становится отметкой личного прогресса — «День 12, серия 6», читаемая в любом мессенджере, без названий заданий. Роль главного канала роста переходит к карточке в RuStore, а не к шерингу. Полноценно вернуть сравнимость может только глобальный набор дня — вне MVP |
| R-7 | Отсутствие мотивации без соревнования: «зачем мне баллы» | Средняя / среднее | Отток после 3–5 дней | Смещение акцента с очков на факт и серию: объяснение — главный экран результата, а не сноска |
| R-8 | Первый день непонятен: пользователь не догадывается, что карточки перетаскиваются | Низкая / высокое | Уход с первой головоломки без проверки | Контекстная подсказка на первой карточке, лёгкая анимация «покачивания», подпись направления сортировки прямо у списка |
| R-9 | Уведомления воспринимаются как навязчивые и приложение отключают целиком | Низкая / среднее | Отзывы, отписки | Максимум одно в день, спрашивать разрешение не при первом запуске, а после первого завершённого дня; нейтральный тон |
| R-10 | Реклама, добавленная позже, ломает тон продукта | Средняя / высокое | Падение оценок после обновления | Границы зафиксированы архитектурно и продуктово: не чаще одного показа в сутки, только после завершённой сессии, никогда до и не между заданиями |

## 6. Критерии проверки гипотезы

**Гипотеза.** Русскоязычной аудитории 20–45 лет нужен спокойный ежедневный ритуал на фактах, и механики упорядочивания достаточно, чтобы возвращаться без соревнования и наград.

### Что мы в принципе способны измерить в MVP

Это надо зафиксировать честно, до всяких порогов. Внешнего аналитического SDK в MVP нет, backend нет, аккаунтов нет. **Значит, разработчик не видит поведения пользователей.** Ни удержания, ни завершаемости сессий, ни средних баллов по аудитории. Локальные показатели считаются на устройстве и видны только самому пользователю — наружу они не уходят.

Доступны ровно три источника:

| Источник | Что даёт | Чего не даёт |
| --- | --- | --- |
| Локальные показатели на устройстве | Пользователю — его статистику. Разработчику — те же цифры, но только на своих тестовых и альфа-устройствах | Ничего об аудитории в целом |
| Ручное тестирование и альфа-группа | Понимание механики, длительность сессии, места отказа, качество объяснений | Масштаб и статистическую значимость |
| RuStore Console | Установки, просмотры карточки приложения, конверсия «просмотр → установка», оценки и текст отзывов | Поведение внутри приложения |

**Удержание (D1/D7/D30) в MVP измерить нечем.** Любой порог вида «D7 ≥ 25%» до подключения внешней аналитики непроверяем, и ставить такие цели — самообман. Ранее записанные в этом документе пороги удержания удалены именно поэтому.

**Подключение внешней аналитики — отдельное решение после MVP.** Оно требует собственного разбора: какой поставщик, какие данные уходят с устройства, что написано в политике конфиденциальности, как это согласуется с обещанием «ничего не собираем». Интерфейс `AnalyticsTracker` с no-op реализацией существует в коде именно для того, чтобы это решение можно было принять позже, не переписывая экраны.

### Контур A — локальные показатели

Считаются на устройстве и показываются пользователю в статистике. Как инструмент проверки гипотезы применимы только на устройствах альфа-группы, где цифры можно посмотреть глазами или получить скриншотом.

| Показатель | Как считается | Целевой ориентир |
| --- | --- | --- |
| Завершаемость дня | дней с 3/3 заданиями ÷ дней с ≥1 заданием | ≥ 80% |
| Средний дневной балл | среднее по завершённым дням | 13–15 из 18 (случайный порядок даёт 9) |
| Доля брошенных головоломок | открыта, но не проверена | ≤ 10% |
| Длина серии | текущая и лучшая | медиана ≥ 4 к третьей неделе |

### Контур B — сигналы магазина

| Сигнал | Порог, при котором гипотеза считается подтверждённой |
| --- | --- |
| Конверсия «просмотр карточки → установка» | ≥ 20% — позиционирование и оформление карточки понятны |
| Оценка в RuStore | ≥ 4,3 при 30+ отзывах |
| Отзывы про факты и объяснения | упоминаются чаще, чем баллы и рекорды |
| Жалобы на неоднозначные ответы | ≤ 2% отзывов; ни одной подтверждённой фактической ошибки |
| Упоминания «мало заданий» | появляются — сигнал, что ритуал сформировался и контент кончился раньше интереса |

### Контур C — ручные проверки и альфа-группа

Основной инструмент проверки гипотезы в MVP. Проводится до публичного релиза.

- 5–7 человек из целевой аудитории проходят **не менее семи дней подряд** на своих устройствах (три дня показывают понятность механики, но не ритуал);
- ≥ 5 из 7 без подсказки понимают, что карточки перетаскиваются, и доходят до итога дня;
- ≥ 4 из 7 возвращаются на следующий день без напоминания от разработчика;
- никто не задаёт вопрос «а почему такой порядок правильный» после прочтения объяснения;
- никто не спрашивает, как считаются баллы, дважды: правило парного подсчёта должно быть понято с первого результата;
- сессия укладывается в 2–4 минуты;
- полное прохождение с включённым TalkBack и шрифтом 200% возможно без перетаскивания;
- по итогам — короткое интервью: что запомнилось из фактов, вернулись бы сами.

### Условия опровержения

Гипотезу считаем неподтверждённой, если:

- в альфа-группе меньше половины участников возвращаются на второй и третий день по своей воле — ежедневный ритуал не формируется;
- завершаемость дня в альфа-группе < 60% — механика или контент не удерживают внутри сессии;
- участники не могут вспомнить ни одного факта из пройденных заданий — обучающая ценность, на которой стоит продукт, не работает;
- подтверждены ≥ 2 фактические ошибки в контенте — приоритет смещается на редакторский процесс до любой продуктовой работы;
- в отзывах доминирует «мало заданий» при хорошей оценке — это **не** опровержение гипотезы, а сигнал ускорить контент-пайплайн.

Отдельно: если по итогам альфы окажется, что для решения о развитии продукта не хватает именно поведенческих данных, — это и есть момент вернуться к вопросу о внешней аналитике, а не пытаться додумать удержание по числу установок.
