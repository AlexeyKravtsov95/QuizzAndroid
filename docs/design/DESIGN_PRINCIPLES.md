# DESIGN_PRINCIPLES.md — «По порядку!»

Design Gate, часть B1. Статус: утверждено, 2026-08-30. Визуальное направление — концепция D «Альманах исследователя» (`design/concepts/concept-d.svg`, `design/concepts/HYBRID.md`), утверждена пользователем.

Приоритет источников при любом конфликте: 1) `docs/PRODUCT.md`, `docs/UX_FLOW.md`, `docs/ARCHITECTURE.md`, `docs/CONTENT_MODEL.md`, `docs/IMPLEMENTATION_PLAN.md`; 2) концепция D; 3) настоящий документ и остальные документы `docs/design/`; 4) Material 3; 5) общие рекомендации UI/UX. Этот документ не меняет продукт и UX ради удобства дизайна — он объясняет решения концепции D через их привязку к конкретным значениям в `DESIGN_TOKENS.md`, а не через эпитеты.

## 1. Суть продукта

Каждое визуальное решение в этом документе подчинено пяти фактам о продукте (`PRODUCT.md`, разделы 1–2):

1. **Ежедневный спокойный ритуал**, а не сессия, которую нужно продлевать. Интерфейс не должен создавать ощущение незавершённости или подталкивать оставаться дольше 2–4 минут.
2. **Взрослая аудитория 20–45 лет**, «любители фактов», не считающие себя геймерами. Интерфейс обращается к ним как к читателям, а не как к игрокам.
3. **Интеллектуальное развлечение без давления** — ни таймеров, ни «жизней», ни штрафной риторики за пропуск дня.
4. **Факты и объяснение важнее очков.** Экран результата (`PuzzleResult`) типографически весомее счёта: объяснение — `bodyLarge`, счёт — компонентный токен `ScoreBadge`, а не display-заголовок.
5. **Одна короткая сессия в день.** Ничего в визуальном языке не намекает на «ещё один раунд» — нет прогресс-баров, ведущих за пределы сегодняшних трёх заданий.

## 2. Визуальная метафора

Концепция D — «современный альманах, в котором факты организованы с точностью исследовательского каталога» (`HYBRID.md`, раздел 1). Практически это означает:

- **Современный альманах.** Основа — редакционная типографическая иерархия: serif для содержания, sans для интерфейса, hairline-разделители вместо рамок и теней (см. `concept-a.svg`, унаследовано без изменений).
- **Исследовательская систематизация.** Ограниченный набор точек, где это видно: моно-нумерация (`Metadata`, `CardIndex`, `IssueNumber`), небольшая каталожная метка категории (`CategoryLabel`), индексная зона `OrderableCard`.
- **Редакционная иерархия остаётся главной.** Каталожные элементы — акцент, не основа: если убрать все моно-элементы, экран должен по-прежнему читаться как альманах, а не как пустой каркас.
- **Точечность каталожных элементов проверяема:** ровно один срезанный угол (`OrderableCardCutCorner`, только у `OrderableCard`), ровно один хвойно-зелёный основной интерактивный цвет (`primary`), ровно четыре типа контента, где допустим mono (`DESIGN_TOKENS.md`, раздел 6.3). Любой пятый — нарушение.
- **Интерфейс не выглядит старым архивом.** Запрещены: линованный/бумажный фон-текстура, состаренные тона (сепия, хаки, потёртый край), штампы на каждом элементе, декоративные «печати». Палитра тёплая, но современная — бумага `#F6F0E2`, а не крафт или пергамент с текстурой.

## 3. Иерархия внимания по экранам

Порядок перечисления — порядок, в котором взгляд должен встречать элементы. Экран не прошёл ревью, если эта последовательность визуально нарушена (например, вторичный элемент крупнее или контрастнее первичного).

### Home

1. `DailyIssuePanel` (день + серия + лучший день + сыграно дней как единая композиция со spine-меткой; в `FirstRun` — без строк статистики, см. `COMPONENTS.md`) — самый весомый элемент экрана по совокупности размера и позиции.
2. `PrimaryButton` «Играть»/«Начать»/«Продолжить»/«Посмотреть итог» — единственное следующее действие.
3. `HomeHeader` (мастхед «ПО ПОРЯДКУ!», дата, иконки архива/настроек) — контекст, перифериен, не крупнее `titleMedium` по зрительному весу, не привлекает внимание раньше пункта 1.

В состоянии `ContentExhausted` иерархия другая и зафиксирована отдельно: `HomeHeader` → нейтральный текст об исчерпании контента → `StatisticsBlock` (сохранённая статистика) → `PrimaryButton` «Открыть архив». `DailyIssuePanel` в этом состоянии не показывается вовсе — см. `COMPONENTS.md`, state sheet `ContentExhausted`.

Категория дня **не входит** в иерархию Home ни на каком уровне: она не показывается (`UX_FLOW.md`, раздел 3).

### Puzzle

1. Формулировка задания (`EditorialTitle`, serif) — то, ради чего открыт экран.
2. Список из четырёх `OrderableCard` — основная рабочая область.
3. `PrimaryButton` «Проверить» — закреплён внизу, всегда видим без прокрутки при обычном шрифте.
4. Подпись направления сортировки — подчинена карточкам, но должна быть прочитана до первого перемещения (позиционируется между формулировкой и списком, не после).
5. Шапка (номер задания, `CategoryLabel`, кнопка назад) — контекст, самый низкий приоритет на экране.

### PuzzleResult

1. Правильный порядок со значениями карточек — обучающая часть, идёт первой.
2. Объяснение (`bodyLarge`) — вторая по весу текстовая единица экрана, весомее счёта.
3. `ScoreBadge` («N из 6») — заметен, но не крупнее объяснения по площади.
4. `ScoringHint` (только на первом в жизни `PuzzleResult`) — сразу под `ScoreBadge`, `bodyMedium`, подчинена счёту.
5. Перечень перепутанных пар (`InvertedPairRow`) — подчинён объяснению, использует терракоту (`tertiary`), не сигнальный красный (`error` не используется на этом экране).
6. `SourcesBlock` (свёрнутый по умолчанию) и `ReportInaccuracyAction` — низший приоритет, `bodySmall`/`labelSmall`.
7. `PrimaryButton` «Дальше»/«К итогу дня» — закреплена внизу, всегда доступна.

### DayRecap

1. Итоговый счёт «N из 18» — крупнейший текстовый элемент экрана.
2. Три строки `DayResultRow` (категория + результат по каждому заданию).
3. `StreakRow` (серия, лучшая серия при обновлении рекорда).
4. `SecondaryButton` «Поделиться» (формирует текст через невизуальный `ShareCardBuilder` — `ShareCard` сам по себе не Compose-компонент и в иерархии экрана не участвует, см. `COMPONENTS.md`).
5. `PrimaryButton` «Готово»/«Назад».

### Archive

1. `Statistics block` (сыграно дней, средний балл, лучший день, серия) — сводка, видна без прокрутки.
2. Список дней (`Archive row`) — основная прокручиваемая область.

### Settings

1. Список настроек (`Settings row`), сгруппированный по смыслу (звук/вибрация/напоминание → тема → о приложении/источники → обратная связь) — плоский список без визуальной иерархии внутри себя: ни одна строка настроек не крупнее и не контрастнее другой.

## 4. Плотность и пустое пространство

- **Редакционное поле.** Пространство считается редакционным полем (то есть намеренным и правильным), если оно: (а) отделяет смысловые блоки друг от друга по вертикальной шкале отступов (`DESIGN_TOKENS.md`, раздел 6.5), и (б) не может быть заполнено существующим продуктовым контентом без искажения состояния экрана (пример: пространство под статистикой на Home в состоянии `Ready` — там нет дополнительных полей `HomeUiState.Ready`, заполнить нечем).
- **Потерянное пространство.** Пространство считается потерянным, если тот же экран в том же состоянии содержит контент, который мог бы туда переместиться, но остался разрознен (это была диагностированная проблема исходной концепции A на Home — решена в D слиянием дня и статистики в `DailyIssuePanel`, `HYBRID.md` раздел 5). Ревьюер обязан отклонить макет, где такое разрознение появилось вновь.
- **Запрет фиктивного контента.** Пустое пространство никогда не закрывается: цитатами, случайными фактами, декоративными иллюстрациями, категорией дня, счётчиками с нулевыми/бессмысленными значениями. Единственный легальный способ уменьшить пустоту — более плотная композиция уже существующих полей состояния экрана.
- **Плотность Puzzle.** Задание должно помещаться на экране 390 × 844 без обязательной прокрутки при системном масштабе шрифта 100% (`UX_FLOW.md`, раздел 4). Бюджет высоты фиксирован в `DESIGN_TOKENS.md` (раздел 6.5, «Puzzle vertical budget»). Если новый элемент не помещается в бюджет — сокращается не карточка и не кнопка «Проверить», а второстепенный текст (например, длина `directionLabel`).
- **320 dp.** На ширине 320 dp сокращается только горизонтальный отступ экрана (24 dp → 16 dp, токен `spacing.margin.compact`) и ширина центральной текстовой колонки `OrderableCard`. Индексная зона, кнопки перемещения, ручка перетаскивания и срезанный угол не уменьшаются — это проверено на стресс-примере `concept-d.svg`.
- **200%.** При удвоенном шрифте компоненты растут по высоте, а не сжимаются по ширине. Ни один компонент не имеет фиксированной высоты, кроме кнопок и сенсорных целей (`DESIGN_TOKENS.md`, раздел 6.5) — они масштабируются по тексту, а не наоборот.

## 5. Типографическая логика

- **Serif — содержательные заголовки и факты.** Формулировка задания, слово «День» в `IssueNumber`, название карточки (`titleLarge` в `OrderableCard`), правильный порядок на `PuzzleResult`. Правило проверяемо: если элемент — это факт или его название, он serif; если это управление или мета-информация, он не serif. **Явное исключение — мастхед `HomeHeader` (роль `Masthead`).** Это не нарушение правила «serif только для фактов»: мастхед — фирменная редакционная подпись продукта, а не обычная навигационная шапка экрана и не факт о головоломке. Единственное такое исключение в системе; ни один другой заголовок интерфейса (`AppTopBar`, заголовки секций) его не получает.
- **Sans — интерфейс и управление.** Кнопки, шапки экранов, значения статистики, тело объяснений, настройки. Ничего из перечисленного не переводится на serif ради «редакционности» — это разрушило бы проверяемость правила выше.
- **Mono — ровно четыре места, и только они:** дата (`Metadata`), номер дня (числовая часть `IssueNumber`), номер карточки `№1…№4` (`CardIndex`), метка «ВЫПУСК» (`IssueLabel`). `CapsLabel` (метки строк статистики — «СЕРИЯ», «ЛУЧШИЙ ДЕНЬ», «СЫГРАНО ДНЕЙ») — **не mono**, это Golos Text (sans) с трекингом и регистром поверх `labelSmall`; совпадение размера/трекинга с `IssueLabel` не делает их одной ролью или одним семейством шрифта. Полный перечень — раздел 6.3/6.4 `DESIGN_TOKENS.md`; расширять его без изменения этого документа запрещено.
- **Запрет расширять mono на обычный текст.** Объяснение, формулировка задания, названия карточек, текст настроек, содержимое `SourcesBlock` — никогда mono, вне зависимости от того, насколько «каталожно» выглядела бы страница.
- **Переносы русских слов.** Перенос — это перенос, выполняемый движком переноса Compose (`hyphens = Hyphens.Auto` при поддержке платформы) или естественный перенос по пробелу/дефису, уже присутствующему в слове (например, «санкт-петербург» переносится по существующему дефису). Название карточки и формулировка задания не обрезаются эллипсисом — при нехватке ширины строка переносится целиком на новую строку.
- **Запрет вручную вставлять дефисы ради макета.** Ни в UI-коде, ни в контенте не допускается символ мягкого переноса (`­`) или обычного дефиса, вставленный только для того, чтобы слово разместилось в текущей ширине контейнера. Пример со стресс-борда `concept-d.svg` («Кили-манд-жаро») — это иллюстрация того, как *движок* перенесёт слово при недостатке места, а не образец текста для вставки заранее. Единственное исключение — слова, где дефис — часть орфографии (например, «Санкт-Петербург», «из-за»).

## 6. Формы и поверхности

- **Единственный фирменный срезанный угол.** Форма `OrderableCardCutCorner` (`DESIGN_TOKENS.md`, раздел 6.6) применяется только к `OrderableCard`. Ни одна кнопка, метка, диалог, `bottom sheet` или другой контейнер его не получает — ни сейчас, ни при добавлении новых компонентов позже без пересмотра этого документа.
- **Небольшие радиусы остальных компонентов.** Кнопки, категорийная метка, три обычных угла `OrderableCard` — используют `shape.small`/`shape.medium` (6–12 dp). Полностью прямые (0 dp) или полностью скруглённые (pill, radius = половина высоты) формы не используются нигде в продукте.
- **Отсутствие декоративных теней.** Ни у одного компонента в состоянии покоя нет тени. Функциональных теней в продукте ровно две: `OrderableCard` в состоянии `dragging` (`elevation.dragged`) и `NotificationOptInDialog` — единственный диалог MVP (`elevation.dialog`). Третьего исключения не появляется без пересмотра этого документа.
- **Elevation только при функциональном подъёме или системной модальности.** Правило проверяемо буквально: если элемент не физически «поднят» пользователем в данный момент (перетаскивание) и не является активным модальным диалогом, elevation этого элемента равен `elevation.resting` (0 dp). Наведение/фокус/нажатие обычных компонентов меняют цвет через `state layer`, а не тень. Форма и тень `NotificationOptInDialog` (`shape.large`, `elevation.dialog`) не распространяются на `OrderableCard`, `DailyIssuePanel` или любой другой обычный контейнер.
- **Hairline-разделители.** Границы между строками статистики, элементами списка и секциями настроек — линия толщиной `divider.thickness` цветом `outlineVariant`, а не тень, не отступ-заменитель и не рамка вокруг блока.
- **Редакционная вертикальная метка Home.** `spine` — сплошная заливка `primary` шириной `spacing.spine.width`, идёт вдоль всего блока `DailyIssuePanel`. Это единственное место в продукте, где сплошная заливка `primary` используется как декоративно-структурный, а не только интерактивный элемент (кнопка) — исключение зафиксировано явно, чтобы не расширяться самопроизвольно на другие экраны.

## 7. Цвет

- **Роли, а не оттенки.** Бумага = `surface`/`background`; чернила = `onSurface`/`onBackground`; хвойный зелёный = `primary`; терракота = `tertiary`. Полные схемы, HEX и коэффициенты контраста — `DESIGN_TOKENS.md`, раздел 6.2.
- **Терракота не является основным CTA.** `tertiary` не применяется к `PrimaryButton`, `SecondaryButton` или любому основному действию экрана. Её легальные применения перечислены в `DESIGN_TOKENS.md` и `COMPONENTS.md` поимённо (`IssueLabel` «ВЫПУСК», текст `InvertedPairRow`) — если применения нет в списке, использовать терракоту нельзя.
- **Цвет не единственный носитель состояния.** Каждое состояние, различаемое цветом (disabled/enabled управление, правильная/перепутанная пара на `PuzzleResult`, включено/выключено в настройках), обязано иметь второй, не цветовой признак: форму (заливка против обводки), иконку, текст или позицию. Проверяется по чек-листу `UI_REVIEW_CHECKLIST.md`.
- **Динамические цвета Android отключены.** `dynamicColorScheme`/Material You не используется ни в светлой, ни в тёмной теме. Схема всегда берётся из статичных `lightColorScheme`/`darkColorScheme`, собранных из значений раздела 6.2 `DESIGN_TOKENS.md`. Причина: фирменная палитра — часть продукта (`ARCHITECTURE.md`, раздел 11), а не результат обоев пользователя.

## 8. Иконография

- **Единая line-система.** Все иконки — контурные (stroke), без заливки, кроме случаев, где заливка часть смысла (например, залитый треугольник категории «География» в `CategoryLabel` — сама пиктограмма, а не декоративный контур).
- **Размеры и толщина.** Стандартный размер иконки — `icon.size.default` (24 dp), уменьшенный — `icon.size.small` (16 dp, только внутри `CategoryLabel` и подобных компактных меток). Толщина линии — `icon.strokeWidth` (2 dp для 24 dp-иконок, 1.6 dp для 16 dp-иконок, чтобы оптическая толщина оставалась одинаковой). Значения — `DESIGN_TOKENS.md`, раздел 6.5.
- **Запрет эмодзи — с одним явным исключением.** Ни в UI, ни в контенте головоломок эмодзи не используются как иконки или носители смысла (в самом контенте это дополнительно закрыто схемой `CONTENT_MODEL.md`). **Единственное исключение — текстовый payload `ShareCard`**: символы 🟩/⬜, формирующие шкалу результата (`UX_FLOW.md`, раздел 6). Это не визуальный Compose-компонент и не иконка интерфейса — это содержимое строки, которую строит `ShareCardBuilder` и передаёт в системный `Intent.ACTION_SEND`; на экранах приложения эти символы никогда не рендерятся как UI.
- **Категории имеют иконку и текст всегда вместе.** Ни один экран не показывает только иконку категории без текстового названия и не показывает категорию только цветом.
- **Иконки управления не становятся декоративными.** Ручка перетаскивания, стрелки перемещения, шеврон «назад» — всегда прикреплены к работающему элементу управления с сенсорной целью ≥ 48×48 dp. Иконка без действия за ней не размещается на экране ни при каких обстоятельствах.

## 9. Motion

Полные значения длительностей и кривых — `DESIGN_TOKENS.md`, раздел 6.8. Здесь фиксируется, *что именно* анимируется и почему.

| Событие | Анимируется | Не анимируется |
| --- | --- | --- |
| Перестановка карточки (кнопка ↑/↓ или drag-and-drop) | Позиция карточки (layout-анимация, `motion.duration.long`, `motion.easing.standard`) | Номер позиции внутри `CardIndex` — обновляется мгновенно вместе с перестановкой, не «доезжает» отдельно |
| Захват карточки (`dragging`) | Elevation 0→`elevation.dragged` (`motion.duration.medium`, `motion.easing.standardAccelerate` на подъём); масштаб карточки не меняется в этом состоянии | Масштаб карточки; поворот/наклон карточки — оба не используются в `dragging`. Поворот в принципе существует в системе только один раз — как одноразовое покачивание `DragEducationHint` (`dragHint.wobbleAmplitude`), и это не часть обычного состояния `dragging` |
| Отпускание карточки | Возврат elevation к `elevation.resting` (`motion.duration.medium`, `motion.easing.emphasizedDecelerate`) | «Пружинный» перелёт с overshoot — запрещён (см. запреты ниже) |
| Нажатие любой кнопки/`MoveButton` | State layer (`opacity.pressedStateLayer`, `motion.duration.short`, линейно) | Масштаб кнопки (нет scale-эффекта нажатия) |
| Переход к экрану результата (`Puzzle` → `PuzzleResult`) | Вход нового экрана — `motion.duration.long`/`motion.easing.standardDecelerate`; выход текущего — `motion.duration.medium`/`motion.easing.standardAccelerate` (вход медленнее выхода — «exit faster than enter») | Само число баллов не анимируется счётчиком — оно уже финально в момент показа |
| Появление результата построчно (`PuzzleResult`) | Каждая строка — фейд, `motion.duration.short`, сдвиг между строками `motion.stagger.resultReveal` = 60 мс (значение зафиксировано в `UX_FLOW.md`, раздел 5, и перенесено без изменений) | Победные эффекты, свечение, изменение цвета при 6 из 6 |
| Переключатель в настройках | Стандартная M3-анимация переключателя (`motion.duration.short`) | — |

**Что не анимируется никогда:** фон экрана, типографика (нет анимации цвета/веса текста), значение `ScoreBadge` (не считается вверх), число серии (не «прокручивается»).

**disabled↔enabled переход `MoveButton` — не мгновенный и не отдельный.** Он анимируется (`motion.duration.short`, 100 мс), и начинается синхронно с `motion.duration.long`-перестановкой карточки, которая его вызывает — то есть у него нет собственной, задержанной анимации, но и нет резкого «прыжка» без перехода: обе анимации стартуют в один и тот же момент и завершаются в разное время (100 мс и 300 мс соответственно), что визуально нормально для двух независимых свойств одного элемента.

**Системное «Убрать анимацию».** Если включена настройка ОС (`LocalAccessibilityManager`/аналог), все токены `motion.duration.*` разрешаются в 1 мс, `motion.stagger.resultReveal` — в 0 мс, кривая — линейная. Анимация не отключается вырезанием переходов из кода (это ломает layout-инвалидацию некоторых Compose-анимаций) — она резко ускоряется до незаметной.

**Запрещено безусловно:** bounce/overshoot-кривые (в том числе `spring()` с `dampingRatio` ниже `DampingRatioNoBouncy`), конфетти, вспышки, победные звуковые/визуальные комбо, любая анимация, обозначающая «выигрыш» отдельно от нейтрального показа результата (`UX_FLOW.md`, раздел 5: «результат 6 из 6 отмечается сдержанно»).

## 10. Тон текста

- **Спокойный и нейтральный.** Формулировки — по образцу `CONTENT_MODEL.md` (раздел 8, шаг 4): без восклицаний, без «а вы не знали?», без обращения на «ты».
- **Без обвинений за пропуск.** Строка «Вчера день остался незавершённым» (`UX_FLOW.md`, раздел 9) — ровно так, без «!», без «увы», без предложений «наверстать». Этот тон обязателен для любого будущего текста о пропущенных днях или обнулённой серии.
- **Без восклицаний ради удержания.** Уведомления, тексты кнопок и системные сообщения не используют «!» как приём вовлечения. Восклицательный знак в названии продукта («По порядку!») — часть нейм-брендинга, не паттерн для остального текста.
- **Без инфантильных формулировок.** Никаких уменьшительных форм («заданьице», «карточка-малышка»), обращений как к ребёнку, восторженных превосходных степеней («супер!», «вау!»).

## 11. Запрещённые решения (anti-slop список)

Каждый пункт — проверяемый факт о макете, не оценочное суждение.

| Запрещено | Проверяемый признак нарушения |
| --- | --- |
| AI-градиенты (фиолетово-синие и любые другие декоративные) | В коде компонента присутствует `Brush.linearGradient`/`radialGradient` на фоне контента, не являющемся частью официальной M3 тональной elevation-системы |
| Glassmorphism | Использован `blur()`/полупрозрачный фон с размытием под элементом |
| Neon | Насыщенность (S в HSL) любого цвета токена выше значений, зафиксированных в `DESIGN_TOKENS.md`, раздел 6.2, для одноимённой роли |
| Pill-интерфейс | Радиус скругления равен половине высоты компонента у кнопки, метки или карточки |
| Карточка вокруг каждого текстового элемента | Более одного вложенного `Surface`/`Card` на один смысловой блок без функциональной причины (например, обычная строка настроек обёрнута в собственную карточку) |
| Чрезмерные тени | `elevation` > `elevation.resting` (0 dp) вне состояния `dragging` или вне `NotificationOptInDialog` — только эти два исключения существуют |
| Случайные радиусы | Значение `cornerRadius`, не входящее в перечень `shape.*` (`DESIGN_TOKENS.md`, раздел 6.6) |
| Декоративные фигуры | Любой SVG/Canvas-элемент на экране, не входящий в инвентарь `COMPONENTS.md` и не несущий продуктового значения |
| Огромные заголовки | Роль `displayLarge`/`displayMedium`/`displaySmall` использована на любом из шести экранов продукта (эти роли зарезервированы, не задействованы в MVP — раздел 6.4 `DESIGN_TOKENS.md`) |
| Generic dashboard | Более двух одинаковых по форме и размеру цветных плиток статистики подряд (симптом «плиточного» AI-дэшборда, отвергнутого ещё на этапе выбора между A/B/C) |
| Duolingo-подобная геймификация | Присутствие «жизней», индикатора XP, стрик-огня как иконки, наградного попапа |
| Казино | Присутствие обратного отсчёта, «джекпот»-эффекта, вращающихся элементов |
| Ретро-канцелярия | Текстура бумаги/линовки на фоне, состаренная палитра (сепия/хаки), потрёпанные края |
| Штампы на каждом элементе | Более одного компонента на экране использует мотив «печати» (заливка + жёсткий контур с эффектом оттиска) |
| Линованный фон | Повторяющиеся параллельные линии как фон секции или всего экрана |
| Ручные переносы слов | Символ `­` или литеральный дефис в строковом ресурсе/контенте, не являющийся частью орфографии слова |
| Нестандартные значения вне токенов | Любое числовое значение цвета, размера, радиуса, длительности или кривой в коде компонента, не являющееся ссылкой на именованный токен из `DESIGN_TOKENS.md` |
