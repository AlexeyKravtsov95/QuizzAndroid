# UI_REVIEW_CHECKLIST.md — «По порядку!»

Design Gate, часть B1. Практический чек-лист приёмки экрана и Pull Request. Каждый пункт — проверяемое утверждение (истина/ложь по конкретному признаку), не общая рекомендация. Ссылки на токены — `DESIGN_TOKENS.md`; на компоненты — `COMPONENTS.md`; на состояния экранов — `UX_FLOW.md`.

Применяется в итерациях 3, 5 и 6 `IMPLEMENTATION_PLAN.md`, и к любому PR, трогающему `ui/**`.

---

## Соответствие UX Flow

- [ ] Каждое состояние экрана в коде (`HomeUiState`, `PuzzleUiState`, и т.д.) имеет соответствующее визуальное представление, перечисленное в `UX_FLOW.md` для этого экрана — ни одно состояние не показано «как получится».
- [ ] Переходы между состояниями экрана происходят в тех точках, что описаны в `UX_FLOW.md` (например, `PuzzleResult(2) → recap/today` вычищает граф `dailySession` из бэкстека).
- [ ] Ни один экран не показывает данные, которых нет в `UiState` этого экрана (например, `PuzzleResult` не может отрисовать поле, отсутствующее в `PuzzleUiState`).

## Соответствие утверждённому состоянию

- [ ] На макете/экране нет ни одного визуального элемента вне инвентаря `COMPONENTS.md` — каждый прямоугольник, иконка, линия на экране — это конкретный именованный компонент или его состояние.
- [ ] На Home категория дня не раскрыта ни текстом, ни иконкой, ни цветом ни в одном состоянии (`Ready`, `InProgress`, `Completed`, `AwaitingNextDay`, `ContentExhausted`).
- [ ] `DailyIssuePanel` показывает день и относящееся к нему содержимое как единый композитный блок со spine-меткой — не как раздельные, разнесённые по экрану поверхности.
- [ ] Содержимое `DailyIssuePanel` в точности соответствует состоянию (`COMPONENTS.md`, таблица «Содержимое по состояниям»): `FirstRun` — без статистики; `Ready` — серия/лучший день/сыграно дней; `InProgress` — «Задание N из 3» + `ThreeStepProgress`, без счёта; `Completed` — «Сегодня: N из 18» + серия + время до следующего; `AwaitingNextDay` — «Итог: N из 18» последнего дня; `ContentExhausted`/`Error` — компонент отсутствует. Ни одно состояние не показывает содержимое другого.
- [ ] `OrderableCardCutCorner` применён ровно к одному компоненту (`OrderableCard`) и ни к одному другому элементу экрана.
- [ ] Видимость иконки «Архив» в `HomeHeader` вычисляется по `completedDayCount > 0` и факту чтения прогресса, а не по имени `HomeUiState` — код не содержит условия вида `if (state is HomeUiState.FirstRun)` для этой иконки.
- [ ] На `Home.Loading` иконка «Архив» скрыта до момента чтения прогресса (не мигает при появлении экрана); на `Home.Error` иконка «Архив» видна только если прогресс успешно прочитан и `completedDayCount > 0`.
- [ ] При недостатке ширины (320 dp и/или 200%) в `HomeHeader` мастхед остаётся первой строкой, иконки архива/настроек переносятся на отдельную строку под ним; `size.headerIcon` (48 × 48 dp) не уменьшен ни при каком переносе.

## AppTopBar

- [ ] `AppTopBar` использован на `Puzzle`, `PuzzleResult`, `DayRecap`, `Archive` и `Settings`; отдельного компонента-заголовка для `DayRecap` не создано.
- [ ] Сегодняшний итог `DayRecap` показывает заголовок «Сегодня» и **не** имеет leading-иконки «Назад»; выход с экрана — только `PrimaryButton` «Готово» или системная кнопка «назад».
- [ ] Архивный итог `DayRecap` показывает дату этого дня, имеет кнопку «Назад» в шапке (ведёт в `Archive`), а нижняя `PrimaryButton` подписана «Назад», не «Готово».
- [ ] Текст нижней кнопки и наличие leading-иконки согласованы между собой: «Готово» без иконки — сегодняшний итог, «Назад» с иконкой — архивный; смешанных сочетаний нет.
- [ ] На `Puzzle` при достаточной ширине `CategoryLabel` находится в правом слоте `AppTopBar`, выровненная по правому краю контентной колонки.
- [ ] При 320 dp и/или 200%, если `ширина заголовка + spacing.300 + ширина CategoryLabel` превышает доступную ширину, `CategoryLabel` перенесена на вторую строку шапки по левому краю заголовка, а высота `AppTopBar` выросла на высоту метки плюс `spacing.200` сверху и снизу.
- [ ] При переносе `CategoryLabel` кнопка «Назад» сохраняет 48 × 48 dp, сама метка не уменьшена (ни `labelMedium`, ни `icon.size.small`, ни внутренние отступы), ни одна сенсорная цель не сжата.
- [ ] Порядок фокуса TalkBack в шапке — «Назад» → заголовок → категория — одинаков независимо от того, перенесена метка или нет.

## Токены

- [ ] `grep` по изменённым файлам `ui/**` на `Color(0x` не даёт совпадений вне `ui/theme/Color.kt`.
- [ ] `grep` по изменённым файлам на `.dp` и `.sp` с числовым литералом не даёт совпадений вне `ui/theme/*.kt` (все размеры — ссылки на `AppTokens`/`MaterialTheme`).
- [ ] Ни одна анимация не использует числовую длительность или `CubicBezierEasing(...)` с литеральными координатами вне `ui/theme/Motion.kt`.
- [ ] Каждый использованный радиус скругления — одно из значений `shape.none/extraSmall/small/medium/large/extraLarge` или `OrderableCardCutCorner`; других значений в коде нет.

## Цвет и контраст

- [ ] Каждая пара «текст на поверхности», присутствующая на экране, входит в таблицы `DESIGN_TOKENS.md` (раздел 6.2) — если появилась новая пара, она предварительно добавлена в токены с рассчитанным коэффициентом, а не используется «по аналогии».
- [ ] Обычный текст на экране — коэффициент контраста ≥ 4.5:1 к своей поверхности (сверено по таблице, не на глаз).
- [ ] Крупный текст (`headlineSmall` и крупнее) — ≥ 3:1, и если возможно без ущерба — тоже ≥ 4.5:1.
- [ ] Значимые границы и иконки управления (`outline`, обводка disabled-`MoveButton`, обводка `SecondaryButton`) — ≥ 3:1 к своей поверхности.
- [ ] `tertiary` (терракота) не использована как заливка `PrimaryButton`/`SecondaryButton` ни в одном состоянии.
- [ ] `PrimaryButton.disabled` не содержит заливки `primary`/`onPrimary` ни в каком виде и не содержит заливки `surfaceContainer`: фон прозрачный, обводка `outline` при `opacity.disabledContent` (38%), текст `onSurface` при той же непрозрачности, `disabled`-семантика выставлена.
- [ ] `PrimaryButton.disabled` используется только в трёх местах MVP (`Puzzle.Loading`; первые `dragHint.submitLockDuration` после `DragEducationHint`; при необходимости — `Submitting`, если кнопка остаётся в дереве) — не как декоративное состояние где-либо ещё.
- [ ] Кнопка «Проверить» остаётся `disabled` **весь** период, пока `UiState` — `Submitting`, а не только первые `motion.duration.short` (100 мс); повторный `Submit` не проходит, потому что `ViewModel` принимает его только из состояния `Playing`, а не потому что действует временное окно блокировки.
- [ ] Ни одно состояние (correct/inverted pair, enabled/disabled, on/off) не различимо только по цвету — у каждого есть второй признак (форма, иконка, текст), проверено визуально построчно по экрану.
- [ ] Динамические цвета Android (`dynamicLightColorScheme`/`dynamicDarkColorScheme`) не вызваны нигде в `ui/theme/`.

## Типографика

- [ ] Serif использован только для содержательных заголовков и фактов (формулировка задания, слово «День», название карточки, правильный порядок на `PuzzleResult`) плюс ровно одно явное исключение — мастхед `HomeHeader` (роль `Masthead`), фирменная редакционная подпись, а не навигационная шапка; ни одна кнопка, метка, `AppTopBar`-заголовок или строка настроек не в serif.
- [ ] Мастхед использует именованную роль `Masthead`, а не `titleLarge` с переопределённым `letterSpacing` на месте; в коде компонента нет литерала `letterSpacing = 2.sp`.
- [ ] Mono использован ровно в четырёх местах, не больше: дата (`Metadata`), числовая часть номера дня (`IssueNumber`), `№1…№4` (`CardIndex`), метка «ВЫПУСК» (`IssueLabel`). `CapsLabel` (метки строк статистики — «СЕРИЯ», «ЛУЧШИЙ ДЕНЬ», «СЫГРАНО ДНЕЙ») — Golos Text (sans), не mono; ни принципы, ни этот чек-лист не описывают mono-вариант `CapsLabel`.
- [ ] Каждый текстовый узел на экране использует одну из ролей `DESIGN_TOKENS.md` (раздел 6.4) через `MaterialTheme.typography`/`AppTypography`, не произвольный `fontSize`.

## Естественные переносы

- [ ] В строках ресурсов и в контенте головоломок нет символа мягкого переноса (`­`, U+00AD) — `grep -RP '\xC2\xAD'` по `res/values/strings.xml` и `assets/content/` не даёт совпадений.
- [ ] Нет литерального дефиса, вставленного только ради переноса (отличимо от орфографического дефиса вроде «Санкт-Петербург» — ревьюер проверяет каждое найденное вхождение дефиса вручную на орфографичность).
- [ ] Длинные названия карточек и формулировки переносятся автоматически (`Hyphens.Auto`/перенос по пробелу), не обрезаются эллипсисом.
- [ ] Каждый видимый в макете дефис переноса стоит в орфографически допустимой точке слова (проверяется по словарю переноса ru_RU, а не на глаз). Для артбордов B2 это делает `tools/design-b2/validate.py`, проверка 2: она вытаскивает все перенесённые фрагменты из SVG и требует, чтобы каждый соответствовал точке переноса реального исходного слова.
- [ ] Ни один перенос не получен делением слова по ширине (бинарным или посимвольным поиском): такие разрывы («Располож-ите», «Кили-манд-», «Монбл-ан») отклоняются, даже если визуально помещаются.
- [ ] Текст нигде не уменьшен ради размещения — при нехватке места переносится строка или включается прокрутка, но не меняется кегль.

## Светлая тема

- [ ] Экран проверен при `Theme = Светлая` — все цвета соответствуют светлой колонке `DESIGN_TOKENS.md`.
- [ ] Ни один элемент не «унаследовал» тёмный цвет по ошибке смешения тем (визуальная проверка на отсутствие тёмных пятен на светлом фоне и наоборот).

## Тёмная тема

- [ ] Экран проверен при `Theme = Тёмная` — тёмная тема не инверсия светлой один в один (значения ролей отличаются, не просто `255 - RGB`).
- [ ] Фон — тёплый почти-чёрный (`#1C1A16`), не синевато-чёрный и не чистый `#000000` вне `scrim`.
- [ ] Терракота и хвойный зелёный использованы в осветлённых для тёмной темы вариантах (`#D68A63`/`#3E6350`), не в светлых HEX светлой темы.

## 320 dp

- [ ] Экран отрендерен на ширине 320 dp без горизонтальной прокрутки любого контейнера, кроме предусмотренных `LazyColumn`/`LazyRow`.
- [ ] Горизонтальное поле экрана — `spacing.margin.compact` (16 dp), не `spacing.margin.default`.
- [ ] Индексная зона `OrderableCard` (56 dp), зона `MoveButton` (48 dp), срез угла (18 dp) — без изменений относительно эталонной ширины 390 dp.
- [ ] Ни один текст не обрезан и не наложен на соседний элемент (визуальная проверка каждой строки).

## 390 dp (эталон)

- [ ] Все четыре карточки `OrderableCard` и кнопка «Проверить» помещаются на экране `Puzzle.Playing` без обязательной прокрутки при системном шрифте 100% (`UX_FLOW.md`, раздел 4).
- [ ] Расчётный вертикальный бюджет `Puzzle` (раздел 6.5 `DESIGN_TOKENS.md`: 766 dp содержимого против доступных 772 dp при кнопочной навигации / 796 dp при жестовой — окно 844 dp за вычетом верхнего и нижнего `safeDrawing` inset) не превышен фактической вёрсткой более чем на заявленный запас (6 dp в худшем случае навигации).

## Планшет

- [ ] На ширине ≥ 600 dp контентная колонка ограничена `maxWidth = 480.dp` и центрирована — ни один компонент не растянут на всю ширину окна.
- [ ] Отдельная раскладка для планшета не создана (по `PRODUCT.md` — только адаптивное сужение, не отдельный дизайн).

## Landscape

- [ ] В ландшафтной ориентации применено то же правило `maxWidth = 480.dp`, что и для планшета.
- [ ] Если список `OrderableCard` не помещается по высоте — включена прокрутка **и** реализован авто-скролл к краю контейнера при перетаскивании карточки к границе видимой области (обязательное условие `UX_FLOW.md`, раздел 4, при появлении прокрутки).

## Шрифт 200%

- [ ] Экран отрендерен при системном масштабе шрифта 200% — ни один текст не обрезан эллипсисом там, где это не предусмотрено `COMPONENTS.md`.
- [ ] Компоненты выросли по высоте, ни один не сжался по ширине текстовой части.
- [ ] Touch targets (48 × 48 dp), иконки (`icon.size.default`/`icon.size.small`), индексная зона `OrderableCard` (56 dp) и срез угла (18 dp) — размер не изменился относительно 100%.
- [ ] Кнопка «Проверить»/«Играть» и другие `PrimaryButton` остаются полностью видимыми и нажимаемыми (не уехали за пределы экрана из-за роста контента над ними).
- [ ] Закреплённая внизу кнопка не перекрывает контент прокручиваемой области: у scroll-контейнера есть нижний padding не меньше высоты закреплённого блока кнопок плюс `spacing.section`, и в конце прокрутки последний элемент виден целиком.
- [ ] Если при 200% контент экрана перестал помещаться, прокручивается **весь** контентный блок целиком (формулировка, подписи и список вместе), а не только его часть: заголовок не выталкивает список за пределы экрана.

## Edge-to-edge

- [ ] `enableEdgeToEdge()` активен, контент отрисовывается под системными панелями (не оставляет закрашенных «полос» под статус-баром/навигацией).
- [ ] Верхний системный inset применён к самому верхнему видимому контейнеру экрана: `AppTopBar` на `Puzzle`/`PuzzleResult`/`Archive`/`Settings`, `HomeHeader` на `Home` (во всех состояниях Home, включая `FirstRun` и `ContentExhausted`) — **не** к `DailyIssuePanel`, который не является верхним контейнером экрана.
- [ ] Нижний системный inset применён к контейнеру, где закреплена нижняя `PrimaryButton`, а не ко всему экрану целиком.

## Системные inset

- [ ] Ни один интерактивный элемент не перекрыт жестовой панелью или вырезом экрана (`WindowInsets.safeDrawing` учтён там, где применимо).
- [ ] В коде нет захардкоженного значения отступа под системные панели (например, литерального `28.dp`, использованного как заглушка insets в иллюстративном борде `concept-d.svg`) — все insets получены динамически.

## Touch targets

- [ ] Каждый интерактивный элемент экрана ≥ 48 × 48 dp фактической области нажатия (не только визуального размера иконки внутри).
- [ ] Соседние независимые touch targets (например, иконки архива и настроек на Home) не пересекаются, расстояние между центрами ≥ размера самой цели.
- [ ] `MoveButton` не уменьшена относительно 48 × 48 dp ни при каком состоянии карточки (длинное название, 320 dp, 200%).

## TalkBack

- [ ] У каждого интерактивного элемента есть осмысленный `contentDescription`, соответствующий шаблонам `COMPONENTS.md`, и он не включает слово «кнопка»/название роли самостоятельно — например, `contentDescription` кнопки перемещения = «Переместить вверх» (не «Переместить вверх, кнопка» и не «Button»/пусто); итоговая TalkBack-озвучка с ролью — «Переместить вверх, кнопка» — добавляется системой автоматически поверх `contentDescription` для любого компонента с ролью `Button` в этом документе, компонент не дублирует роль в тексте описания сам.
- [ ] Заголовки экранов и секций помечены `semantics { heading() }`.
- [ ] Порядок фокуса TalkBack идёт сверху вниз и заканчивается на основной кнопке экрана (`Проверить`/`Играть`/`Дальше`), как описано в `UX_FLOW.md`, раздел 10.
- [ ] `DailyIssuePanel` озвучивается TalkBack как один составной узел, а не как последовательность из 4+ отдельных фокус-стопов.
- [ ] Полное прохождение дня возможно только средствами TalkBack, без единого жеста перетаскивания (использованы только `MoveButton` и/или custom actions).

## Custom accessibility actions

- [ ] У каждой `OrderableCard` определены все четыре `customActions` в MVP: «Переместить выше», «Переместить ниже», «Переместить в начало», «Переместить в конец» — не как факультативная доработка. У карточки на первой позиции нет «Переместить выше»/«Переместить в начало»; у карточки на последней позиции нет «Переместить ниже»/«Переместить в конец» (действие, не меняющее позицию, не предлагается).
- [ ] После срабатывания custom action или нажатия `MoveButton` вызывается `announceForAccessibility` с текстом вида «{Название} перемещён на позицию N из 4».
- [ ] `liveRegion = Polite` установлен на контейнере списка `OrderableCard`, чтобы перестановки озвучивались без потери фокуса.

## Reduced motion

- [ ] При включённой системной настройке уменьшения анимации все длительности переходов на экране визуально неотличимы от мгновенных (≈1 мс), а не отключены полностью с потерей состояния.
- [ ] Постраничный reveal результатов на `PuzzleResult` при reduced motion показывает все строки одновременно (`motion.stagger.resultReveal` = 0 мс), не «зависает» на первой строке.

## Клавиатура и switch access

- [ ] Каждый интерактивный элемент достижим последовательным нажатием Tab/переключателя (switch access) в том же порядке, что и порядок фокуса TalkBack.
- [ ] Состояние фокуса клавиатуры/switch access визуально видно (`opacity.focusStateLayer`, 12%) и не совпадает визуально с `pressed`-состоянием (различимы по контексту взаимодействия, не обязаны быть разными цветами).

## DayResultRow — единая схема списка

- [ ] Все три `DayResultRow` на `DayRecap` используют **одну** раскладку: либо все три `inline`, либо все три `stacked`. Список, где часть строк в одну строку, а часть в две, — дефект, а не адаптация.
- [ ] Переход в `stacked` выполнен по правилу «хотя бы одна строка не помещается» (`ширина CategoryLabel + spacing.400 + ширина результата > ширина контентной колонки`), а не по признаку конкретной строки.

## Отдельный чек-лист: макет `PuzzleResult`

Второй по риску экран — самый плотный по содержанию (`ARCHITECTURE.md`, раздел 11: «отдельное внимание — экрану результата»).

- [ ] Порядок сверху вниз соответствует иерархии `DESIGN_PRINCIPLES.md` (раздел 3): правильный порядок → объяснение → `ScoreBadge` → `ScoringHint` (только первый в жизни экран) → `InvertedPairRow` → `SourcesBlock` → `ReportInaccuracyAction` → `PrimaryButton`.
- [ ] `ScoringHint` показан только когда `hasSeenScoringHint == false`, установлен без контейнера/иконки/цветной подложки (`bodyMedium`, `onSurfaceVariant`), и после показа `hasSeenScoringHint` выставлен в `true` и подсказка не появляется на последующих `PuzzleResult`.
- [ ] TalkBack-порядок на `PuzzleResult` проходит `ScoringHint` (если показан) сразу после `ScoreBadge` и до `InvertedPairRow` — не до счёта и не после перечня пар.
- [ ] Объяснение (`bodyLarge`) визуально весомее `ScoreBadge` (`headlineSmall`, но не крупнее объяснения по совокупной площади блока) — счёт не самый заметный элемент экрана.
- [ ] Количество строк `InvertedPairRow` в точности равно `6 − score` для этой головоломки (сверка с `PairwiseScoreCalculator.invertedPairs`).
- [ ] Ни одна строка `InvertedPairRow` не содержит слов «выше»/«ниже».
- [ ] При счёте 6 из 6 — только нейтральная строка «Всё верно», без конфетти, свечения или изменения цвета `ScoreBadge`.
- [ ] При счёте 0 из 6 — карточки не подсвечены красным/тревожным цветом, `error`-роль не задействована.
- [ ] `SourcesBlock` свёрнут по умолчанию при первом показе экрана.
- [ ] `SourceRow` реализует ровно три состояния — `link`, `urlPlainText`, `referenceOnly` — не два; наличие `url` само по себе не делает строку кликабельной без проверки `resolveActivity()`.
- [ ] Состояние `link` (есть `url` и найден обработчик `ACTION_VIEW`) кликабельно целиком, открывает браузер, показывает иконку внешнего перехода и объявляется TalkBack как «{Название источника}. Открыть источник в браузере» — с названием, не только шаблонной фразой.
- [ ] Состояние `urlPlainText` (есть `url`, но `resolveActivity() == null`) показывает `url` как обычный читаемый текст — некликабельно, без иконки, без ошибки и без скрытия строки.
- [ ] Состояние `referenceOnly` (`url` отсутствует) показывает обязательный `reference` — некликабельно, без иконки.
- [ ] Во всех трёх состояниях, где у источника есть и `url`, и `reference`, оба показаны — `reference` не скрыт из-за наличия `url`; `accessedAt` показан всегда, у каждого источника без исключений и в любом из трёх состояний.
- [ ] `urlPlainText` и `referenceOnly` не перепутаны между собой — это разные условия (наличие `url` без обработчика vs полное отсутствие `url`), а не два имени одного и того же состояния.
- [ ] Все четыре значения `Source.kind` (`official`, `encyclopedia`, `academic`, `other`) имеют точную русскую подпись из `COMPONENTS.md` → `SourceRow` («Официальный источник», «Энциклопедия», «Научный источник», «Дополнительный источник») — сверено по каждому значению отдельно, не выборочно.
- [ ] Raw-значение enum `kind` нигде не попадает в UI — ни как основной текст, ни как временно видимый отладочный вывод; на экране и в снапшот-тестах присутствует только русская подпись.
- [ ] Значение `kind`, не входящее в перечисленные четыре, обрабатывается как ошибка данных (падение валидации контента/лог ошибки), а не отображается пользователю как произвольный fallback-текст.
- [ ] `ReportInaccuracyAction` («Сообщить о неточности») присутствует, использует `labelSmall`, визуально второстепенно относительно `SourcesBlock` и `PrimaryButton`; отсутствует из дерева компонентов (не показана как `disabled`), если `resolveActivity == null` для `mailto`-интента.
- [ ] Постраничное появление строк (`motion.stagger.resultReveal` = 60 мс) применено только к этому экрану при первом заходе — при возврате на уже просмотренный результат (если такой сценарий появится) контент не переигрывает анимацию заново без необходимости.
- [ ] На 200% — правильный порядок, объяснение и перечень перепутанных пар остаются полностью читаемыми без обязательной горизонтальной прокрутки; вертикальная прокрутка всего экрана допустима и ожидаема на этом экране (в отличие от `Puzzle`, для `PuzzleResult` не зафиксировано требование «без прокрутки»).
- [ ] На 320 dp — сокращённая форма строки `InvertedPairRow» («„Эльбрус" — после „Монблан"») используется вместо полной, если она не помещается; TalkBack получает полную форму независимо от того, какая показана визуально.
