# CONTENT_MODEL.md — «По порядку!»

Модель контента, схема данных, версионирование и редакторский протокол. Статус: утверждено, 2026-08-30.

---

## 1. Принципы

1. **Контент — данные, а не код.** Игровая логика ничего не знает о конкретных головоломках. Добавление 105 новых задач не меняет ни одного класса.
2. **Контент неизменяем после выпуска.** Опубликованная головоломка (`puzzleId`) никогда не редактируется по смыслу. Ошибку исправляют выпуском новой версии контента и отзывом старой головоломки — см. раздел 7.
3. **Одна головоломка — один проверяемый факт.** Порядок должен следовать из значений, которые редактор выписал явно, а не из «общеизвестного».
4. **Значения хранятся, а не только порядок.** У каждой карточки есть `sortValue` — это и есть доказательство правильности, и это же показывается пользователю в результате.
5. **Каждая карточка отвечает за свои источники.** Источник привязан не к головоломке целиком, а к конкретной карточке через `sourceIds`. Иначе «два источника на головоломку» может означать, что три значения из четырёх никем не проверены.
6. **Набор — это порядковый номер, а не дата.** Головоломка самостоятельна; набор её только компонует и получает позицию в последовательности, которую каждый пользователь проходит от начала.

## 2. Структура файлов

Контент лежит в `app/src/main/assets/content/` и поставляется вместе с APK.

```
assets/content/
  manifest.json          # версия контента, состав пакета, контрольные суммы
  puzzles-001.json       # пул головоломок, пакет 001
  daily-sets-001.json    # наборы, пакет 001
```

Разделение пула и наборов даёт:

- возможность переиспользовать головоломку в тематическом паке, не дублируя текст;
- возможность отозвать головоломку, не переписывая все наборы;
- удобную валидацию: наборы ссылаются на `puzzleId`, валидатор проверяет ссылочную целостность.

Альтернатива «один файл на день» отклонена: 35 файлов ради экономии, которой нет — весь контент альфы это ~300 КБ, он читается целиком за один раз при первом запуске и переносится в локальную базу.

**Ровно три файла, шардов нет** (итерация 4, **I4-D5**). Манифест допускает ровно один `puzzles-NNN.json` и ровно один `daily-sets-NNN.json`; любой другой файл или подкаталог в `assets/content/` — ошибка валидации (`M08`). Шардирование потребовало бы порядка объединения, дедупликации идентификаторов между шардами, семантики частичного отказа («шард 2 не прочитался — импортировать первый?») и отдельных диагностик — ради экономии, которой на 300 КБ не возникает.

**Батчи дописывают файлы в конец.** Контент приходит пятью батчами по семь наборов; каждый добавляет 21 объект в массив `puzzles` и 7 объектов в массив `sets`, **ничего не переставляя**. Diff батча аддитивен и читается построчно, а валидатор на каждом батче проверяет пакет как самостоятельный корректный черновик: счётчики манифеста равны фактическим, `setIndex` непрерывен от нуля, кросс-файловые правила выполняются. Требование «35 наборов / 105 головоломок» — не правило валидатора, а критерий релиза, проверяемый явными флагами `--expect-sets` / `--expect-puzzles`.

## 3. `manifest.json`

```json
{
  "schemaVersion": 1,
  "contentVersion": 3,
  "packId": "core-ru",
  "packTitle": "Основной набор",
  "setCount": 35,
  "puzzleCount": 105,
  "files": [
    { "path": "puzzles-001.json", "sha256": "…" },
    { "path": "daily-sets-001.json", "sha256": "…" }
  ]
}
```

| Поле | Назначение |
| --- | --- |
| `schemaVersion` | Версия **формата**. Меняется только при несовместимых изменениях структуры |
| `contentVersion` | Версия **данных**. Растёт при каждом выпуске нового контента |
| `packId` | Идентификатор пакета. `core-ru` — основной; тематические паки получат свои |
| `setCount` | Число наборов в пакете |
| `puzzleCount` | Число головоломок в пуле пакета |
| `files` | **Ровно два** элемента: один с префиксом `puzzles-`, один с `daily-sets-`, пути различны |
| `sha256` | Проверяется в отладочной сборке и в CI, не в релизе (лишний расход батареи) |

### Требования к манифесту (итерация 4)

| Требование | Код нарушения | Почему |
| --- | --- | --- |
| `schemaVersion` не больше `SUPPORTED_SCHEMA_VERSION` | `M01` | Пакет более нового формата приложение прочитать не может и не должно пытаться |
| `packId` совпадает во всех трёх файлах **и** с активным пакетом приложения (`ContentPack.CORE_RU`) | `M02` | Две независимые проверки, обе в CI. Сверка файлов между собой — единственная защита от «собрали пакет из двух половин разных паков»: ссылочная целостность такую ошибку не ловит, если идентификаторы случайно совпали. Сверка с активным пакетом ловит самосогласованный пакет с чужим `packId`: он не импортируется приложением ни при каких условиях, потому что все запросы импортёра pack-scoped |
| `files[].path` целиком совпадает с `^(puzzles\|daily-sets)-[0-9]{3}\.json$` | `M03` | Это **не путь, а имя из закрытого множества** (**I4-D6**). Шаблон по построению отсекает `..`, `/`, `\`, `~`, абсолютный путь, подкаталог, `manifest.json`, другое расширение и другой регистр. Allow-list выбран вместо санитайзера сознательно: у него не бывает обходов. Физический путь строится только как `content/` + проверенное имя |
| Ровно два элемента `files`, по одному каждого типа, пути различны | `M03` | Шардов нет (§2) |
| Объявленный файл существует | `M04` | — |
| Файл разбирается как JSON | `M05` | — |
| `sha256` — **64 строчных hex-символа** от **точных байтов** файла | `M06` | Верхний регистр — тоже несовпадение: сравнение точное |
| `schemaVersion` совпадает между манифестом и обоими файлами | `M07` | — |
| В каталоге нет необъявленных файлов и подкаталогов | `M08` | — |
| **UTF-8 без BOM**, файл заканчивается **ровно одним** `\n` | `M09` | BOM ломает разбор и меняет хеш, а редакторы Windows добавляют его молча. Фиксированная нормализация нужна потому, что `--sync-manifest` переписывает манифест: без неё хеши прыгали бы от смены редактора |
| `setCount` / `puzzleCount` совпадают с фактическими | `R21` | — |
| Фактический объём совпал с `--expect-sets` / `--expect-puzzles` | `M10` | Критерий **релиза**, а не формата: батчи 4C-1…4C-4 законно меньше 35/105 |

Отступ файлов — 2 пробела, кириллица хранится как есть (`ensure_ascii = false`), а не `\uXXXX`: без этого diff батча нечитаем.

**Начальная настоящая `contentVersion` — `1`.** Значение `3` в примере выше — иллюстрация формата, а не стартовая версия пакета; все пять контентных батчей идут с `contentVersion: 1`, потому что батчи — черновик одного ещё не выпущенного пакета, а не пять выпусков.

Производные значения манифеста поддерживаются не руками:

```bash
python3 tools/validate-content/validate.py app/src/main/assets/content --sync-manifest
```

Режим пересчитывает **только** `sha256`, `setCount` и `puzzleCount`, печатает каждое изменение и не трогает ни `contentVersion`, ни `schemaVersion`, ни `packId`, ни имена файлов, ни содержимое контентных файлов. Запуск после любой правки контента обязателен: иначе приложение не увидит изменений, а CI не пропустит PR.

### Чего в манифесте больше нет

Поле `contentStartDate` **удалено**. В MVP наборы не привязаны к календарю: каждый пользователь проходит их последовательно от первого, с какой бы даты ни начал (см. `UX_FLOW.md`, раздел 9). Дата первого набора не существует как понятие.

Следствие для контента: **порядок наборов в пакете — это порядок, в котором их увидит каждый пользователь**, а не расписание. Первые наборы должны быть самыми выверенными и самыми доступными, потому что через них пройдут все, включая тех, кто удалит приложение на третий день.

Глобальный общий набор дня (challenge of the day) вынесен за пределы MVP. Если он появится, ему понадобится отдельное поле привязки и, вероятно, backend — но текущая схема этого не предвосхищает и не платит за это сложностью.

### Объём пакета

105 головоломок (35 наборов) — объём **для альфы**. Публичный релиз требует не менее 60 наборов (180 головоломок) либо полностью готового следующего пакета: при последовательной выдаче все пользователи упираются в конец контента одинаково, ровно на 36-й активный день. Обоснование — в `PRODUCT.md`, раздел «Объём контента».

## 4. Схема головоломки

### JSON Schema (сокращённо)

Полные схемы — **`tools/validate-content/schema/*.schema.json`**: три строгих файла Draft 2020-12 (`manifest.schema.json`, `puzzles.schema.json`, `daily-sets.schema.json`), а не один `tools/content-schema.json`, как планировалось до итерации 4 (**I4-D8**). Схемы лежат внутри инструмента, который их исполняет.

**Конверт файла головоломок** задаётся симметрично файлу наборов (**I4-D5**):

```json
{ "schemaVersion": 1, "packId": "core-ru", "puzzles": [ /* объекты ниже */ ] }
```

Сокращённая схема ниже приведена для чтения; она **слабее** исполняемой, и все расхождения — в сторону строгости:

| В исполняемой схеме | Почему |
| --- | --- |
| `retiredIn` в `required`, тип `["integer","null"]` | Отсутствие поля и явный `null` — разные вещи только для человека; обязательность снимает вопрос «забыли или отозвали» |
| `uniqueItems: true` у `correctOrder` и `sourceIds` | Дубликат `cardId` в порядке — не «правило», а бессмыслица: отсекается схемой, а не семантикой |
| `anyOf`: у источника обязателен `url` **или** `reference` | Правило 17 выражается схемой полностью, без семантического дублёра |
| `pattern: "^https://"` у `url` | `http://` в источнике 2026 года — сигнал небрежности; `format: uri` без этого пропускает `ftp://` и `javascript:` |
| Верхние границы `maxItems`/`maxLength` везде: `sources` — 1–12, `sourceIds` — 1–8, `title`, `note`, `puzzleId` (48) | Неограниченное поле — это неограниченный размер APK и неограниченная строка на экране |
| `minLength` у необязательных строк (`subtitle`, `note`) | Пустая строка вместо отсутствия поля — самая частая ошибка ручного авторинга |
| `sets[].puzzleIds` — ровно три уникальных; `setIndex ≥ 0`; `files` — ровно два уникальных элемента | Форма, а не правило |
| `additionalProperties: false` на **каждом** объекте, включая карточку, источник, элемент `files` и элемент `sets` | В момент авторинга неизвестный ключ — всегда опечатка. `sourceId` вместо `sourceIds`, `subtitile` молча теряются при терпимом разборе |

**Даты проверяются тремя слоями,** потому что в Draft 2020-12 `format` по умолчанию — аннотация, а не утверждение: `pattern` задаёт форму, `FormatChecker` включается явно, а календарная корректность (`R04A`) и «не в будущем» (`R04B`) проверяются семантически. `pattern` пропускает `2026-13-45`, а зависеть от того, что реализация включила `format`, — значит зависеть от настройки, которую легко потерять.

Схема **разрешает** всё, что запрещено политикой: пять отложенных `sortKey` остаются в `enum`, `volatility: "volatile"` — тоже. Их запрет — семантические правила `R08C` и `R09`, а не удаление из формата: формат не меняется, когда меняется политика пака.

```jsonc
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://poporyadku.app/schema/puzzle/v1",
  "type": "object",
  "required": [
    "puzzleId", "category", "prompt", "sortKey", "sortDirection",
    "directionLabel", "cards", "correctOrder", "explanation", "sources",
    "volatility", "difficulty", "verifiedAt", "verifiedBy"
  ],
  "additionalProperties": false,
  "properties": {
    "puzzleId":       { "type": "string", "pattern": "^[a-z0-9]+-[a-z0-9-]+-\\d{3}$" },
    "category":       { "enum": ["history","geography","science","nature","culture","russia","mixed"] },
    "prompt":         { "type": "string", "minLength": 10, "maxLength": 90 },
    "sortKey":        { "enum": ["year","date","height","depth","length","area","population","distance","latitude","longitude","temperature","mass","speed","duration"] },
    "sortDirection":  { "enum": ["ascending","descending"] },
    "directionLabel": { "type": "string", "maxLength": 40 },

    "cards": {
      "type": "array", "minItems": 4, "maxItems": 4,
      "items": {
        "type": "object",
        "required": ["cardId","title","sortValue","displayValue","sourceIds"],
        "additionalProperties": false,
        "properties": {
          "cardId":       { "type": "string", "pattern": "^c[1-4]$" },
          "title":        { "type": "string", "minLength": 1, "maxLength": 40 },
          "subtitle":     { "type": "string", "maxLength": 50 },
          "sortValue":    { "type": "number" },
          "displayValue": { "type": "string", "maxLength": 30 },
          "note":         { "type": "string", "maxLength": 80 },
          "sourceIds":    { "type": "array", "minItems": 1, "items": { "type": "string" } },
          "disputed":     { "type": "boolean", "default": false }
        }
      }
    },

    "correctOrder": {
      "type": "array", "minItems": 4, "maxItems": 4,
      "items": { "type": "string", "pattern": "^c[1-4]$" }
    },

    "explanation":  { "type": "string", "minLength": 40, "maxLength": 320 },

    "sources": {
      "type": "array", "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sourceId","title","kind","accessedAt"],
        "additionalProperties": false,
        "properties": {
          "sourceId":   { "type": "string", "pattern": "^s\\d{1,2}$" },
          "title":      { "type": "string" },
          "kind":       { "enum": ["official","encyclopedia","academic","other"] },
          "url":        { "type": "string", "format": "uri" },
          "reference":  { "type": "string" },
          "accessedAt": { "type": "string", "format": "date" },
          "note":       { "type": "string" }
        }
      }
    },

    "volatility":  { "enum": ["stable","slow","volatile"] },
    "difficulty":  { "type": "integer", "minimum": 1, "maximum": 3 },
    "verifiedAt":  { "type": "string", "format": "date" },
    "verifiedBy":  { "type": "string" },
    "retiredIn":   { "type": ["integer","null"] }
  }
}
```

### Пояснения к ключевым полям

**`correctOrder` обязателен и при этом избыточен — это сделано намеренно.** Правильный порядок вычисляется из `sortValue` + `sortDirection`, но обязан храниться явно. Валидатор в CI сверяет вычисленный порядок с записанным: расхождение = ошибка сборки. Так опечатка в значении ловится автоматически, а не пользователем. Поле переведено в `required` именно потому, что необязательность лишала бы эту проверку смысла: головоломку без `correctOrder` было бы не с чем сверять.

**`sourceIds` у каждой карточки** — привязка проверки к конкретному значению. `sources` на уровне головоломки — это пул, а `sourceIds` — то, чем проверена именно эта карточка. Валидатор проверяет покрытие каждой карточки (правила в разделе 8).

**`kind` источника** задаёт авторитетность:

| `kind` | Что это | Годится как единственный источник карточки |
| --- | --- | --- |
| `official` | Официальный сайт организации, госоргана, музея, космического агентства | Да |
| `encyclopedia` | БРЭ, Britannica и подобные редактируемые профессионально справочники | Да |
| `academic` | Научная публикация, монография, справочник с выходными данными | Да |
| `other` | Википедия, СМИ, отраслевые сайты, блоги | **Нет.** Только как дополнительный |

**`url` необязателен, но нужен либо `url`, либо `reference`.** Печатный справочник — полноценный источник, и требовать для него ссылку значило бы выталкивать редактора к менее качественным, но «ссылочным» источникам. `reference` — библиографическое описание с выходными данными.

**`disputed`** у карточки — редакторская отметка «значение спорное или варьируется между источниками». Включает требование второго источника.

**`sortValue` — всегда число**, приведённое к одной единице внутри одной головоломки (все метры, или все годы). Единица в JSON не хранится: она уже отражена в `displayValue`, который показывается пользователю («8848 м», «1961 год»). Смешивать единицы внутри головоломки запрещено.

### `sortKey` → единица `sortValue` → правило разрыва (I4-D24)

Без этой таблицы правило 8 неисполнимо: «≥ 3 %» не определено, пока не сказано, в чём измеряется значение, а для интервальной шкалы относительный порог бессмыслен вовсе.

| `sortKey` | Единица `sortValue` | Правило разрыва | Статус в паке v1 |
| --- | --- | --- | --- |
| `year` | год; до н. э. — отрицательное число, нуля не существует | \|a − b\| ≥ 2 | **разрешён** |
| `height`, `depth`, `length`, `distance` | метры | \|a − b\| ≥ 0,03 · max(\|a\|, \|b\|) | **разрешён** |
| `area` | квадратные километры | то же, относительное | **разрешён** |
| `mass` | килограммы | то же, относительное | **разрешён** |
| `speed` | километры в час | то же, относительное | **разрешён** |
| `duration` | секунды | то же, относительное | **разрешён** |
| `population` | — | — | **запрещён**: по природе `volatile` (правило 9 и §9) |
| `temperature` | — | — | **запрещён в v1**: интервальная шкала, относительный порог неприменим, абсолютный не задан |
| `date` | — | — | **запрещён в v1**: единица не зафиксирована — день эпохи или год |
| `latitude`, `longitude` | — | — | **запрещён в v1**: относительный порог вырождается около экватора и нулевого меридиана |

Запрет реализован кодом `R08C`. Отложенных ключей **пять**; разрешение любого из них — отдельное решение с дописанной строкой в эту таблицу, формат при этом не меняется. Дополнительно: на всех разрешённых ратио-шкалах требуется `sortValue > 0` (`R08D`), а при `sortKey: "year"` запрещено значение `0` (`R08E`) — нулевого года не существует.

Граница включающая: ровно 2 года и ровно 3,00 % **проходят**, один год и 2,99 % — нет. Проверяются соседние значения после сортировки.

**Что остаётся человеку.** Машина знает 2 года и 3 %; она не знает погрешности измерения. Соответствие разрыва реальной погрешности источников — пункт `CONTENT_REVIEW_CHECKLIST.md`, а не правило валидатора.

**Годы до нашей эры** — отрицательные числа (`-776`), `displayValue` — «776 до н. э.».

**`displayValue`** — то, что видит пользователь в результате. Это делает экран результата обучающим, а не просто «правильно/неправильно».

**`directionLabel`** — готовая русская строка для игрового экрана («Сверху — самое раннее»). Не собирается из `sortKey` + `sortDirection` в коде: русский язык слишком неудобен для машинной сборки таких фраз, а строк всего ~14.

**`volatility`:**

| Значение | Смысл | Правило |
| --- | --- | --- |
| `stable` | Значение не изменится (год события, дата основания, широта города) | Один авторитетный источник на карточку |
| `slow` | Меняется медленно или уточняется измерениями (высота горы, площадь озера) | **Два источника на каждую карточку**, разрыв заведомо больше возможного изменения |
| `volatile` | Меняется быстро (население, рекорды, курсы, «самый высокий небоскрёб») | **Запрещено в MVP.** Значение оставлено в схеме для будущих паков с датированной привязкой |

**`difficulty` 1–3** — редакторская оценка, используется при компоновке наборов, пользователю не показывается.

**`retiredIn`** — номер `contentVersion`, начиная с которого головоломка не должна использоваться (см. раздел 7).

## 6. Наборы

```json
{
  "schemaVersion": 1,
  "packId": "core-ru",
  "sets": [
    {
      "setIndex": 0,
      "puzzleIds": ["hist-izobreteniya-012", "geo-vysota-gor-007", "sci-otkrytiya-031"]
    },
    {
      "setIndex": 1,
      "puzzleIds": ["nat-zhivotnye-004", "cult-kino-019", "rus-goroda-002"]
    }
  ]
}
```

- `setIndex` — **порядковый номер набора в пакете**, а не смещение от какой-либо даты. Поле переименовано из `dayIndex` вместе с переходом на последовательную выдачу: прежнее имя подразумевало календарь, которого больше нет.
- `setIndex` уникален и непрерывен от 0 до `setCount - 1`. Дыра = ошибка валидации.
- Каждая головоломка используется не более одного раза внутри пакета.

### Правила компоновки набора

- Три разные категории в одном наборе (исключение: `mixed` может соседствовать с любой) — код `R20A`.
- Сложность внутри набора по возрастанию: `difficulty` 1 → 2 → 2, или 1 → 2 → 3. Первое задание никогда не самое сложное — код `R20B`.
- Одна и та же категория не открывает два набора подряд — код `R20C`.
- В первых семи наборах — только `difficulty` 1 и 2 — код `R20D`.

Формализация правил в предикаты (**I4-D25**) ничего к ним не добавляет и ничего не ослабляет — она только раздаёт коды:

| Подправило | Предикат | Код |
| --- | --- | --- |
| Три **попарно различные** категории | `c₀ ≠ c₁ ∧ c₁ ≠ c₂ ∧ c₀ ≠ c₂` | `R20A` |
| Профиль сложности — один из двух | `(d₀,d₁,d₂) ∈ { (1,2,2), (1,2,3) }` | `R20B` |
| Категория не открывает два набора подряд | `category(set[i].slot0) ≠ category(set[i−1].slot0)` | `R20C` |
| В наборах `setIndex 0…6` нет `difficulty = 3` | `setIndex ≤ 6 ⇒ max(d) ≤ 2` | `R20D` |

**Профили — перечень из двух, а не неравенства.** Допустимы ровно `[1,2,2]` и `[1,2,3]`; `[1,1,2]`, `[2,2,3]`, `[2,2,2]`, `[1,3,3]`, `[2,1,3]`, `[3,1,2]` и любые другие запрещены. Вывод через неравенства (`d₀ ≤ d₁ ≤ d₂ ∧ d₀ < d₂`) пропустил бы `[1,1,2]` и `[2,2,3]`, то есть **расширил** бы это правило, а не выразил его.

`R20B` и `R20D` вместе оставляют в первых семи наборах ровно **один** профиль — `[1,2,2]`: второй содержит `difficulty 3`, запрещённую до восьмого набора. Это самое узкое место контракта, и оно намеренно узкое: через первые семь наборов проходит каждый пользователь.

**`mixed` не является исключением ни в `R20A`, ни в `R20C`.** «Три разные категории» — это три различных значения поля `category`, а `mixed` — такое же значение, как `history`. Он совместим с любой парой других **различных** категорий (`mixed + history + science` допустимо), но не разрешает ни второй `mixed` в наборе (`mixed + mixed + science` — нарушение `R20A`), ни повтор другой категории рядом с собой (`mixed + history + history` — тоже `R20A`), ни право открывать два соседних набора (`R20C` сравнивает значения). Формулировка «`mixed` может соседствовать с любой» означает совместимость по темам, а не разрешение на дубликат: набор из двух `mixed` не имеет трёх категорий ни в каком прочтении.

`R20C` проверяется **сквозь границы батчей**: валидатор всегда видит файл целиком, поэтому набор 7 сверяется с набором 6 из предыдущего батча автоматически.

Последнее правило теперь важнее, чем при календарной привязке: через первые наборы проходит **каждый** пользователь, а не только те, кто установил приложение в первую неделю. Первые семь наборов — это фактически витрина продукта, и калибровать их надо тщательнее остальных.

## 7. Версионирование и миграции

### Две независимые оси

| Ось | Что означает | Кто реагирует |
| --- | --- | --- |
| `schemaVersion` | Формат данных | Код приложения |
| `contentVersion` | Наполнение | Загрузчик контента |

### Правила изменения `schemaVersion`

Увеличивается **только** при несовместимом изменении: удаление обязательного поля, изменение типа, изменение смысла существующего поля. Добавление нового необязательного поля `schemaVersion` не меняет.

Приложение хранит константу `SUPPORTED_SCHEMA_VERSION`. Если `manifest.schemaVersion` больше поддерживаемой — приложение отказывается импортировать контент и показывает `Home.Error` с текстом «Требуется обновление приложения». Это невозможно в MVP (контент внутри APK), но правило нужно сразу: тематические паки в будущем могут доставляться отдельно.

### Правила изменения `contentVersion`

Растёт при каждом релизе с новым или исправленным контентом. При старте приложение сравнивает `manifest.contentVersion` с сохранённым в `UserPreferences`:

```
если storedContentVersion == manifest.contentVersion  → ничего не делать
если storedContentVersion <  manifest.contentVersion  → импортировать (upsert)
если storedContentVersion >  manifest.contentVersion  → откат приложения; переимпортировать полностью
```

### Что делает импорт

1. Разбирает `puzzles-*.json` и `daily-sets-*.json`.
2. `upsert` головоломок по `puzzleId` — новые добавляются, существующие перезаписываются.
3. `upsert` наборов по `(packId, setIndex)`.
4. Обновляет `storedContentVersion`.
5. **Никогда не трогает таблицы прогресса и назначений.** Прогресс и контент разделены полностью.

### Что происходит с прогрессом при изменении контента

Прогресс ссылается на `puzzleId` и на дату — не на текст головоломки. Поэтому:

- исправление опечатки в `explanation` → архив просто начинает показывать исправленный текст, это корректно;
- **отзыв головоломки** (обнаружена ошибка в фактах): в новом релизе у неё выставляется `retiredIn: <contentVersion>`, а в наборах она заменяется на другую. Уже сыгранный день у пользователя не переписывается: попытка привязана к `puzzleId`, запись остаётся, но экран результата для отозванной головоломки показывает строку «Задание отозвано: в нём была неточность». Честнее, чем тихо подменить факт;
- удалять головоломки из `puzzles-*.json` нельзя никогда — иначе архив пользователей ломается ссылочной целостностью. Только `retiredIn`.

### Правило неизменности состава набора (усилено)

**Состав уже выпущенного `setIndex` не меняется никогда.** Новые наборы только добавляются в конец последовательности.

При календарной привязке правка была допустима для будущих дат: было точно известно, что этот день ещё никто не видел. С последовательной выдачей такой гарантии больше нет — пользователи находятся в разных точках последовательности, и `setIndex 12` для кого-то будущее, а для кого-то прошлое. Определить это без backend невозможно, поэтому правило становится безусловным.

Единственное исключение — замена отозванной головоломки: она вынужденная, и её последствия видны пользователю явной пометкой «задание отозвано», а не тихой подменой.

### Тематические паки (задел, не MVP)

Пак — тот же набор файлов с другим `packId` и собственной последовательностью. Схема готова к этому: `packId` уже присутствует в манифесте и в ключе набора. Игровая логика получает набор через `DailySetRepository.getSet(packId, setIndex)` и не меняется. Правило «один активный пак на пользователя» фиксируется сейчас, чтобы не проектировать смешение позже.

## 8. Редакторский протокол

Обязателен для каждой головоломки до попадания в пакет.

### Шаг 1 — Отбор признака

Признак допустим, если он:

- числовой или сводится к числу (год, метры, километры, широта);
- имеет **общепринятое** значение, а не оценочное;
- не зависит от определения («самый большой город» — по населению или по площади? — такая формулировка запрещена, нужна явная).

Запрещённые признаки в MVP: субъективные (популярность, известность, красота), спорные (приоритет открытия, авторство), политически чувствительные (границы, принадлежность территорий), быстро меняющиеся (`volatile`).

### Шаг 2 — Подбор источников для каждой карточки

Источники подбираются **на каждую карточку отдельно**, а не на головоломку целиком.

- **Минимум один авторитетный источник на карточку**: `kind` = `official`, `encyclopedia` или `academic`. Википедия (`other`) авторитетным источником не считается и может быть только дополнением — её роль в том, чтобы привести редактора к первоисточнику.
- **Второй источник обязателен**, если головоломка имеет `volatility: "slow"` или карточка помечена `disputed: true`. Второй источник должен быть **независимым**: не зеркало, не перевод и не пересказ первого.
- Записать `accessedAt` для каждого источника и фактически открыть каждую ссылку.
- Если источники расходятся в значении — карточка помечается `disputed`, и решение принимается в пользу более авторитетного, с `note`, объясняющей расхождение. Если расхождение достаточно велико, чтобы изменить порядок, головоломка отклоняется целиком.

### Шаг 3 — Проверка однозначности (главная)

Правило минимального разрыва:

| `volatility` | Требование к разрыву между соседними `sortValue` |
| --- | --- |
| `stable` (годы, даты) | ≥ 2 года; для событий одного года — запрещено |
| `slow` (физические величины) | ≥ 3% от большего из пары **и** ≥ типичной погрешности источников |
| `volatile` | Запрещено |

Дополнительно:

- ни одной пары с равными `sortValue`;
- разрывы не обязаны быть равномерными, но самый маленький разрыв определяет допустимость всей головоломки;
- формулировка не должна допускать второго прочтения: тест — «может ли грамотный человек обосновать другой порядок?». Если да — переформулировать или отклонить.

Замечание про парный подсчёт баллов: он делает цену одной неоднозначной пары ниже (пользователь теряет 1 балл из 6, а не сбивает все позиции), но **не смягчает требований**. Неоднозначность разрушает доверие независимо от того, во сколько баллов она обходится.

### Шаг 4 — Формулировка и объяснение

- `prompt` — до 90 символов, повелительное наклонение, без «попробуйте угадать».
- `explanation` — 40–320 символов, объясняет **почему**, а не пересказывает порядок. Плохо: «Первым идёт Монблан, вторым Эльбрус». Хорошо: «Монблан — высшая точка Альп, но уступает Эльбрусу».
- Нейтральный тон, без восклицаний, без обращения «вы не знали?».
- Проверка орфографии и типографики: тире (—), неразрывные пробелы в числах с единицами, «ё» пишется.

### Шаг 5 — Фиксация

Заполнить `verifiedAt`, `verifiedBy`. Головоломка без этих полей не проходит валидацию.

### Шаг 6 — Автоматическая валидация

Инструмент `tools/validate-content` запускается **в CI на каждый push** и вручную автором контента. Каждое правило имеет стабильный код: он одинаков в CI и в приложении, и именно он — контракт, а не текст сообщения.

```bash
python3 tools/validate-content/validate.py app/src/main/assets/content
```

Коды выхода: `0` — нарушений нет, `1` — пакет прочитан и найдены нарушения, `2` — инструмент не смог выполнить проверку (каталога нет, нет прав, повреждена схема). Разделение `1` и `2` обязательно: без него «контент плохой» и «валидатор сломан» выглядят в CI одинаково, и второе чинят как первое.

**Структура**

| № | Правило | Код |
| --- | --- | --- |
| 1 | JSON не соответствует схеме | `R01_SCHEMA` |
| 2 | Отсутствует `correctOrder` (поле обязательное) | `R02_CORRECT_ORDER_MISSING` |

### Где какая проверка выполняется

| Проверка | CI | debug | release |
| --- | --- | --- | --- |
| Имена файлов, шаблон `path`, отсутствие путей (`M03`) | да | да | **да** |
| Разбор JSON, конверты, `schemaVersion`, `packId` (`M01`, `M02`, `M04`, `M05`, `M07`, `R01`) | да | да | **да** |
| Защитные инварианты перед записью в Room (`R05`, `R18`–`R18C`, `R19`, `R21` и форма головоломки) | да | да | **да** |
| `sha256` файлов (`M06`), лишний файл (`M08`), кодировка (`M09`) | да | да | нет |
| Все 21 правило: порядок, разрывы, источники, компоновка | **да** | нет | нет |

**Валидация в приложении выполняется на пути импорта, а не при каждом старте** (**I4-D30**). Прежняя формулировка «валидация обязательна и в CI, и в отладочной сборке при старте» неисполнима: подтверждение установленного контента выполняется на каждом пересчёте Home, и полная валидация означала бы разбор 300 КБ при каждом вызове. Полные 21 правило остаются за CI — они работают до мержа, и нарушение любого из них делает контент неверным, но не ломает приложение. В рантайме остаётся защитный набор: то, нарушение чего испортило бы базу пользователя.

Приложение отвечает на вопрос «что не так» грубее, чем CI, и это зафиксировано, а не случайно: у CI есть JSON Schema, которая видит документ целиком и называет конкретное нарушенное ограничение, а у приложения — сериализация, которая либо строит объект, либо нет. Поэтому корректный JSON, из которого не строится DTO (нет обязательного поля, неверный тип), в рантайме всегда `R01`, тогда как CI назовёт точный код `R02`, `R03`, `R04`, `R11` или `R17`. **`R02` и `R11` — специализированные коды CI**: в рантайме отказ приходит раньше и уже назван `R01`. Воспроизводить точность схемы в приложении значило бы написать вторую JSON Schema руками — и разойтись с настоящей при первой же правке формата.

### Четыре вида проверки, которые нельзя смешивать

Смешение этих четырёх — главный способ выдать «валидатор зелёный» за «контент проверен».

| Область | Кто проверяет | Артефакт | Почему автомат бессилен |
| --- | --- | --- | --- |
| **Формальная корректность** — схема, ссылки, порядок, разрывы, покрытие источниками, компоновка | валидатор в CI | код выхода и диагностики | — |
| **Достоверность источника** — ссылка открывается, страница существует, издание существует, `kind` соответствует характеру издания | человек | пункт чек-листа с датой и подписью `verifiedBy` | Схема не отличает настоящий URL от правдоподобного; сетевой доступ из CI проверял бы доступность, а не факт |
| **Корректность утверждения** — на странице действительно указано это значение; значение соответствует признаку и единице; разрыв больше реальной погрешности | человек | заполненная строка чек-листа на каждую карточку | Требует чтения источника и понимания предметной области |
| **Редакционная приёмка** — формулировка однозначна, объяснение объясняет «почему», тон нейтральный, типографика | человек | подписанный чек-лист батча `docs/content-reviews/4C-N.md` | Это суждение, а не проверка |

**Правило приёмки батча: зелёный валидатор — необходимое условие мержа, но не достаточное.** Достаточным его делает заполненный и подписанный `docs/CONTENT_REVIEW_CHECKLIST.md`.

Чего валидатор принципиально **не** может: проверить, что ссылка ведёт на существующую страницу, что страница содержит указанное значение и что источник не выдуман. Это остаётся на человеке, и никакая автоматика этого не заменит.

### Шаг 7 — Ручная приёмка набора

Перед релизом пакета: пройти все наборы самому, засекая, где возникает сомнение. Каждое сомнение — повод пересмотреть головоломку, даже если она формально прошла валидацию. Первым семи наборам — отдельный проход, потому что через них пройдут все.

## 9. Защита от устаревания после релиза

- **Проектная защита.** Запрет `volatile` и правило минимального разрыва — основная линия обороны. Головоломка про высоту Эльбруса не устареет; головоломка про население Новосибирска устареет за год, поэтому её нельзя.
- **Датирование.** Если признак меняется, но нужен — формулировка обязана содержать дату: «Расположите по населению на 2021 год». В MVP таких головоломок не делаем.
- **Ревизия.** Раз в релиз проверяются головоломки с `volatility: "slow"` и все карточки с `disputed: true` старше двух лет по `verifiedAt`: значения сверяются заново, `verifiedAt` обновляется.
- **Отзыв.** Обнаруженная ошибка → `retiredIn` в ближайшем релизе + замена в наборах. Приложение показывает пользователю честную пометку вместо тихой подмены.
- **Обратная связь — действие «Сообщить о неточности».** Решено включить в MVP. На экране результата и в настройках есть `mailto`-действие, открывающее почтовый клиент с предзаполненными `puzzleId`, версией приложения и версией контента; текст письма пользователь видит целиком и отправляет сам. Сети приложению по-прежнему не требуется, и никакие данные никуда не уходят автоматически — обещание «ничего не собираем» не нарушено. Для редактора это главный источник раннего обнаружения ошибок: письмо с `puzzleId` приходит адресно, в отличие от отзыва «где-то была ошибка» в магазине.

## 10. Локальное представление контента

Импортированный контент хранится в таблицах, описанных в `ARCHITECTURE.md`:

- `puzzles` — плоские поля + `cards` и `sources` как JSON-строки (они читаются только целиком, отдельные запросы по ним не нужны);
- `daily_sets` — `(pack_id, set_index)` → три `puzzleId`.

Прогресс и назначения лежат отдельно и на контент внешними ключами не ссылаются:

- `day_assignments` — `local_date → set_index`, кто какой набор получил и когда;
- `puzzle_attempts`, `day_results` — что и с каким результатом сыграно.

Именно это разделение позволяет переимпортировать контент, не касаясь истории пользователя, и переживать отзыв головоломки.

Причина, по которой контент вообще переносится в базу, а не читается из assets на лету: единый источник для join с прогрессом (архив за 200 дней — один запрос вместо 200 разборов JSON) и предсказуемая работа при росте пакета до 60+ наборов. Разбор сотни головоломок при первом запуске занимает единицы десятков миллисекунд и делается один раз на версию контента.
