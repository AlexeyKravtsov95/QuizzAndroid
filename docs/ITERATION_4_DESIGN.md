Документ проектирует пять вещей и ничего больше:

1. формат настоящего контентного пакета в `app/src/main/assets/content/`;
2. валидацию этого пакета — в CI и в приложении, с доказанной эквивалентностью на общих фикстурах;
3. чтение, разбор и **атомарный** импорт пакета в Room;
4. безопасный переход с временной фикстуры итерации 3 на настоящий пакет;
5. удаление `data/content/temporary` без «висящих» ссылок.

Кода в этой ревизии нет: все листинги — проект, а не реализация.

## 2. Room: почему миграции нет

### I4-D1. Версия схемы остаётся 1; пустая миграция 1→2 запрещена

Экспортированная схема `app/schemas/ru.poporyadku.data.db.AppDatabase/1.json` (identityHash `3fa608dc84948b21be3f2dc251759862`) уже содержит:

```sql
CREATE TABLE puzzles (
  puzzle_id TEXT NOT NULL, pack_id TEXT NOT NULL, category TEXT NOT NULL,
  prompt TEXT NOT NULL, sort_key TEXT NOT NULL, sort_direction TEXT NOT NULL,
  direction_label TEXT NOT NULL, cards_json TEXT NOT NULL, correct_order TEXT NOT NULL,
  explanation TEXT NOT NULL, sources_json TEXT NOT NULL, difficulty INTEGER NOT NULL,
  retired_in INTEGER, content_version INTEGER NOT NULL, PRIMARY KEY(puzzle_id));
CREATE TABLE daily_sets (
  pack_id TEXT NOT NULL, set_index INTEGER NOT NULL,
  puzzle_id_1 TEXT NOT NULL, puzzle_id_2 TEXT NOT NULL, puzzle_id_3 TEXT NOT NULL,
  PRIMARY KEY(pack_id, set_index));
```

Импорту настоящего пакета этого достаточно: каждое поле формата имеет либо колонку, либо осознанное место в JSON-полях, либо осознанное отсутствие (**I4-D16**). Ни одной новой колонки, ни одного нового индекса, ни одной новой таблицы итерация 4 не требует.

**Следствия, фиксируемые как правила:**

1. `AppDatabase.version` остаётся `1`; файл `app/schemas/…/1.json` не меняется, второй файл схемы не появляется. Проверка: `git diff --stat main -- app/schemas` пуст после каждого PR итерации 4.
2. **`contentVersion` — не версия Room.** Это версия *данных пакета*; она живёт в `manifest.json`, в колонке `puzzles.content_version` и в DataStore. Room о ней не знает и знать не должен: рост `contentVersion` не меняет ни одной DDL-инструкции.
3. **Пустая миграция 1→2 «чтобы завести `MigrationTestHelper`» запрещена.** Миграция, ничего не меняющая, — это подпись под утверждением «схема изменилась», которое ложно; она навсегда закрепляет фиктивную точку в истории схемы и требует поддерживать тест, ничего не проверяющий.
4. `androidx.room:room-testing` **не подключается** (продолжение **D-22** итерации 2). Единственный нужный проекту API этого артефакта — `MigrationTestHelper`; он появляется вместе с первым реальным изменением схемы, а не «за компанию» с итерацией 4. Строка `IMPLEMENTATION_PLAN.md` («подключить `room-testing` вместе с первой настоящей миграцией») остаётся верной по существу и неверной по адресу — она относится не к итерации 4; помечается для синхронизации (раздел 19).
5. Migration-тест включается в тестовую матрицу **только** при реальном изменении схемы. В матрице раздела 17 его нет.

### Что было бы изменением схемы — и почему мы этого не делаем

| Соблазн | Зачем мог бы понадобиться | Почему отклонён |
| --- | --- | --- |
| Индекс `puzzles(pack_id, content_version)` | Ускорить подтверждение «все головоломки текущей версии на месте» | Подтверждение выполняется 105 точечными lookup-ами по PK `puzzle_id` (раздел 10.3), а не сканом по `pack_id`. Индекс дал бы микросекунды и стоил бы миграции |
| Колонки `volatility`, `verified_at`, `verified_by` | «Пусть в базе будет всё, что в JSON» | Ни один экран их не показывает; редакторский протокол проверяется в CI до сборки. Хранить непотребляемые данные — платить миграцией за отсутствие пользы (**I4-D16**) |
| FK `daily_sets → puzzles` | Ссылочная целостность | Прямо отклонено **D-11** итерации 2: `retiredIn` требует, чтобы отозванная головоломка оставалась в таблице, а целостность проверяет валидатор в CI |
| Отдельная таблица `content_packs` (версия, отпечаток) | Хранить состояние установки в Room, а не в DataStore | Одна строка на пакет — это скаляр, а `ARCHITECTURE.md` §3 отдаёт скаляры DataStore. Плюс атомарная граница (раздел 10.5) требует, чтобы отметка «установлено» лежала **вне** транзакции, иначе она стала бы неотличима от данных, которые подтверждает |

Если при реализации всё же обнаружится реальная потребность в изменении схемы, она оформляется отдельным решением с (а) продуктовым обоснованием, (б) SQL-дельтой, (в) `Migration(1, 2)` и `MigrationTestHelper`, (г) подключением `room-testing`. Ни одного такого случая анализ не выявил.

## 3. Переход с временного контента

### 3.1 Фактическое состояние, из которого исходим

| Факт | Последствие для перехода |
| --- | --- |
| Временный пакет использует `packId = "core-ru"` | Настоящий пакет занимает **тот же** ключ; изоляции по пакету не будет |
| Временные наборы занимают `setIndex = 0, 1, 2` | Первые три индекса настоящего пакета пересекаются с уже выданными |
| Состав настоящих наборов 0–2 будет другим | Пересечение — не совпадение: те же индексы, другие `puzzleId` |
| Временные головоломки **никогда не писались** в `puzzles` | После переключения `PuzzleRepository` старые `tmp-*` ID не загрузятся ничем: строки для них не существует и создать её неоткуда |
| В базе разработчика/тестировщика уже могут быть `day_assignments`, `puzzle_attempts`, `day_results` по временным наборам | Молчаливая подмена состава показала бы в архиве чужие головоломки на сыгранных днях |
| Публичного релиза не было (раздел 0) | Обратная совместимость с фикстурой никому не обещана |

### 3.2 I4-D3. Предрелизный hard cutover

**Решение.** Владелец подтвердил условие (раздел 0, 2026-09-03), поэтому временный контент объявляется внутренней предрелизной фикстурой, а не опубликованной версией пакета `core-ru`. Из этого следуют семь правил, и все они реализуются механикой раздела 10, а не отдельным «режимом миграции»:

1. **Legacy-пакета не заводится.** Второй `packId`, сохранение payload временных головоломок и «переезд» истории не проектируются: обещание совместимости не давалось.
2. **Строки `daily_sets`, на которые нет назначений, заменяются транзакционно** — независимо от того, временные они или просто отличаются.
3. **Назначение, указывающее на лишний индекс или на индекс с изменившимся составом, — это `ContentInstallException.Conflict`.** Импорт прекращается.
4. **При конфликте не изменяется ни одна таблица и не обновляется DataStore.** Гарантия обеспечивается формой кода: исключение бросается **внутри** `withTransaction`, запись в DataStore стоит после `withTransaction` (раздел 10.5).
5. **Восстановление — только явным подтверждённым действием человека**, через уже существующий debug-механизм полного сброса (`HomeErrorRecoveryAction` → `clearAllTables()`), который в release-сборке не компилируется.
6. **Молчаливое изменение состава назначенного дня запрещено.** Это единственное правило, ради которого существует вся диагностика 3.3.
7. **Публичной обратной совместимости с фикстурой нет** — публичного распространения не было, это подтверждено владельцем. Разработчик с «грязной» базой получает честный конфликт и одно нажатие сброса, а не тихо испорченный архив.

**Что делает решение обратимым.** Механика раздела 10 не зависит от этого выбора: конфликт обнаруживается и объявляется одинаково в обоих случаях. Отличается только реакция на него — «сбросить базу вручную» против «поставить legacy-пакет». Поэтому отрицательный ответ владельца стоит дополнительной работы, но не переделки импортёра.

**Практическое следствие для команды из одного человека:** после мержа PR 4D первый запуск debug-сборки на устройстве, где игрались временные дни, покажет `Home.Error` с действием «Сбросить контент». Это ожидаемый и единственный сценарий ручной приёмки «конфликт → сброс → первый запуск» (`I4-E3`).

### 3.3 I4-D4. Как обнаруживается подмена назначенного набора

Обнаружить недостаточно «лишний `setIndex`»: составы могут разойтись **внутри** ожидаемого диапазона. Проверяются три независимых свидетельства, и каждое имеет собственный запрос.

**Свидетельство A — назначение вне диапазона пакета.** Ожидаемые индексы по правилу `R19` непрерывны: `0 .. setCount-1`. Поэтому диапазонный предикат точен и, в отличие от `NOT IN (:keep)`, не растёт со списком параметров при пакете в 35, 60 и более наборов.

```kotlin
// AssignmentDao
@Query(
    """
    SELECT set_index FROM day_assignments
     WHERE pack_id = :packId AND (set_index < 0 OR set_index >= :setCount)
     ORDER BY set_index
    """
)
suspend fun setIndexesOutsideRange(packId: String, setCount: Int): List<Int>

/** Дешёвая форма того же вопроса для пути подтверждения (10.3): нужен только факт. */
@Query("SELECT COUNT(*) FROM day_assignments WHERE pack_id = :packId AND (set_index < 0 OR set_index >= :setCount)")
suspend fun countOutsideRange(packId: String, setCount: Int): Int

/** Даты назначений вне диапазона — часть полезной нагрузки Conflict. */
@Query("SELECT local_date FROM day_assignments WHERE pack_id = :packId AND (set_index < 0 OR set_index >= :setCount) ORDER BY local_date")
suspend fun datesOutsideRange(packId: String, setCount: Int): List<String>
```

**Свидетельство B — сохранённый состав назначенного набора отличается от asset-пакета.** Читаются все назначения пакета вместе с датами и все строки `daily_sets` пакета; сравнение выполняется в Kotlin, потому что «ожидаемый состав» приходит из assets и в SQL его не передать дешевле, чем сравнить 35 троек в памяти.

```kotlin
// AssignmentDao
data class AssignedSetRow(val setIndex: Int, val localDate: String)

@Query("SELECT set_index AS setIndex, local_date AS localDate FROM day_assignments WHERE pack_id = :packId ORDER BY set_index")
suspend fun assignedSets(packId: String): List<AssignedSetRow>

// DailySetDao
@Query("SELECT * FROM daily_sets WHERE pack_id = :packId ORDER BY set_index")
suspend fun byPack(packId: String): List<DailySetEntity>
```

**Свидетельство C — фактически сыгранные головоломки не совпадают с составом asset-пакета.** Это сильнее B: строки `daily_sets` могли быть удалены (сценарий **I3-D50**), а `puzzle_attempts.puzzle_id` — прямое свидетельство того, что́ пользователь реально видел, и оно переживает любую очистку контента.

```kotlin
// AssignmentDao — запрос идёт ОТ назначений, поэтому живёт здесь, а не в AttemptDao
data class PlayedPuzzleRow(val setIndex: Int, val slotIndex: Int, val puzzleId: String, val localDate: String)

@Query(
    """
    SELECT a.set_index AS setIndex, t.slot_index AS slotIndex,
           t.puzzle_id AS puzzleId, a.local_date AS localDate
      FROM day_assignments a
      JOIN puzzle_attempts t ON t.local_date = a.local_date
     WHERE a.pack_id = :packId
     ORDER BY a.set_index, t.slot_index
    """
)
suspend fun playedPuzzles(packId: String): List<PlayedPuzzleRow>
```

**Правило вывода.**

```
staleIndexes   = A
changedIndexes = { setIndex назначения | (B: строка daily_sets есть и её тройка ≠ ожидаемой ПОСЛОТОВО)
                                       ∨ (C: есть попытка, у которой puzzle_id ≠ ожидаемому В ЕЁ СЛОТЕ) }
                 за вычетом допустимых расхождений (см. ниже)
конфликт ⇔ staleIndexes ∪ changedIndexes ≠ ∅
blockedDates = даты назначений из staleIndexes ∪ changedIndexes, отсортированные
```

Сравнение **послотовое, а не множественное**. Слот — часть контракта: попытка записана как `(local_date, slot_index, puzzle_id)`, и головоломка, переехавшая из слота 0 в слот 1, для пользователя не «та же самая на месте», а другая головоломка в открывающем задании дня.

**Допустимое расхождение — ровно одно: послотовая замена отозванной головоломки.** `CONTENT_MODEL.md` §7 объявляет состав выпущенного `setIndex` неизменяемым с единственным исключением — заменой головоломки, у которой выставлен `retiredIn`. Расхождение допустимо, только если выполняются **все** условия сразу:

1. список позиций, где `old[i] ≠ new[i]`, **непуст** (иначе расхождения нет вовсе, и разговор о «замене» не начинается);
2. ни один идентификатор, оставшийся в наборе, не занял другую позицию — то есть в изменившихся слотах нет ID, присутствующих в старом составе;
3. в каждой изменившейся позиции старый ID **есть в пакете и отозван** (`retiredIn != null`, и `retiredIn ≤ manifest.contentVersion`);
4. в той же позиции новый ID **существует и активен** (`retiredIn == null`).

Отсюда прямо следуют три отказа: чистая перестановка того же множества (`[A,B,C] → [B,A,C]`) — всегда конфликт (нарушено 2); сочетание «одну отозванную заменили, другую активную переставили» — конфликт (нарушено 2); замена отозванной на другую отозванную — конфликт (нарушено 4). Если старого идентификатора в новом пакете нет вовсе — как у всех `tmp-*` — нарушено 3, и это конфликт.

При допустимой замене архив по-прежнему разрешает старый `puzzleId` в строку `puzzles`, а экран результата показывает честную пометку «Задание отозвано» (итерация 5).

Ветка недостижима содержимым пакета v1 (`retiredIn` там везде `null`) и потому проверяется синтетическими фикстурами (`I4-I14a`–`I4-I14d`). Проектируется она сейчас, потому что без неё документ противоречил бы утверждённому `CONTENT_MODEL.md` §7, а первый же отзыв головоломки после релиза заблокировал бы обновление у всех, кто сыграл затронутый день.

**Одна ветка сознательно не является конфликтом:** назначение на индекс **внутри** диапазона, у которого строки `daily_sets` нет и **ни одной попытки не записано**. Доказательства иного состава не существует, пользователь не видел ни одной головоломки этого дня, и единственное осмысленное действие — записать корректный состав. Это «висячее назначение» **I3-D50** в его починяемой форме; вне диапазона оно остаётся конфликтом (свидетельство A).

### 3.4 Чего импорт не делает никогда

| Таблица | Что разрешено импортёру |
| --- | --- |
| `puzzles` | только `upsert`. **Ни одного `DELETE`** — головоломка, на которую может ссылаться история, не удаляется (`CONTENT_MODEL.md` §7) |
| `daily_sets` | `upsert` ожидаемых строк и **единственный `DELETE`** — строк активного пакета с `set_index` вне `[0, setCount)` |
| `day_assignments`, `puzzle_attempts`, `day_results` | ничего: ни `DELETE`, ни `UPDATE`, ни `INSERT` |
| Чужие `pack_id` | ничего: все запросы импортёра pack-scoped |

Проверка формой кода: `rg -n "DELETE FROM (day_assignments|puzzle_attempts|day_results)" app/src/main` — пусто; `rg -n "clearAllTables" app/src/main` — пусто (существует только в `src/debug`).

## 4. Формат пакета в assets

### 4.1 Каталог и файлы

```
app/src/main/assets/content/
    manifest.json          # версия, состав, контрольные суммы
    puzzles-001.json       # пул головоломок пакета 001
    daily-sets-001.json    # наборы пакета 001
```

Ровно три файла, ровно эти имена. Любой другой файл в каталоге — ошибка (`M08`).

### 4.2 `manifest.json`

```json
{
  "schemaVersion": 1,
  "contentVersion": 1,
  "packId": "core-ru",
  "packTitle": "Основной набор",
  "setCount": 35,
  "puzzleCount": 105,
  "files": [
    { "path": "puzzles-001.json",    "sha256": "…64 hex lowercase…" },
    { "path": "daily-sets-001.json", "sha256": "…64 hex lowercase…" }
  ]
}
```

| Поле | Обязательно | Ограничение | Комментарий |
| --- | --- | --- | --- |
| `schemaVersion` | да | `integer`, `1..1` в паке v1 | Поддерживаемое приложением значение — константа `SUPPORTED_SCHEMA_VERSION = 1`. Больше — отказ импорта (`M01`) |
| `contentVersion` | да | `integer ≥ 1` | **Начальная настоящая версия — `1`.** Пример `contentVersion: 3` в `CONTENT_MODEL.md` §3 — иллюстрация формата |
| `packId` | да | `^[a-z0-9]+(-[a-z0-9]+)*$`, длина 3..32 | Должен совпадать с `ContentPack.CORE_RU` и с `@ActivePack` |
| `packTitle` | да | 1..40 символов | В Room не переносится (**I4-D16**); потребитель — экран «о приложении», итерация 5 |
| `setCount` | да | `integer ≥ 1` | Сверяется с фактическим числом наборов (`R21`) |
| `puzzleCount` | да | `integer ≥ 3` | Сверяется с фактическим числом головоломок (`R21`) |
| `files` | да | ровно 2 элемента | Один с префиксом `puzzles-`, один с `daily-sets-`, пути различны |
| `files[].path` | да | `^(puzzles\|daily-sets)-[0-9]{3}\.json$` | Закрытый шаблон — см. 4.5 |
| `files[].sha256` | да | `^[0-9a-f]{64}$` | Нижний регистр, от **точных байтов** файла |

`contentStartDate` в манифесте отсутствует и не вводится (`CONTENT_MODEL.md` §3).

### 4.3 Конверты файлов

`puzzles-001.json` (**I4-D5** — конверт задаётся симметрично файлу наборов; в `CONTENT_MODEL.md` §4 он не был описан):

```json
{ "schemaVersion": 1, "packId": "core-ru", "puzzles": [ { /* объект §4 CONTENT_MODEL */ } ] }
```

`daily-sets-001.json` (как в `CONTENT_MODEL.md` §6):

```json
{ "schemaVersion": 1, "packId": "core-ru",
  "sets": [ { "setIndex": 0, "puzzleIds": ["…", "…", "…"] } ] }
```

`schemaVersion` и `packId` обязаны совпадать во всех трёх файлах (`M02`, `M07`). Это единственная защита от «собрали пакет из двух половин разных паков»: ссылочная целостность такую ошибку не ловит, если идентификаторы случайно совпали.

### 4.4 Кодировка и байты

- **UTF-8 без BOM.** BOM запрещён (`M09`): он ломает разбор и меняет хеш, а редакторы Windows добавляют его молча.
- Перевод строки — `\n`; файл заканчивается ровно одним переводом строки. Это не эстетика: `--sync-manifest` (4.7) переписывает файлы, и без фиксированной нормализации хеши прыгали бы от смены редактора.
- `sha256` считается **от точных байтов файла в assets**, включая завершающий перевод строки. `AssetManager.open()` отдаёт исходные байты (упаковщик может сжать asset, поток отдаёт распакованное содержимое), поэтому `noCompress` не требуется.
- Отступ — 2 пробела, `ensure_ascii = false`: кириллица хранится как есть, а не `\uXXXX`. Без этого diff батча нечитаем.

### 4.5 I4-D6. Манифест не может прочитать произвольный asset

Разделяются **два независимых контракта**, и их нельзя сводить к одному шаблону: манифест не объявляет сам себя, а объявляемые им файлы никогда не могут называться `manifest.json`.

| Контракт | Кто задаёт имя | Допустимые значения |
| --- | --- | --- |
| `ContentAssetSource.read(fileName)` | код приложения и `ContentPackReader` | ровно одно из: константа `ContentPaths.MANIFEST = "manifest.json"` **или** значение, прошедшее шаблон контентного файла |
| `manifest.files[].path` | автор контента | **только** `^(puzzles\|daily-sets)-[0-9]{3}\.json$`; `manifest.json` здесь недопустим (`M03`) |

`files[].path` — **не путь, а имя из закрытого множества**. Правила, проверяемые и в CI, и в рантайме **во всех типах сборки**:

1. Значение целиком совпадает с `^(puzzles|daily-sets)-[0-9]{3}\.json$`. Абсолютный путь, `..`, `/`, `\`, `~`, пустая строка, имя каталога, `manifest.json` и любое расширение кроме `.json` не проходят по построению.
2. Ровно два элемента; ровно один с каждым префиксом; пути различны (`M03` покрывает и дубликат, и лишний элемент).
3. Физический путь строится **только** как `content/` + проверенное имя. Конкатенация выполняется в одном месте — `ContentPaths.assetPath(name)`, — которому предшествует `require(name == MANIFEST || name.matches(CONTENT_FILE_NAME))`. Ни манифест, ни контентный файл не могут содержать `/`, `\`, `..`, `~`, абсолютный путь или подкаталог: оба имени проходят через одну и ту же проверку, различаются только допустимые значения.
4. Никаких `File`, `FileInputStream`, `openFileInput` и абсолютных путей в `data/content`: единственный источник байтов — `AssetManager.open`. Проверка: `rg -n "java\.io\.File|openFileInput|\.\./" app/src/main/java/ru/poporyadku/data/content` — пусто.

Шаблон, а не «санитайзер», выбран сознательно: список разрешённых имён известен заранее, и валидация через allow-list не имеет обходов, в отличие от нормализации путей.

### 4.6 I4-D5. Один файл каждого типа, без шардов

**Решение: манифест допускает ровно один `puzzles-*.json` и ровно один `daily-sets-*.json`. Шарды не поддерживаются.**

Почему не поддерживаются: 105 головоломок — около 300 КБ; они читаются один раз на версию контента (`ARCHITECTURE.md` ADR-003). Шардирование добавило бы порядок объединения, дедупликацию идентификаторов между шардами, семантику частичного отказа («шард 2 не прочитался — импортировать первый?») и отдельные правила диагностик — ради экономии, которой в пяти контентных PR не возникает.

**Как батчи дописывают один файл, не активируя неполный пакет.** Массивы `puzzles` и `sets` **дополняются в конец**: батч добавляет 21 объект головоломки и 7 объектов набора, ничего не переставляя. Diff батча аддитивен и читается построчно. Активации не происходит потому, что до PR 4D `ContentModule` связывает `ContentInstaller` с `TemporaryContentInstaller`, а `PuzzleRepository` — с `TemporaryPuzzleRepository`: **ни одна строка продуктового кода не открывает `assets/content/` до 4D**. Валидатор при этом видит пакет на каждом батче и проверяет его как самостоятельный корректный черновик: `setCount`/`puzzleCount` в манифесте равны фактическим (7/21, 14/42, …), непрерывность `setIndex` соблюдена от нуля, кросс-файловые правила выполняются. Требование «35 наборов / 105 головоломок» — **не правило валидатора, а критерий релиза**, проверяемый явным флагом (4.7) и включаемый в CI в PR 4D.

**Условие пересмотра:** пакет, где один тип файла превысил ~2 МБ, либо появление паков, собираемых из независимо авторируемых частей. Тогда `files` уже является массивом — формат менять не придётся, изменится только правило `M03`.

### 4.7 Порядок чтения и детерминированность

**Порядок ввода-вывода** определяется тем, что именно понадобилось, и различается у двух путей (раздел 10.3):

| Путь | Что читается | Когда |
| --- | --- | --- |
| Заголовок (каждый вызов `ensureInstalled()`, один раз на процесс) | `manifest.json` → `daily-sets-001.json` | всегда |
| Тело (только когда импорт действительно нужен) | дополнительно `puzzles-001.json` | при первом импорте, обновлении, откате, несовпадении отпечатка и при непройденном подтверждении базы |

Файл головоломок не читается на быстром пути сознательно (**I4-D10**): 300 КБ разбора на каждый пересчёт Home ради вывода «делать нечего» — плата, ради которой быстрый путь и существует. Валидатор в CI такого разделения не имеет: он читает все три файла всегда.

**Порядок отображения диагностик** — отдельная величина и фиксирован как `manifest.json` → `puzzles-001.json` → `daily-sets-001.json`. Он совпадает с направлением ссылок (наборы ссылаются на головоломки), удобен для чтения человеком и **не обязан** совпадать с порядком ввода-вывода. Подробности сортировки — раздел 7.6.

Поведение при отклонениях:

| Ситуация | CI | Рантайм |
| --- | --- | --- |
| Файл, объявленный в манифесте, отсутствует | `M04`, exit 1 | `BundleInvalid(M04)` |
| В каталоге есть файл, не объявленный в манифесте (кроме `manifest.json`) | `M08`, exit 1 | `BundleInvalid(M08)` — только в debug (**I4-D7**) |
| Хеш не совпал | `M06`, exit 1 | `BundleInvalid(M06)` — только в debug (**I4-D7**) |
| JSON не разбирается | `M05`, exit 1 | `BundleInvalid(M05)` |
| `schemaVersion` больше поддерживаемой | `M01`, exit 1 | `UnsupportedSchema` |
| `packId` расходится между файлами или с активным пакетом | `M02`, exit 1 | `BundleInvalid(M02)` |

Инструмент имеет два вспомогательных режима:

```bash
# пересчитать sha256 и counts в манифесте после правки контента
python3 tools/validate-content/validate.py app/src/main/assets/content --sync-manifest

# критерий релиза (включается в CI в PR 4D)
python3 tools/validate-content/validate.py app/src/main/assets/content --expect-sets 35 --expect-puzzles 105
```

`--sync-manifest` правит **только** `sha256` и `setCount`/`puzzleCount`, печатает каждое изменение и сохраняет форматирование. Производные данные, поддерживаемые руками через пять батчей, — гарантированный источник шума; при этом `R21` продолжает охранять **закоммиченный** артефакт, а diff манифеста в PR читается человеком. Обязательный шаг протокола: **после любой правки контента запускается `--sync-manifest`, иначе приложение не увидит изменений (раздел 10.2), а CI не пропустит PR.**

### 4.8 I4-D7. Что проверяется в release, а что нет

| Проверка | CI | debug | release | Почему |
| --- | --- | --- | --- | --- |
| Имена файлов, шаблон `path`, отсутствие путей | да | да | **да** | Это защита, а не целостность: цена — сравнение строки с regex |
| Разбор JSON, конверты, `schemaVersion`, `packId` | да | да | **да** | Без этого нечего импортировать |
| Защитные инварианты перед записью в Room (раздел 7.2) | да | да | **да** | Единственная преграда между испорченным пакетом и базой пользователя |
| `sha256` файлов | да | да | нет | `CONTENT_MODEL.md` §3: лишний расход батареи; APK подписан, а его целостность обеспечивает система пакетов |
| Лишний файл в каталоге | да | да | нет | Та же категория: целостность артефакта, проверенная до сборки |
| Все 21 правило (порядок, разрывы, источники, компоновка) | **да** | нет | нет | Авторские правила: нарушение делает контент неверным, но не ломает приложение. Их место — до мержа (**I4-D30**) |

## 5. JSON Schema (Draft 2020-12)

### 5.1 Файлы и общие правила

```
tools/validate-content/schema/
    manifest.schema.json      $id https://poporyadku.app/schema/manifest/v1
    puzzles.schema.json       $id https://poporyadku.app/schema/puzzles/v1
    daily-sets.schema.json    $id https://poporyadku.app/schema/daily-sets/v1
```

Общие требования ко всем трём:

- `"$schema": "https://json-schema.org/draft/2020-12/schema"`;
- `"additionalProperties": false` на **каждом** объекте, включая вложенные (карточка, источник, элемент `files`, элемент `sets`);
- `"type"` указан явно везде; свободных `{}`-подсхем нет;
- строковые поля имеют `minLength`/`maxLength`, числовые — `minimum`/`maximum`, массивы — `minItems`/`maxItems`;
- перечисления заданы `enum`, идентификаторы — `pattern`;
- `$defs` используются для повторяющихся типов (`isoDate`, `sha256`, `cardId`, `sourceId`).

**Исключение из требования о числовых границах — только верхняя, и только там, где границей владеет правило.** Пять полей её не имеют: `schemaVersion` (сверяется с `SUPPORTED_SCHEMA_VERSION` правилом `M01`), `retiredIn` (с `contentVersion` — `R18C`), `setCount` и `puzzleCount` (с фактическим числом элементов — `R21`), `setIndex` (с `0..setCount−1` — `R19`). Выдуманное `maximum` там не просто дублирует правило вторым кодом: находка схемы блокирует семантические правила файла, поэтому точный `R18C` или `R19` заменился бы общим `R01`. Нижние границы этих полей и обе границы всех остальных числовых полей на месте. Подробности и остальные границы владения — раздел «Уточнения, сделанные при реализации PR 4A» в конце документа.

### 5.2 Даты ISO: почему `format` недостаточно

В Draft 2020-12 `format` по умолчанию — **аннотация**, а не утверждение: валидатор вправе его игнорировать, и большинство реализаций так и делает. Поэтому даты проверяются тремя слоями:

1. `"pattern": "^\\d{4}-\\d{2}-\\d{2}$"` — форма, работает в любой реализации;
2. `"format": "date"` при **явно включённом** режиме проверки формата (в CLI — `FormatChecker`, зафиксировано в тестах `I4-A33`);
3. семантическая проверка каждой ISO-даты пакета (`verifiedAt`, `accessedAt`): дата разбирается календарно — `R04A_DATE_NOT_CALENDAR` отсекает `2026-02-30` и `2026-13-01`; дата не лежит в будущем — `R04B_DATE_IN_FUTURE`.

Слой 3 обязателен: `pattern` пропускает `2026-13-45`, а зависеть от того, что реализация включила `format`, — значит зависеть от настройки, которую легко потерять.

**«Будущее» задаётся параметром, а не системными часами.** Валидатор принимает `--validation-date YYYY-MM-DD` (по умолчанию — сегодняшняя дата), а внутри правила работают с явно переданным значением, а не с `date.today()`. Причина практическая: тест, сравнивающий дату фикстуры с календарём машины, «зелёный сегодня и красный через год» — то есть не тест, а таймер. Все тесты `I4-A8` передают фиксированную `--validation-date`, и фикстуры содержат литеральные даты; в CI и при ручном запуске значение по умолчанию даёт обычное поведение. То же значение передаётся в диагностику, поэтому сообщение воспроизводимо.

Отличия от сокращённой схемы `CONTENT_MODEL.md` §4 — все в сторону строгости, все требуют синхронизации документа (раздел 19):

| Изменение | Причина |
| --- | --- |
| `retiredIn` переведён в `required` (тип `["integer","null"]`) | Отсутствие поля и явный `null` — разные вещи только для человека; для кода это одно и то же состояние, и обязательность снимает вопрос «забыли или отозвали» |
| `uniqueItems: true` у `correctOrder` и `sourceIds` | Дубликат `cardId` в порядке — не «правило», а бессмыслица; отсекается схемой, а не семантикой |
| `anyOf` «`url` или `reference`» | Правило 17 выражается схемой полностью, не требуя семантического дублёра |
| `pattern: "^https://"` у `url` | `http://` в источнике 2026 года — сигнал небрежности; `format: uri` без этого пропускает `ftp://` и `javascript:` |
| Верхние границы `maxItems`/`maxLength` там, где их не было (`sources`, `title`, `note`, `puzzleId`) | Строгая схема не должна иметь неограниченных полей: неограниченное поле — это неограниченный размер APK и неограниченная строка на экране |
| `minLength` у необязательных строк (`subtitle`, `note`) | Пустая строка вместо отсутствия поля — самая частая ошибка ручного авторинга |

Схема наборов и манифеста строится теми же правилами: `sets[].puzzleIds` — `minItems: 3, maxItems: 3, uniqueItems: true`, `setIndex` — `integer, minimum: 0`, `files` — `minItems: 2, maxItems: 2, uniqueItems: true`.

### 5.4 I4-D24. Единицы `sortValue` и правило минимального разрыва

`CONTENT_MODEL.md` §8 задаёт разрыв «≥ 2 года» и «≥ 3 %», не определяя единицу `sortValue` для каждого `sortKey`. Без такой таблицы правило 8 неисполнимо: 3 % от −40 °C бессмысленны (интервальная шкала), 3 % от широты 0,5° вырождаются в ноль.

| `sortKey` | Единица `sortValue` | Правило разрыва | Статус в паке v1 |
| --- | --- | --- | --- |
| `year` | год; до н. э. — отрицательное число; нуля не существует | `\|a − b\| ≥ 2` | **разрешён** |
| `height`, `depth`, `length`, `distance` | метры | `\|a − b\| ≥ 0,03 · max(\|a\|,\|b\|)` | **разрешён** |
| `area` | квадратные километры | то же, относительное | **разрешён** |
| `mass` | килограммы | то же, относительное | **разрешён** |
| `speed` | километры в час | то же, относительное | **разрешён** |
| `duration` | секунды | то же, относительное | **разрешён** |
| `population` | — | — | **запрещён**: по природе `volatile` (правило 9 и §9 «защита от устаревания») |
| `temperature` | — | — | **запрещён в v1**: интервальная шкала, относительный порог неприменим; абсолютный порог не задан ни одним документом |
| `date` | — | — | **запрещён в v1**: единица (день эпохи? год?) не зафиксирована |
| `latitude`, `longitude` | — | — | **запрещён в v1**: относительный порог вырождается около экватора/нулевого меридиана |

Запрет реализуется кодом `R08C`. Отложенных ключей **пять**: `date`, `population`, `temperature`, `latitude`, `longitude`. Разрешение любого из них — отдельное решение с дописанной строкой в эту таблицу; формат при этом не меняется, `enum` в схеме остаётся полным.

Дополнительно правило 8 требует для ратио-шкал `sortValue > 0` (`R08D`) и запрещает `sortValue == 0` при `sortKey = year` (`R08E`: нулевого года не существует).

**Что остаётся человеку:** «разрыв ≥ типичной погрешности источников». Машина не знает погрешности; она проверяет 2 года и 3 %. Соответствие разрыва реальной погрешности измерения — пункт редакционного чек-листа (раздел 7).

### 5.5 I4-D25. Формализация правила компоновки набора

`CONTENT_MODEL.md` §6 задаёт **исчерпывающий** контракт, а не иллюстрации: «сложность внутри набора по возрастанию: `difficulty` 1 → 2 → 2, или 1 → 2 → 3» — это перечень допустимых профилей целиком, и «три разные категории» означает попарную различность. Настоящий раздел ничего к контракту не добавляет и ничего в нём не ослабляет: он переводит его в проверяемые предикаты и раздаёт им коды.

| Подправило | Предикат | Код |
| --- | --- | --- |
| Три **попарно различные** категории | `c₀ ≠ c₁ ∧ c₁ ≠ c₂ ∧ c₀ ≠ c₂` — без исключений, включая `mixed` | `R20A` |
| Профиль сложности — один из двух | `(d₀,d₁,d₂) ∈ { (1,2,2), (1,2,3) }` | `R20B` |
| Категория не открывает два набора подряд | `category(set[i].slot0) ≠ category(set[i−1].slot0)` — **включая** `mixed` | `R20C` |
| В первых семи наборах нет `difficulty = 3` | `setIndex ≤ 6 ⇒ max(d) ≤ 2` | `R20D` |

**Профили сложности.** Допустимы ровно `[1,2,2]` и `[1,2,3]`. Запрещены `[1,1,2]`, `[2,2,3]`, `[2,2,2]`, `[1,3,3]`, `[2,1,3]`, `[3,1,2]` и любые другие. Перечень из двух элементов сравнивается напрямую, без вывода через неравенства: неравенства `d₀ ≤ d₁ ≤ d₂ ∧ d₀ < d₂` пропускают `[1,1,2]` и `[2,2,3]`, то есть **расширяют** утверждённое правило, а не выражают его.

**Первые семь наборов.** `R20B` и `R20D` вместе оставляют там ровно **один** профиль — `[1,2,2]`: второй допустимый профиль содержит `difficulty = 3`, запрещённую до восьмого набора. Это самое узкое место контракта, и оно намеренно узкое: через первые семь наборов проходит каждый пользователь.

**`mixed` не является исключением ни в `R20A`, ни в `R20C`.** «Три разные категории» — это три различных значения поля `category`; `mixed` — такое же значение, как `history`. Он совместим с любой парой других **различных** категорий (`mixed + history + science` допустимо), но не разрешает ни второй `mixed` в наборе (`mixed + mixed + science` — нарушение `R20A`), ни повтор какой-либо другой категории рядом с собой (`mixed + history + history` — тоже `R20A`). Точно так же `mixed` не даёт права открывать два набора подряд: `R20C` сравнивает значения, а не «содержательность» категории. Формулировка `CONTENT_MODEL.md` §6 «исключение: `mixed` может соседствовать с любой» означает совместимость по темам, а не разрешение на дубликат: набор из двух `mixed` не имеет трёх категорий ни в каком прочтении.

`R20C` проверяется **сквозь границы батчей**: валидатор всегда видит файл целиком, поэтому набор 7 сверяется с набором 6 из предыдущего батча автоматически.

## 6. Двадцать одно правило и правила уровня пакета

### 6.1 Уровни

| Уровень | Что означает | Где живёт |
| --- | --- | --- |
| **schema** | Выражается JSON Schema Draft 2020-12 целиком | `tools/validate-content/schema/*.schema.json` |
| **semantic** | Требует вычисления или сравнения внутри одного объекта/файла | `tools/validate-content/contentval/rules_semantic.py` |
| **cross-file** | Требует данных из двух и более файлов пакета | `…/rules_crossfile.py` |
| **bundle** | Свойство самого пакета: манифест, имена, байты, счётчики | `…/rules_manifest.py` |
| **editorial** | Проверяет человек; автоматика может только напомнить | `docs/CONTENT_REVIEW_CHECKLIST.md` |
| **runtime** | Входит в защитный набор, проверяемый приложением до записи в Room | `data/content/validation/ContentValidator.kt` |

Позитивный тест по умолчанию — `I4-A1` (полная валидная фикстура `fixtures/valid/`) и `I4-A2` (`fixtures/valid-minimal/`, 1 набор / 3 головоломки).

**Состав `fixtures/valid/` — 8 наборов / 25 головоломок:** 24 активные используются ровно по одному разу (8 × 3), 1 отозванная (`retiredIn` = текущая `contentVersion`) присутствует в пуле и **не используется** ни одним набором. Двадцать пять, а не двадцать четыре: `R18B` требует, чтобы каждая головоломка набора встречалась не более раза, а `R18A` запрещает ссылаться на отозванную, — значит отозванная обязана быть лишней в пуле, и `manifest.puzzleCount` фикстуры равен `25`, тогда как `setCount` равен `8`. Фикстура также содержит `slow`, `disputed`, оба направления сортировки, четыре разрешённых `sortKey` и оба допустимых профиля сложности (`[1,2,2]` в наборах 0–6, `[1,2,3]` в наборе 7). Отдельные позитивные тесты указаны там, где нужен специальный случай.

### 6.4 Что автомат проверить не может

`CONTENT_MODEL.md` §8 говорит об этом одним абзацем; здесь список разведён явно, потому что смешение этих четырёх вещей — главный способ выдать «валидатор зелёный» за «контент проверен».

| Область | Кто проверяет | Артефакт | Почему автомат бессилен |
| --- | --- | --- | --- |
| **Формальная корректность** — схема, ссылки, порядок, разрывы, покрытие источниками, компоновка | валидатор в CI | exit-код и диагностики | — |
| **Достоверность источника** — ссылка открывается, страница существует, издание существует, `kind` соответствует характеру издания | человек | пункт чек-листа с датой и подписью `verifiedBy` | Схема не отличает настоящий URL от правдоподобного; сетевой доступ из CI не сделал бы это проверкой факта — только проверкой доступности |
| **Корректность утверждения** — на странице действительно указано это значение; значение соответствует признаку и единице; разрыв больше реальной погрешности | человек | заполненная строка чек-листа на каждую карточку | Требует чтения источника и понимания предметной области |
| **Редакционная приёмка** — формулировка однозначна, объяснение объясняет «почему», тон нейтральный, типографика (тире, «ё», неразрывные пробелы), «может ли грамотный человек обосновать другой порядок?» | человек | подписанный чек-лист батча `docs/content-reviews/4C-N.md` | Это суждение, а не проверка |

Правило приёмки батча: **валидатор зелёный — необходимое условие мержа, но не достаточное.** Достаточным его делает подписанный чек-лист (раздел 12).

## 7. Одна семантика в CI и в приложении

### 7.1 I4-D8. Технология валидатора

**Решение: JSON Schema Draft 2020-12 + CLI на Python 3.12 в `tools/validate-content/`; в приложении — pure-Kotlin `ContentValidator`, реализующий только защитный набор; эквивалентность доказывается общими фикстурами.**

| Вариант | Плюсы | Минусы | Итог |
| --- | --- | --- | --- |
| **Python 3.12 + `jsonschema`** | Референсная реализация Draft 2020-12; ноль влияния на Gradle-сборку; мгновенный запуск; в репозитории уже есть Python-инструмент (`tools/design-b2/`, README, тот же стиль) | Алгоритм перемешивания (правило 10) приходится портировать; нужна pin-фиксация зависимости в CI | **выбран** |
| Kotlin/JVM CLI отдельной сборкой | `DeterministicShuffler` переиспользуется исходником, порт не нужен | Второй Gradle-артефакт, конфигурация, +десятки секунд к CI; чтобы не копировать шаффлер, нужен либо общий модуль (против ADR-001), либо подключение чужого `srcDir` — приём, который потом никто не объяснит | отклонён |
| Gradle-задача внутри `:app` | Ничего нового не появляется | Валидатор становится зависимым от Android-сборки; запуск «просто проверить контент» тянет AGP; авторинг контента блокируется состоянием кода | отклонён |
| Только рантайм-валидация, без CI | Одна реализация | Ошибка контента обнаруживается на устройстве, а не в PR. Прямо против `CONTENT_MODEL.md` §8 | отклонён |

Зависимости инструмента фиксируются точными версиями с хешами:

```
tools/validate-content/requirements.txt      # jsonschema==<pin>, referencing==<pin>, --hash=sha256:…
```

Конкретные значения проставляются в PR 4A по официальным источникам и записываются в `docs/VERSIONS.md` тем же порядком, что все прочие версии проекта (компонент → версия → первичный источник → дата проверки). Заранее выписывать номера здесь нельзя: между документом и PR пройдёт время, и выдуманная версия хуже отсутствующей.

### 7.2 Разделение обязанностей: 21 правило против защитного набора

Двадцать одно правило **не** реализуется дважды. Реализуются:

- **в CLI — все 21 + `M01…M10`**: это авторский шлюз, он работает до мержа и имеет право быть медленным и подробным;
- **в приложении — защитный набор из 16 кодов**, и у него **два владельца**, а не один:

| Владелец | Коды | Когда работает |
| --- | --- | --- |
| `ContentPackReader` | `M01`, `M02`, `M03`, `M04`, `M05`, `M07`, `R01` (+ `M06`, `M09` в debug) | при чтении и декодировании; до того, как `ParsedPack` существует |
| `ContentValidator` | `R05`, `R18`, `R18A`, `R18B`, `R18C`, `R19`, `R21`, `D01`, `D02` | только над **успешно построенным** `ParsedPack` |
| `AssetContentSource` / `ContentPackReader` (debug) | `M08` | при листинге каталога |

Приписывать все шестнадцать кодов `ContentValidator` было бы неверно фактически: семь из них возникают там, где валидатора ещё не во что вызывать.

Граница проведена по одному критерию: **защитный набор — это то, нарушение чего ломает приложение или портит базу; остальное — то, нарушение чего делает контент неверным.** Испорченная ссылочная целостность даёт `SetNotFound` на живом устройстве; неверный `correctOrder` даёт неправильный ответ — плохо, но экран работает, и место такой ошибки — в CI, а не в защите рантайма. Дублировать в Kotlin вычисление разрывов, покрытие источниками и правила компоновки значило бы завести вторую независимую реализацию 21 правила без выигрыша: пакет лежит внутри APK и уже прошёл CI.

Кодов `R02` и `R11` в защитном наборе нет намеренно — почему, объясняет 7.3.

### 7.3 Разбор, декодирование и точность кода в рантайме

CLI и приложение отвечают на вопрос «что не так» разными инструментами: у CLI есть JSON Schema, которая видит документ целиком и умеет назвать конкретное нарушенное ограничение; у приложения есть `kotlinx-serialization`, которая либо строит DTO, либо не строит. Пытаться воспроизвести точность схемы в Kotlin — значит написать вторую JSON Schema руками. Поэтому модель фиксируется явно:

| Что случилось | Код в рантайме | Код в CLI |
| --- | --- | --- |
| Байты не являются корректным JSON (обрыв, лишняя запятая, одиночные кавычки, BOM в debug) | `M05_MALFORMED_JSON` | `M05_MALFORMED_JSON` |
| JSON корректен, но DTO не строится: нет обязательного поля, неверный тип, неверная форма массива | **`R01_SCHEMA`** — один код на все случаи, с текстом исключения сериализации в `detail` | точный код: `R01`, `R02`, `R03`, `R04`, `R11`, `R17`, … |
| Неизвестное **необязательное** поле | игнорируется (**I4-D9**) | `R01_SCHEMA` (`additionalProperties: false`) |
| DTO построен, но значения нарушают защитный инвариант | `D01`, `D02`, `R05`, `R18`, `R18A`, `R18B`, `R19`, `R21` | те же коды |

Следствия, которые обязаны быть одинаково понятны обеим сторонам:

1. **`R02` и `R11` — специализированные коды CLI.** Отсутствующий `correctOrder` и отсутствующий `sourceIds` в рантайме не доходят до `ContentValidator`: DTO не строится, и отказ уже назван `R01`. Рантайм **не обещает** `R02`/`R11` и не должен их возвращать.
2. **`D01_PUZZLE_FORM` проверяет только значения успешно построенного DTO** — количество карточек, уникальность `cardId`, перестановочность `correctOrder`, непустоту текстов. Он не заменяет схему и не подменяет `R01`.
3. **Пустой `sourceIds` защитным инвариантом не является:** приложение не читает источники при выдаче головоломки, отсутствие источника ничего не ломает и ловится в CI (`R11`). Поэтому его нет ни в `D01`, ни в защитном наборе.
4. **Parity-тест `I4-P2` сравнивает коды с учётом этой модели** и запускает **полный runtime-путь** `ContentPackReader → ContentValidator`, а не один валидатор: `R01` возникает в читателе, и требовать его от `ContentValidator` было бы требованием невыполнимого. На фикстурах, где CLI даёт `R02`, `R11`, `R03` или `R04` из-за несобираемого DTO, ожидаемый код рантайма — `R01`. Соответствие записано в `expectations.json` двумя колонками (`cli`, `runtime`), а не одной; там, где колонки совпадают, вторая опускается.
5. **Границу владельцев фиксирует отдельный тест `I4-P6`:** на фикстуре с несобираемым DTO читатель возвращает `R01`, а `ContentValidator` **не вызывается вовсе** (подставной валидатор считает вызовы). Без этого теста «reader отвечает за `R01`» осталось бы соглашением на словах.

Альтернатива «вернуть точный код и в рантайме» отклонена: она требует либо дублирования JSON Schema в Kotlin, либо nullable-DTO с ручной проверкой каждого поля — то есть той же схемы, написанной вручную и расходящейся с настоящей при первой же правке формата.

### 7.4 Как доказывается эквивалентность

Общий каталог фикстур — **единственный** источник истины для обеих сторон:

```
tools/validate-content/fixtures/
    valid/            valid-minimal/          # позитивные пакеты
    invalid/<code>/                            # по одному пакету на код
    expectations.json                          # фикстура → ожидаемые коды (отсортированные)
    shuffle-vectors.json                       # puzzleId → стартовый порядок
```

- `expectations.json` читается и pytest-тестами CLI, и JVM-тестами: `app/build.gradle.kts` передаёт путь системным свойством `content.fixtures.dir`, поэтому тест не зависит от рабочего каталога Gradle;
- **`I4-P1`** — CLI на каждой фикстуре выдаёт ровно ожидаемый список кодов;
- **общий parity harness** прогоняет фикстуру через **полный runtime-путь** — `ContentPackReader` поверх `ResourceContentSource`, затем `ContentValidator` над построенным `ParsedPack` — и собирает коды обоих слоёв в один отсортированный список. Именно этот список сравнивается с ожиданиями: разделение обязанностей внутри рантайма — деталь реализации, а контракт «какие коды даёт приложение на этой фикстуре» один;
- **`I4-P2`** — полный runtime-путь на фикстурах защитного набора выдаёт коды колонки `runtime`;
- **`I4-P3`** — на фикстурах, нарушающих только авторские правила, полный runtime-путь **не находит нарушений**. Асимметрия не побочный эффект, а проверяемое свойство: если рантайм начнёт отвергать авторские нарушения, тест упадёт и потребует осознанного решения;
- **`I4-P6`** — на фикстуре с несобираемым DTO читатель даёт `R01`, а `ContentValidator` не вызывается;
- **`I4-P4`** — `shuffle-vectors.json` совпадает с результатом настоящего `DeterministicShuffler` (JVM) и с портом (Python). Векторы включают три `tmp-*`-идентификатора из `I3-H2` (контракт, зафиксированный в итерации 3), кириллический идентификатор, идентификатор длиной в верхнюю границу и пару идентификаторов, различающихся одним байтом, — набор, на котором расходятся реализации с ошибками в знаковой арифметике, сдвигах и переполнении;
- **`I4-C3`** — правило 10 дополнительно проверяется по настоящему пакету настоящим `DeterministicShuffler` в JVM-тесте. Порт может ошибиться только в сторону ложного пропуска, и этот тест ловит ложный пропуск в том же прогоне CI.

Порт шаффлера в Python занимает шесть строк и обязан явно маскировать 64-битную арифметику (`& 0xFFFFFFFFFFFFFFFF`) и воспроизводить логический сдвиг вправо. Это единственное место дублирования алгоритма во всём проекте, и оно закрыто векторами.

### 7.5 I4-D9. Строгий CI против терпимого рантайма

Противоречие формулируется так: JSON Schema имеет `additionalProperties: false` и падает на неизвестном поле, а `kotlinx-serialization` в приложении настраивается с `ignoreUnknownKeys = true`.

**Оба поведения правильны, и вот почему они не конфликтуют.**

`CONTENT_MODEL.md` §7 прямо постановляет: «Добавление нового **необязательного** поля `schemaVersion` не меняет». Значит, по утверждённой политике версионирования существует легальный пакет, который содержит поле, неизвестное данной версии приложения, и при этом обязан импортироваться. Приложение, падающее на неизвестном ключе, сделало бы эту политику неисполнимой: любое расширение формата требовало бы синхронного обновления приложения, то есть `schemaVersion`-бампа — ровно того, что §7 запрещает. Поэтому **терпимость рантайма — требование политики версионирования, а не послабление.**

CI строг по противоположной причине: в момент авторинга неизвестный ключ **всегда** опечатка. `sourceId` вместо `sourceIds`, `retiredIn` вместо `retired_in`, `subtitile` — это ошибки, которые молча теряются при терпимом разборе, и единственный способ их поймать — запретить всё, что не описано схемой. Схема — контракт для автора; терпимость — контракт для будущего пакета.

Практически: неизвестное поле не может доехать до пользователя, потому что оно не проходит CI; терпимость рантайма используется только тем сценарием, ради которого объявлена, — паком, собранным по более новому минорному формату. В MVP пакет едет внутри APK, поэтому ветка недостижима и проверяется тестом `I4-R1` (пакет с лишним ключом разбирается, значение игнорируется, импорт проходит).

Настройки разбора фиксируются буквально:

```kotlin
@AssetJson   Json { ignoreUnknownKeys = true;  isLenient = false; coerceInputValues = false; explicitNulls = false }
@StorageJson Json { ignoreUnknownKeys = false; isLenient = false; coerceInputValues = false; explicitNulls = false }
```

`isLenient = false` — без него разбор принял бы кавычки-одиночки и незакавыченные ключи, то есть «почти JSON». `coerceInputValues = false` — без него `null` в поле с умолчанием молча превратился бы в умолчание, а это тихая потеря данных. `@StorageJson` **строг**: то, что лежит в `cards_json`, писали мы сами, и неизвестный ключ там означает повреждение, а не совместимость.

### 7.6 CI: команда, коды выхода, диагностики

Шаги, добавляемые в `.github/workflows/ci.yml`:

```yaml
- name: Set up Python
  uses: actions/setup-python@v6
  with:
    python-version: "3.12"
    cache: pip
    cache-dependency-path: tools/validate-content/requirements.txt

- name: Install content validator
  run: pip install --require-hashes -r tools/validate-content/requirements.txt

# PR 4A: фикстуры инструмента
- name: Validator self-check
  run: python3 -m pytest tools/validate-content/tests -q

# PR 4C-1: настоящий пакет; в PR 4D добавляются --expect-sets 35 --expect-puzzles 105
- name: Validate content pack
  run: python3 tools/validate-content/validate.py app/src/main/assets/content
```

**Коды выхода:**

| Код | Значение | Пример |
| --- | --- | --- |
| `0` | нарушений нет | валидный пакет |
| `1` | найдено ≥ 1 нарушение контента | любая фикстура `invalid/*` |
| `2` | инструмент не смог выполнить проверку | каталог не существует, нет прав, сломана схема, внутренняя ошибка |

Разделение 1 и 2 обязательно: без него «контент плохой» и «валидатор сломан» выглядят в CI одинаково, и второе чинят как первое.

**Формат диагностики** — одна строка на находку, машиночитаемая без разбора естественного языка:

```
R06_ORDER_MISMATCH puzzles-001.json#/puzzles/12/correctOrder — записан [c1,c2,c3,c4], вычислен [c2,c1,c3,c4]
R20D_EARLY_DIFFICULTY daily-sets-001.json#/sets/3 — difficulty 3 у головоломки sci-otkrytiya-031 в наборе 3 (первые семь наборов)
```

`--format json` печатает то же самое как `{"findings":[{"code","file","pointer","message"}],"counts":{…}}` в том же порядке.

**Сортировка находок детерминирована** и не зависит ни от порядка обхода словарей, ни от версии Python:

1. файл — в **порядке отображения** (`manifest.json`, `puzzles-001.json`, `daily-sets-001.json`), который задан разделом 4.7 и не зависит от того, в каком порядке файлы фактически читались;
2. JSON-pointer — посегментно, с **числовым** сравнением индексов массивов (`/puzzles/2` раньше `/puzzles/10`);
3. код правила — лексикографически.

Проверка `I4-A33`: перемешивание порядка ключей во входном JSON и запуск на двух версиях интерпретатора дают побайтово одинаковый вывод.

**Что проверяется в CI по assets:** оба файла пакета и манифест целиком, каждый прогон, без инкрементальности и без кеша результатов. Пакет мал, а «валидировали только изменённое» — способ пропустить нарушение кросс-файлового правила, вызванное изменением в другом файле.

### 8.3 `ContentAssetSource`

```kotlin
object ContentPaths {
    const val ROOT = "content"
    /** Имя манифеста — КОНСТАНТА кода, а не значение из данных. */
    const val MANIFEST = "manifest.json"
    /** Имена файлов, объявляемых манифестом. `manifest.json` сюда не подходит. */
    val CONTENT_FILE_NAME = Regex("^(puzzles|daily-sets)-[0-9]{3}\\.json$")

    fun isReadable(name: String) = name == MANIFEST || CONTENT_FILE_NAME.matches(name)

    /** Единственное место конкатенации во всём проекте. */
    fun assetPath(name: String): String {
        require(isReadable(name)) { "недопустимое имя файла контента: '$name'" }
        return "$ROOT/$name"
    }
}

/** Байты пакета. Единственный источник — AssetManager; путь строится только из
 *  проверенного имени (I4-D6). Ничего не разбирает и ничего не проверяет по существу. */
interface ContentAssetSource {
    /** @param fileName либо [ContentPaths.MANIFEST], либо имя по [ContentPaths.CONTENT_FILE_NAME].
     *  @throws IllegalArgumentException если имя не проходит [ContentPaths.isReadable] —
     *          бросается ДО любого обращения к AssetManager.
     *  @throws java.io.IOException если файла нет или он не читается. */
    suspend fun read(fileName: String): ByteArray

    /** Имена файлов каталога content/. Используется только проверкой M08 (debug/CI). */
    suspend fun list(): List<String>
}
```

`ContentAssetSource.read` принимает **два вида имён** — константу манифеста и контентное имя, — а `manifest.files[].path` допускает **только** второе (4.5). Разница не косметическая: имя манифеста задаёт код, поэтому данные не могут им управлять, а любой файл, объявленный данными, обязан пройти закрытый шаблон. Обе ветки закрывают `/`, `\`, `..`, `~`, абсолютные пути и подкаталоги одинаково — через `ContentPaths.isReadable`.

Реализация `AssetContentSource(@ApplicationContext context)` выполняет чтение на `Dispatchers.IO`. Тесты подставляют `ResourceContentSource`, читающий тот же каталог фикстур `tools/validate-content/fixtures/…`, — это и есть механизм parity `I4-P2`/`I4-P3`.

### 8.4 `ContentPackReader`

Отвечает за путь «байты → `ParsedPack`» и **ни за что более**. У него две операции — `readHeader()` и `readBody(header)`, и порядок ввода-вывода определяется тем, какая вызвана (4.7).

`readHeader()`:

1. читает `ContentPaths.MANIFEST` и разбирает его, считает `sha256` его байтов — это `fingerprint` пакета;
2. проверяет `M01`, `M02` (манифест против `@ActivePack`), `M03`;
3. читает `daily-sets-*.json`, при включённой проверке целостности сверяет `M06`, разбирает конверт, проверяет `M07`;
4. отдаёт `PackHeader(manifest, fingerprint, sets, expectedSetRows)`.

`readBody(header)` вызывается **только когда импорт действительно нужен**: читает `puzzles-*.json`, при включённой проверке целостности сверяет `M06`, разбирает конверт, проверяет `M07`, и отдаёт `ParsedPack(manifest, fingerprint, puzzles, sets)`.

Разделение на «заголовок» (манифест + наборы) и «тело» (головоломки) не косметическое: заголовок нужен на каждом вызове `ensureInstalled()`, тело — только на пути импорта (раздел 10). Отсюда и различие порядков ввода-вывода и отображения диагностик (4.7).

### 8.5 `ContentValidator`

```kotlin
class ContentValidator @Inject constructor() {
    /** Все нарушения защитного набора, отсортированные тем же порядком, что диагностики CLI. */
    fun findings(pack: ParsedPack): List<ContentViolation>

    /** @throws ContentInstallException.BundleInvalid при непустом findings(): код первого
     *  нарушения + общее число. */
    fun validate(pack: ParsedPack)
}

data class ContentViolation(val code: String, val file: String, val pointer: String, val message: String)
```

Собирает **все** нарушения, а не падает на первом: сообщение «нарушений 7, первое — R19_SET_INDEX_SEQUENCE» отличает «одна опечатка» от «подложили не тот пакет», а parity-тесты сравнивают полные списки.

`ContentValidator` работает **только над успешно построенным `ParsedPack`** (7.3): всё, что мешает построить DTO, отсекается раньше — `M05` для неразбираемого JSON и `R01` для несобираемого DTO, — и до валидатора не доходит. Поэтому `D01_PUZZLE_FORM` проверяет значения (четыре карточки, уникальность `cardId`, перестановочность `correctOrder`, непустоту текстов), а не наличие полей, и коды `R02`/`R11` он не возвращает никогда.

## 9. Преобразование данных

### 9.1 Три формы одних и тех же данных

| Форма | Тип | Владелец контракта | Меняется вместе с |
| --- | --- | --- | --- |
| Asset-DTO | `PuzzleDto`, `CardDto`, `SourceDto` | формат контента | `schemaVersion` |
| Строка Room | `PuzzleEntity` + `StoredCard`/`StoredSource` в JSON-колонках | схема базы | версией Room |
| Домен | `core.model.Puzzle`, `Card`, `Puzzle.Source` | приложение | никем извне |

### 9.2 I4-D17. Форма JSON-колонок отделена от asset-DTO

`cards_json` и `sources_json` **не** хранят asset-DTO. Для них заводятся собственные `@Serializable`-типы `StoredCard`, `StoredSource` в `data/db/json/`.

Сценарий, который делает это необходимым: `schemaVersion` вырастает, поле формата переименовано, приложение переимпортирует пакет — и все строки переписываются… кроме отозванных головоломок, которых в новом пакете уже нет в наборах, но которые **обязаны остаться** в `puzzles` ради архива (`CONTENT_MODEL.md` §7). Эти строки навсегда остались бы в старой форме payload, и архив за прошлые дни перестал бы открываться. Отдельный тип хранения делает форму payload независимой от формата ассетов.

**Правило, вытекающее отсюда:** форма `cards_json`/`sources_json` — часть контракта схемы Room, хотя SQLite видит там просто `TEXT`. Её изменение требует настоящей миграции, переписывающей колонку, а не «просто добавим поле в DTO». Это правило синхронизируется в `ARCHITECTURE.md` §3 (раздел 19).

### 9.3 I4-D18. Токены перечислений

Перечисления хранятся **токенами формата** (`"geography"`, `"ascending"`), а не именами Kotlin-констант.

- Персистентное значение не должно зависеть от идентификатора в коде: переименование `Category.RUSSIA` не должно требовать миграции данных.
- Словарь становится один на всю систему — тот, что описан в `CONTENT_MODEL.md`; строку в базе можно глазами сравнить с JSON.
- Преобразование — **явный `when` в обе стороны** в единственном файле `data/db/mapper/ContentTokens.kt`. Ни `valueOf`, ни `uppercase()`: неявное соответствие имени токену — именно тот вид связи, который ломается молча.

Неизвестный токен при **чтении** строки — повреждение того, что писали мы сами. Мапперу это не состояние экрана, а дефект: `error("неизвестная категория '\$token' у $puzzleId")`. `PuzzleErrorKind.PuzzleNotFound` здесь был бы неправдой («головоломки нет»), а `InvalidPuzzle` требует построить `Puzzle`, которого построить нельзя.

### 9.5 I4-D15. Смысл `puzzles.content_version`

`content_version` — **отметка поставки**: версия пакета, которая последней записала эту строку, а не «версия, в которой головоломка появилась».

- импорт пишет `manifest.contentVersion` **всем** головоломкам файла, включая неизменившиеся и включая отозванные (по правилу неизменности контента строка перезаписывается идентичной, меняется только отметка);
- отсюда строки текущей версии — ровно те, что входят в установленный пакет **этого** `packId`. Строка с меньшей версией означает одно из двух: она принадлежит другому пакету либо осталась от предыдущей установки и в текущем файле её больше нет. Второе `CONTENT_MODEL.md` §7 прямо запрещает («удалять головоломки из `puzzles-*.json` нельзя никогда. Только `retiredIn`»), поэтому при исправном контенте таких строк не бывает; если они появились — это признак нарушенного правила, а не штатное состояние. Импортёр в любом случае их **не трогает**: архив может на них ссылаться;
- это делает подтверждение «все головоломки текущей версии на месте» точным SQL-предикатом (раздел 10.3), а не эвристикой по количеству.

Альтернатива «версия появления» отклонена: ни один экран не показывает, когда головоломка появилась, а ось отзыва уже закрыта `retiredIn`.

### 9.6 Round trip

Обязательное свойство: **`asset-DTO → Entity → domain` не теряет ничего из того, что попадает в базу.** Проверяется тестами `I4-M1…I4-M6` на данных, включающих кириллицу, длинные тире, неразрывные пробелы, `null` во всех необязательных полях, отрицательный `sortValue`, `disputed = true`, отозванную головоломку и восемь источников на четыре карточки. Отдельный тест `I4-M6` фиксирует **намеренную** потерю `volatility`/`verifiedAt`/`verifiedBy`/`packTitle`: если однажды кто-то решит их хранить, тест обязан упасть первым и потребовать решения, а не молча пропустить изменение схемы.

## 10. Алгоритм `ensureInstalled()`

### 10.1 Обязательные свойства

| Свойство | Чем обеспечено |
| --- | --- |
| `@Singleton` | аннотация на классе + `@Binds` без scope; один экземпляр — один `Mutex` |
| Один process-wide `Mutex` | `private val mutex = Mutex()`; **весь** метод — тело `mutex.withLock` |
| Разбор и валидация — до транзакции записи | шаги 1 и 3 не открывают транзакцию; шаг 4 не читает assets |
| Reconcile — одна `withTransaction` | шаг 4 целиком; конфликт бросается **внутри** неё |
| DataStore — только после успешного commit | шаг 5 стоит **после** `db.withTransaction { … }` |
| DataStore никогда не раньше базы | в коде между `withTransaction` и записью отметки нет ни одной ветки, способной их переставить; проверяется `rg`-порядком строк |
| Отмена внутри транзакции откатывает Room | `withTransaction` откатывает при любом выходе, включая `CancellationException` |
| Сбой между commit и DataStore ⇒ безопасный idempotent-повтор | следующий вызов не находит отметки, повторяет импорт; upsert идемпотентен, конфликтов не создаёт |
| Параллельные вызовы не создают частичного состояния | `Mutex` + единственная транзакция; второй вызов после первого уходит в быстрый путь |
| Нет процессного boolean-флага готовности | в классе нет ни одного поля, хранящего вывод о состоянии базы (**I3-D41** сохраняется) |

### 10.2 I4-D10 / I4-D11. Что кэшируется и почему это не флаг готовности

В классе есть **один** кэш: разобранный **заголовок пакета** — манифест, его `sha256` и файл наборов.

Это законно и не противоречит **I3-D41**, потому что кэшируется **содержимое ассетов, а не вывод о базе**. Ассеты неизменны в пределах жизни процесса: они лежат внутри APK, а обновление APK убивает процесс. Кэш заголовка не отвечает на вопрос «установлено ли»; на него по-прежнему отвечает база, и отвечает **на каждом вызове**.

Что **не** кэшируется никогда: результат сверки с базой, факт успешного импорта, `storedContentVersion`, любой `Boolean installed`. Проверка: `rg -n "installed|isReady|@Volatile" ContentImporter.kt` — пусто.

Файл головоломок (~300 КБ) в заголовок **не входит** и читается только на пути импорта. Иначе каждый пересчёт Home разбирал бы 105 объектов ради вывода «ничего делать не надо».

**Отпечаток пакета.** В DataStore рядом с `storedContentVersion` хранится `storedContentFingerprint` — `sha256` байтов `manifest.json` в нижнем регистре. Он закрывает случай «версия та же, содержимое другое»: правка контента без повышения `contentVersion` при обязательном `--sync-manifest` (раздел 4.7) меняет хеши файлов в манифесте, а значит и его отпечаток. Без отпечатка правка `puzzles-001.json` молча игнорировалась бы приложением до следующего повышения версии — ровно та ловушка, в которую упирается работа над вторым пакетом, где `contentVersion` подолгу не растёт.

Запись обеих величин — **одна операция**, по образцу `updateStreakCache`:

```kotlin
// UserPreferencesRepository — setStoredContentVersion(version) заменяется на:
/** Единственная операция записи отметки об установленном контенте. */
suspend fun setInstalledContent(contentVersion: Int, fingerprint: String)
```

Двух сеттеров нет намеренно: частично записанная отметка («версия новая, отпечаток старый») означала бы состояние, которого не бывает, и потребовала бы отдельной ветки восстановления.

### 10.3 Псевдокод

```kotlin
@Singleton
class ContentImporter @Inject constructor(
    private val db: AppDatabase,
    private val puzzleDao: PuzzleDao,
    private val setDao: DailySetDao,
    private val assignmentDao: AssignmentDao,
    private val source: ContentAssetSource,
    private val reader: ContentPackReader,
    private val validator: ContentValidator,
    private val prefs: UserPreferencesRepository,
    @ActivePack private val activePackId: String,
) : ContentInstaller {

    private val mutex = Mutex()
    /** КЭШ АССЕТОВ, не вывода о базе (I4-D10). Ассеты неизменны в пределах процесса. */
    private var header: PackHeader? = null

    override suspend fun ensureInstalled() = mutex.withLock {

        // ── 1. Заголовок: manifest.json → daily-sets-*.json. Один раз на процесс (4.7).
        //      Коды: M01, M02, M03, M04, M05, M07 (+ M06, M09 в debug); R01 при несобираемом
        //      DTO конверта; R19 и R21(setCount) по файлу наборов.
        val head = header ?: reader.readHeader(activePackId).also { header = it }

        // ── 2. Отметка об установленном контенте. Читается ВНУТРИ lock: иначе два
        //      вызова могли бы принять решение по разным снимкам DataStore.
        val stored = prefs.preferences.first()
        val sameContent = stored.storedContentVersion == head.manifest.contentVersion &&
                          stored.storedContentFingerprint == head.fingerprint

        // ── 3. Единственный ранний выход — и только после подтверждения БАЗОЙ.
        if (sameContent && db.withTransaction { isInstalled(head) }) return@withLock

        // ── 4. Тело пакета: puzzles-*.json читается ТОЛЬКО здесь — разбор, валидация,
        //      маппинг ВНЕ транзакции записи. Коды M04/M05/M06/M07/R01 для файла головоломок
        //      и весь защитный набор (7.2).
        val pack = reader.readBody(head)          // + sha256 в debug
        validator.validate(pack)                  // бросает BundleInvalid со списком нарушений
        val puzzleRows = pack.puzzles.map { it.toEntity(pack.manifest) }   // чистый CPU, без базы
        val setRows = pack.sets.map { it.toEntity(pack.manifest.packId) }

        // ── 5. Одна транзакция: обнаружение конфликта и запись.
        db.withTransaction {
            val conflict = detectConflict(pack)
            if (conflict != null) throw conflict          // откат гарантирован формой кода

            puzzleDao.upsertAll(puzzleRows)               // НИ ОДНОГО DELETE по puzzles
            setDao.deleteOutsideRange(activePackId, pack.setCount)  // единственный DELETE
            setDao.upsertAll(setRows)
        }

        // ── 6. DataStore — ТОЛЬКО после успешного commit. NonCancellable сужает окно
        //      «база записана, отметки нет» до смерти процесса; корректность при этом
        //      держится не на нём, а на идемпотентности повтора (10.6).
        withContext(NonCancellable) {
            prefs.setInstalledContent(head.manifest.contentVersion, head.fingerprint)
        }
    }
```

**Дешёвое подтверждение состояния базы** — четыре запроса. Три из них от размера истории не зависят; `countBlockingPlayedPuzzleMismatches` зависит от числа попыток, но выполняется после `countOutsideRange`, и при пройденном `countOutsideRange == 0` его выборка ограничена сверху `3 × setCount` (10.4):

```kotlin
    /** Всё, что перечислено, обязано выполняться ОДНОВРЕМЕННО. Любое «нет» — полный импорт. */
    private suspend fun isInstalled(head: PackHeader): Boolean {
        // (1) ожидаемые индексы И точный состав каждого ожидаемого набора
        val storedSets = setDao.byPack(activePackId)                     // setCount строк, по PK
        if (storedSets != head.expectedSetRows) return false

        // (2) нет назначений вне диапазона пакета
        if (assignmentDao.countOutsideRange(activePackId, head.setCount) > 0) return false

        // (3) НЕТ БЛОКИРУЮЩИХ расхождений между сыгранными puzzleId и составом слота.
        //     Свидетельство C проверяется и здесь: без него ранний выход скрывал бы
        //     попытку, чей puzzle_id не принадлежит текущему составу набора. Легальная
        //     историческая замена отозванной расхождением НЕ считается (10.3.1).
        if (assignmentDao.countBlockingPlayedPuzzleMismatches(
                activePackId, head.manifest.contentVersion) > 0) return false

        // (4) головоломки текущих наборов существуют, имеют текущую версию И АКТИВНЫ
        if (setDao.countSetsWithMissingPuzzles(
                activePackId, head.manifest.contentVersion) > 0) return false

        return true
    }
```

#### 10.3.1 Предикат (3): что считается блокирующим расхождением

Наивная форма «`puzzle_id` попытки ≠ ID своего слота» неверна **после легального отзыва**. Пусть слот 2 набора 4 содержал `C` с `retiredIn = N`, в версии `N` он заменён активной `D`, а в истории пользователя осталась попытка с `puzzle_id = C`. Расхождение здесь законно и постоянно: попытку переписывать нельзя. Наивный предикат возвращал бы `> 0` **навсегда**, ранний выход не срабатывал бы никогда, и каждый пересчёт Home читал бы и переписывал весь пакет — то есть быстрый путь переставал бы существовать ровно у тех пользователей, ради которых механизм отзыва и придуман.

Предикат считает только **блокирующие** случаи:

| Ситуация | Блокирует предикат (3) |
| --- | --- |
| `puzzle_id` попытки совпадает с ID своего слота | нет — и состояние самой ожидаемой головоломки предикат (3) при этом не смотрит |
| `puzzle_id` попытки ≠ ID слота; старый ID есть в `puzzles` этого пакета, отозван и `retired_in ≤ contentVersion`, а ожидаемый ID слота существует и активен | нет — легальная историческая замена |
| `puzzle_id` попытки ≠ ID слота; старого ID нет в `puzzles`, либо он активен, либо `retired_in > contentVersion` | **да** |
| `puzzle_id` попытки ≠ ID слота; ожидаемого ID слота нет в `puzzles` либо он отозван | **да** — замене нечем обосноваться |
| `slot_index` вне `0..2` | **да** — сравнивать не с чем |

Предикат (3) классифицирует именно **несовпадение сыгранного `puzzleId` с ID слота**: внешнее условие SQL начинается с `t.puzzle_id <> CASE t.slot_index …`, и до состояния строки `puzzles` разбор доходит только внутри этой ветки. Поэтому случай «сыгранный ID **совпадает** с ожидаемым, но ожидаемая головоломка отсутствует в `puzzles`, имеет чужую `content_version` или отозвана» предикат (3) mismatch считать **не обязан** — это не расхождение состава истории. Такое состояние блокирует предикат (4) `countSetsWithMissingPuzzles`, для которого «missing» и означает «нет строки, чужая версия или `retired_in IS NOT NULL`»; его ветка и тест — `I4-I22d` (10.6). Разделение намеренное: (3) отвечает за историю против состава наборов, (4) — за состав наборов против таблицы головоломок, и SQL обоих запросов менять для этого не требуется.

```kotlin
// AssignmentDao — read-only предикат быстрого пути
@Query("""
    SELECT COUNT(*)
      FROM day_assignments a
      JOIN puzzle_attempts t ON t.local_date = a.local_date
      JOIN daily_sets s ON s.pack_id = a.pack_id AND s.set_index = a.set_index
     WHERE a.pack_id = :packId
       AND (
         -- слот вне 0..2: сравнивать не с чем, это блокирующее расхождение
         t.slot_index NOT IN (0, 1, 2)
         OR (
           t.puzzle_id <> CASE t.slot_index
                            WHEN 0 THEN s.puzzle_id_1
                            WHEN 1 THEN s.puzzle_id_2
                            WHEN 2 THEN s.puzzle_id_3
                          END
           AND NOT (
             EXISTS (SELECT 1 FROM puzzles po
                      WHERE po.puzzle_id = t.puzzle_id
                        AND po.pack_id = :packId
                        AND po.retired_in IS NOT NULL
                        AND po.retired_in <= :contentVersion)
             AND EXISTS (SELECT 1 FROM puzzles pn
                          WHERE pn.puzzle_id = CASE t.slot_index
                                                 WHEN 0 THEN s.puzzle_id_1
                                                 WHEN 1 THEN s.puzzle_id_2
                                                 WHEN 2 THEN s.puzzle_id_3
                                               END
                            AND pn.pack_id = :packId
                            AND pn.retired_in IS NULL)
           )
         )
       )
""")
suspend fun countBlockingPlayedPuzzleMismatches(packId: String, contentVersion: Int): Int
```

`CASE` намеренно записан **без `ELSE`**: прежняя форма `ELSE s.puzzle_id_3` молча объявляла третьим слотом любое значение `slot_index`, включая `7` и `-1`. Теперь `CASE` для таких строк даёт `NULL`, сравнение `<> NULL` истинным не бывает, и второй дизъюнкт их не поймал бы вовсе — поэтому первым стоит явный `t.slot_index NOT IN (0, 1, 2)`. Слот вне диапазона не может возникнуть штатно (`UNIQUE(local_date, slot_index)` и `SLOTS_PER_DAY = 3`), но предикат обязан быть тотальным: молчаливое «сойдёт за третий слот» — именно тот способ, которым проверка перестаёт проверять.

Предикат даёт **только факт**: разбор причины (лишний индекс, перестановка, недопустимая замена) стоит дороже и выполняется полной диагностикой `detectConflict` уже на пути импорта. Соединение идёт по первичным ключам `day_assignments.local_date`, `daily_sets(pack_id, set_index)` и индексу `puzzle_attempts(local_date, slot_index)`; подзапросы — точечные lookup-ы по PK `puzzles.puzzle_id`.

Запрос (4) расширен: головоломка считается на месте, только если она существует, имеет **текущую** `contentVersion` и **активна**. Отозванная головоломка в составе набора — нарушение `R18A`, и состояние базы с ней установленным не считается:

```kotlin
// DailySetDao
// «Missing» здесь означает «непригодна как текущий контент»: нет строки, чужая версия
// или retired_in IS NOT NULL. Имя сохранено, семантика шире — она описана здесь.
@Query("""
    SELECT COUNT(*) FROM daily_sets s
     WHERE s.pack_id = :packId AND (
       NOT EXISTS (SELECT 1 FROM puzzles p WHERE p.puzzle_id = s.puzzle_id_1
                    AND p.pack_id = :packId AND p.content_version = :contentVersion
                    AND p.retired_in IS NULL) OR
       NOT EXISTS (SELECT 1 FROM puzzles p WHERE p.puzzle_id = s.puzzle_id_2
                    AND p.pack_id = :packId AND p.content_version = :contentVersion
                    AND p.retired_in IS NULL) OR
       NOT EXISTS (SELECT 1 FROM puzzles p WHERE p.puzzle_id = s.puzzle_id_3
```

**Обнаружение конфликта** (раздел 3.3), выполняется только на пути импорта:

```kotlin
    private suspend fun detectConflict(pack: ParsedPack): ContentInstallException.Conflict? {
        val stale = assignmentDao.setIndexesOutsideRange(activePackId, pack.setCount)   // A
        val assigned = assignmentDao.assignedSets(activePackId)                          // B
        val storedSets = setDao.byPack(activePackId).associateBy { it.setIndex }
        val played = assignmentDao.playedPuzzles(activePackId)                           // C

        val changed = sortedSetOf<Int>()
        for (row in assigned) {                                        // B: сохранённый состав
            val expected = pack.setAt(row.setIndex) ?: continue        // индекс вне диапазона — уже в stale
            storedSets[row.setIndex]?.let { storedRow ->
                if (!isRetirementReplacement(pack, storedRow.puzzleIds, expected.puzzleIds)) {
                    changed += row.setIndex
                }
            }
        }
        for (p in played) {                                            // C: сыгранные головоломки
            val expected = pack.setAt(p.setIndex) ?: continue
            // Послотовое сравнение: попытка сыграна в СВОЁМ слоте, поэтому переезд
            // головоломки в другой слот — расхождение, а не «та же головоломка».
            if (p.puzzleId != expected.puzzleIds[p.slotIndex] &&
                !isRetirementSlot(pack, p.puzzleId, expected.puzzleIds[p.slotIndex])
            ) changed += p.setIndex
        }
        if (stale.isEmpty() && changed.isEmpty()) return null

        val blocked = (assigned.filter { it.setIndex in stale || it.setIndex in changed })
            .map { LocalDate.parse(it.localDate) }.sorted()
        return ContentInstallException.Conflict(
            packId = activePackId,
            staleSetIndexes = stale.sorted(),
            changedSetIndexes = changed.toList(),
            blockedDates = blocked,
        )
    }

    /**
     * Единственное допустимое расхождение состава — ПОСЛОТОВАЯ замена отозванной
     * головоломки (CONTENT_MODEL.md §7). Сравнение идёт по позициям, а не по множествам:
     * множественное сравнение не отличает замену от перестановки.
     */
    private fun isRetirementReplacement(pack: ParsedPack, old: List<String>, new: List<String>): Boolean {
        // Составы совпадают послотово — расхождения нет вовсе.
        if (old == new) return true

        val changedSlots = old.indices.filter { old[it] != new[it] }
        // Пустым быть не может: списки той же длины и не равны. Условие выписано явно,
        // потому что именно на пустом списке all { } молча вернул бы true.
        if (changedSlots.isEmpty()) return false

        // Ни одна НЕизменившаяся позиция не должна «переехать»: если ID сохранился
        // в наборе, но в другом слоте, это перестановка, а не замена.
        val movedIn = new.filterIndexed { i, id -> i in changedSlots && id in old }
        if (movedIn.isNotEmpty()) return false

        return changedSlots.all { slot ->
            val oldId = old[slot]
            val newId = new[slot]
            // Старый ID обязан остаться в пакете и быть отозванным — иначе архив
            // не разрешит его, а замена не имеет основания.
            val retiredOld = pack.puzzleById(oldId)?.retiredIn != null
            // Новый ID обязан существовать и быть АКТИВНЫМ: отозванной головоломкой
            // заменять нельзя (это же запрещает R18A).
            val activeNew = pack.puzzleById(newId)?.let { it.retiredIn == null } == true
            retiredOld && activeNew
        }
    }

    /** Послотовый вариант того же правила для одной сыгранной попытки. */
    private fun isRetirementSlot(pack: ParsedPack, playedId: String, expectedId: String): Boolean {
        val retiredOld = pack.puzzleById(playedId)?.retiredIn != null
        val activeNew = pack.puzzleById(expectedId)?.let { it.retiredIn == null } == true
        // Головоломка, которая осталась в наборе, но в другом слоте, сюда не попадает:
        // playedId нашёлся бы активным, и retiredOld был бы false.
        return retiredOld && activeNew
    }
}
```

**Почему перестановка не проходит как замена отозванной.** Наивная форма `old.filterNot { it in new }.all { isRetired(it) }` сравнивает **множества**: у перестановки `[A,B,C] → [B,A,C]` разность пуста, `all { }` на пустом списке истинна, и подмена состава прошла бы молча — при том что пользователь сыграл `A` в слоте 0, а после импорта в слоте 0 стоит `B`. Послотовое правило закрывает это тремя условиями сразу: список изменившихся позиций обязан быть непустым; ни один ID, оставшийся в наборе, не может занять другую позицию; в каждой изменившейся позиции старый ID отозван, а новый существует и активен. Смешанный случай «одну отозванную заменили, другую активную переставили» отсекается вторым условием.

**Семантика `retiredIn`.** Ненулевое значение — номер `contentVersion`, **начиная с которого** головоломка не используется, и оно **не может быть больше** `manifest.contentVersion` устанавливаемого пакета: «отозвана в будущей версии» — это не отзыв, а опечатка. Проверяется правилом `R18C_RETIRED_IN_FUTURE` в CLI и входит в защитный набор рантайма, потому что от него зависит ветка замены: головоломка с `retiredIn` из будущего считалась бы отозванной и открывала бы дорогу подмене состава.

### 10.4 Почему совпадения `storedContentVersion` недостаточно

Отметка в DataStore и содержимое Room — **разные хранилища с разными жизненными циклами**, и совпадение версии говорит только о том, что импорт когда-то дошёл до шага 6. Оно ничего не говорит о том, что данные на месте **сейчас**:

- **`clearAllTables()`** debug-действия опустошает Room и **не трогает DataStore** (**I3-D48**): версия совпадает, база пуста. Без подтверждения приложение показывало бы `ContentExhausted` до переустановки;
- **процесс упал между commit и записью отметки** — обратный случай: база полна, отметки нет. Он безопасен (повтор идемпотентен), но существует;
- **частичная база** — строку удалили отладочным инструментом или прямой правкой файла БД;
- **отпечаток при равной версии** — контент правили без повышения `contentVersion` (10.2);
- **правило «не молча»** — база и отметка расходятся ровно в тех случаях, где молчаливое доверие отметке скрывает реальную поломку.

- **сыгранная головоломка не из текущего состава** — самый тонкий случай: версия, отпечаток, состав `daily_sets` и наличие головоломок могут совпасть все сразу, а `puzzle_attempts` при этом хранит `puzzle_id`, не принадлежащий своему слоту. Без отдельной проверки ранний выход подтвердил бы «всё установлено» и **скрыл** бы уже случившуюся подмену дня.

Поэтому ранний выход требует **конъюнкции** шести условий: версия совпала, отпечаток совпал, состав всех наборов точен, назначений вне диапазона нет, блокирующих расхождений по сыгранным головоломкам нет, все головоломки наборов существуют, имеют текущую версию и активны.

**Стоимость — четыре запроса**, и их цена различна:

| Запрос | Строк | Зависит от истории |
| --- | --- | --- |
| `byPack` | `setCount` (35) | нет |
| `countOutsideRange` | агрегат по индексу `(pack_id, set_index)` | нет |
| `countBlockingPlayedPuzzleMismatches` | по одной строке на **сыгранный слот** | **да** |
| `countSetsWithMissingPuzzles` | `setCount` строк × 3 lookup-а по PK | нет |

Третий запрос честно зависит от числа попыток, и утверждать обратное нельзя. Но он выполняется **после** второго, а тот уже гарантировал отсутствие назначений вне диапазона; назначений в пакете не больше `setCount` (`UNIQUE(pack_id, set_index)`), на дату приходится не более трёх попыток, поэтому соединение ограничено сверху `3 × setCount` — 105 строк для пакета альфы и 180 для пакета из 60 наборов, независимо от того, сколько лет человек играет. Это по-прежнему на порядок дешевле цены за «контент исчез, а отметка утверждает обратное».

Свидетельство C проверяется на быстром пути **фактом**, а на пути импорта — полной диагностикой: там нужны индексы, даты и разбор причины (лишний индекс, замена отозванной, перестановка), и платить за него на каждом пересчёте Home незачем.

### 10.5 Атомарная граница

```
чтение assets ─ разбор ─ валидация ─ маппинг     вне транзакции, без записи, отменяемо без следов
        │
        ▼
┌─ db.withTransaction ─────────────────────────┐  ЕДИНСТВЕННАЯ точка изменения Room
│  detectConflict()   → throw ⇒ полный откат   │
│  puzzles.upsertAll                            │
│  daily_sets.deleteOutsideRange + upsertAll    │
└───────────────── commit ──────────────────────┘
        │
        ▼
prefs.setInstalledContent(version, fingerprint)   ТОЛЬКО после commit, одной операцией
```

Граница проходит **между Room и DataStore** и всегда в одну сторону: Room — источник истины о контенте, DataStore — производная отметка. Обратный порядок создал бы состояние «отметка есть, данных нет», в котором ранний выход возвращал бы успех при пустой базе, а это и есть тот самый класс ошибок, ради которого существует раздел 10.4.

Маппинг вынесен **до** транзакции сознательно: сериализация 105 карточных списков — это десятки миллисекунд чистого CPU, и держать их внутри транзакции значило бы держать блокировку записи SQLite всё это время.

| **Отмена** | `CancellationException` в любой точке | до commit — Room не изменён и отметки нет; после commit — см. следующую строку | `I4-I16` |
| **Сбой после commit до DataStore** | процесс убит / ошибка DataStore | следующий вызов видит старую отметку → повторный импорт; upsert идемпотентен, дублей нет, конфликт не возникает (составы уже совпадают) | `I4-I17` |
| **Конкурентные вызовы** | N корутин одновременно | `Mutex` сериализует; первая импортирует, остальные уходят в ранний выход; частичного состояния нет | `I4-I18` |

### 10.7 Что импорт не делает с историей

Головоломка, на которую может ссылаться история, **не удаляется автоматически никогда** — ни при обновлении, ни при откате, ни при конфликте. Изменение уже опубликованной головоломки под тем же `puzzleId` запрещено правилом `CONTENT_MODEL.md` §7; смысловое изменение оформляется новым идентификатором либо отзывом (`retiredIn`) с заменой в наборе. Валидатор не может отличить «исправили опечатку в объяснении» от «подменили факт», поэтому это правило редакционное, а импортёр обеспечивает лишь то, что старая строка остаётся доступной архиву.

Экран результата для отозванной головоломки («Задание отозвано: в нём была неточность», `CONTENT_MODEL.md` §7) в итерации 4 **не реализуется**: `retiredIn` в паке v1 везде `null`, а место этой строки — экран архива итерации 5. Пункт зафиксирован здесь, чтобы не потеряться (раздел 20).

## 11. Ошибки

### 11.1 I4-D19. Закрытая taxonomy

`ContentInstallException` остаётся доменным `sealed class` в `domain/content`. К существующему `Conflict` добавляются **три** варианта — итого **четыре**. Закрытость — не украшение: `GetTodayStateUseCase` классифицирует отказ исчерпывающим `when`, и появление пятой причины обязано ломать компиляцию, а не молча уезжать в `Generic`.

Отказов базы среди них нет намеренно. `ContentImporter` не содержит ни одного `catch` (11.2), поэтому обернуть `SQLiteException` в собственный тип он не может, не нарушив собственного правила; вариант `StorageFailure`, который никто не бросает, был бы мёртвым кодом с исчерпывающим `when` вокруг него. Исключения Room проходят наружу как есть, попадают в общий `catch (e: Exception)` внутри `GetTodayStateUseCase` (**I3-D43**) и дают `TodayFailureKind.Generic` — ровно то поведение, которое и требуется: повторить имеет смысл, разрушительных действий не предлагается.

```kotlin
sealed class ContentInstallException(message: String, cause: Throwable? = null) : Exception(message, cause) {

    /** Локальные назначения не позволяют установить пакет. Ни одна таблица не изменена. */
    class Conflict(
        val packId: String,
        val staleSetIndexes: List<Int>,      // назначения вне диапазона пакета
        val changedSetIndexes: List<Int>,    // назначенные наборы с изменившимся составом
        val blockedDates: List<LocalDate>,
    ) : ContentInstallException(…)

    /** Пакет внутри APK не соответствует контракту: форма, целостность, счётчики, ссылки. */
    class BundleInvalid(val code: String, val violations: Int, detail: String) : ContentInstallException(…)

    /** Формат пакета новее, чем понимает это приложение. */
    class UnsupportedSchema(val manifest: Int, val supported: Int) : ContentInstallException(…)

    /** Ассет не прочитался: ввод-вывод, а не содержимое. */

}
```

### 11.2 `CancellationException` не превращается в ошибку

Правило **I3-D43** сохраняется дословно: в `GetTodayStateUseCase` первый `catch` — `CancellationException` с немедленным `throw`, и только затем `catch (e: Exception)`. `ContentImporter` не ловит исключения вовсе: он их только бросает. `withTransaction` откатывает Room при отмене, `withContext(NonCancellable)` шага 6 отмену **не глотает** — он лишь не даёт прерваться уже начатой записи отметки, после чего отмена доставляется вызывающему обычным порядком.

Проверка формой кода: `rg -n "catch" ContentImporter.kt` — пусто; в `GetTodayStateUseCase` порядок блоков не меняется.

### 11.3 Правила о разрушительных действиях

1. **Полный сброс разрешён только для `ContentConflict`** и только через уже существующее явно подтверждаемое debug-действие (`HomeErrorRecoveryAction` + диалог с текстом, который прямо говорит, что стирается весь прогресс). `isApplicableTo(kind)` возвращает `true` **только** для `ContentConflict`; для `ContentUnusable` и `Generic` — `false`.
2. **Повреждённый пакет не предлагает очистку прогресса.** Связь «пакет сломан → сотрём ваш прогресс» ложна: прогресс не при чём, и предложение стереть его — способ потерять данные ради чужой ошибки. Проверяется тестом `I4-V2`.
3. В release-сборке набор действий восстановления пуст (`@Multibinds` без вкладов, **I3-D47**) — правило не меняется.
4. `TemporaryContentReset` переименовывается в `ContentReset`, остаётся в `src/debug`, продолжает делать `clearAllTables()` и по-прежнему **не трогает DataStore**. После сброса ранний выход не срабатывает (10.4), и следующий `ensureInstalled()` переустанавливает пакет — устройство возвращается в состояние первого запуска.

### 11.4 Изменения в `TodayFailureKind`

```kotlin
enum class TodayFailureKind { Generic, ContentConflict, ContentUnusable }
```

`ContentUnusable` — «пакет внутри приложения непригоден; прогресс цел; помочь может только обновление приложения». Это единственное новое значение; `HomeStateMapper` и `HomeScreen` выбирают по `kind` текст и наличие кнопки «Повторить». Правка `COMPONENTS.md` (state sheet `Error`: второй вариант без основной кнопки) и `UX_FLOW.md` (§3, перечень состояний Home) входит в PR 4D — раздел 19.

Ветка недостижима содержимым APK и существует ради двух вещей: требования `CONTENT_MODEL.md` §7 о тексте «Требуется обновление приложения» и будущих паков, доставляемых отдельно. Проверяется тестами, а не устройством.

### 12.4 Как манифест и хеши остаются валидными

Инвариант батча: **после `--sync-manifest` пакет валиден целиком.** Порядок работы автора фиксирован:

```bash
# 1. дописать 21 головоломку и 7 наборов
# 2. привести манифест в соответствие
python3 tools/validate-content/validate.py app/src/main/assets/content --sync-manifest
```

## 15. Отклонённые альтернативы

| Что предлагалось | Почему выглядит разумным | Почему отклонено |
| --- | --- | --- |
| Пустая миграция 1→2 ради `MigrationTestHelper` | План итерации 4 прямо обещает подключить `room-testing` | Миграция, ничего не меняющая, — ложная запись в истории схемы; тест проверял бы собственную заглушку (**I4-D1**) |
| Хранить `volatility`/`verifiedAt`/`verifiedBy` в `puzzles` | «Пусть база повторяет формат» | Потребителя нет ни на одном экране; появились бы новая миграция и обязанность их поддерживать (**I4-D16**) |
| Отдельная таблица `content_packs` с версией и отпечатком | Состояние установки лежало бы рядом с данными | Скаляры принадлежат DataStore (`ARCHITECTURE.md` §3); отметка обязана быть **вне** транзакции, иначе перестаёт быть независимым подтверждением (**I4-D13**) |
| Legacy-пакет `core-ru-legacy` + сохранение payload временных головоломок | Ничей прогресс не сломается | Ломать нечего: релиза не было, `storedContentVersion` не писался, `puzzles` пуста. Цена — второй пакет навсегда в коде ради нуля пользователей (**I4-D3**) |
| Автоматически «чинить» конфликт, удаляя назначения на изменившиеся наборы | Пользователь не увидел бы ошибки | Это молчаливое стирание прогресса. Запрещено `I3-D47`, повторно закреплено `I4-D3` |
| Считать конфликтом любое расхождение состава, без исключений | Проще на одну ветку | Противоречит `CONTENT_MODEL.md` §7: замена отозванной головоломки легальна, и запрет заблокировал бы обновление всем, кто сыграл затронутый день (**I4-D4**) |
| Сравнивать состав только по `daily_sets` | Один запрос вместо двух | Строки `daily_sets` могли быть удалены (**I3-D50**), а `puzzle_attempts.puzzle_id` — прямое свидетельство того, что видел пользователь |
| Списочные предикаты `NOT IN (:keep)` | Уже написаны в итерации 3 | Список параметров растёт с пакетом (35 → 60 → …) и упирается в лимит переменных SQLite; диапазон точен, потому что `R19` гарантирует непрерывность (**I4-D27**) |
| Несколько шардов `puzzles-00N.json` | «Пригодится, когда контента станет больше» | Порядок объединения, дедупликация, семантика частичного отказа — сложность без пользы на пяти PR; `files` уже массив, формат менять не придётся (**I4-D5**) |
| Держать батчи в staging-каталоге и перенести в assets в 4D | Гарантия «неполный пакет не активируется» | Пакет перестал бы валидироваться по конечным путям; финальный PR получил бы один огромный diff вместо пяти читаемых. Неактивация уже обеспечена тем, что DI не переключён (**I4-D5**) |
| CLI на Kotlin/JVM отдельной сборкой | Шаффлер не пришлось бы портировать | Второй Gradle-артефакт и десятки секунд CI; переиспользование одного файла потребовало бы либо общего модуля (против ADR-001), либо чужого `srcDir` (**I4-D8**) |
| Реализовать все 21 правило и в CLI, и в рантайме | «Одинаково везде» | Вторая независимая реализация 21 правила без выигрыша: пакет внутри APK уже прошёл CI. Дублируется только защитный набор, и он покрыт parity-тестами (**I4-D9**) |
| Сделать рантайм строгим к неизвестным полям | «Как в CI» | Сделало бы неисполнимой политику `CONTENT_MODEL.md` §7: добавление необязательного поля не повышает `schemaVersion` (**I4-D9**) |
| Ранний выход по `storedContentVersion == contentVersion` | Один сравнимый скаляр — и всё | `clearAllTables()` не трогает DataStore; правка контента без бампа версии; частичная база. Полный разбор причин — 10.4 |
| Кэшировать `Boolean installed` после успешного импорта | Дешевле трёх запросов | Прямо запрещено **I3-D41**: единственный источник истины о наличии контента — база |
| Разбирать весь пакет на каждом `ensureInstalled()`, чтобы сверять состав | Точная сверка без кэша заголовка | 300 КБ разбора на каждый пересчёт Home; выигрыш нулевой, потому что состав наборов уже сверяется по кэшу заголовка (**I4-D10**) |
| Писать DataStore до Room или в той же транзакции | «Атомарно вместе» | DataStore не участвует в транзакции SQLite; порядок «отметка раньше данных» создаёт состояние «отметка есть, данных нет» — тот самый класс ошибок, ради которого существует подтверждение (**I4-D13**) |

| `PuzzleRepository` возвращает `sealed`-результат вместо `Puzzle?` | Повреждённая строка получила бы своё состояние экрана | Повреждение того, что мы сами записали, — дефект, а не состояние. Правка интерфейса потянула бы четыре use case ради недостижимой ветки (**I4-D18**) |
| Отдельный `TodayFailureKind` на каждую причину отказа | Точнее диагностика | Экрану нужны три поведения: «повторить», «нельзя помочь», «есть debug-восстановление». Пятое значение перечисления не добавило бы ни одного нового поведения (**I4-D19**) |
| Повышать `contentVersion` на каждом батче | «Каждый батч — новая версия данных» | Батчи не выпускаются; пять номеров версии обозначали бы пять несуществующих релизов (**I4-D21**) |
| Требовать 35/105 правилом валидатора | Гарантия полноты пакета | Сделало бы CI красным на всех батчах, кроме последнего. Полнота — критерий релиза, проверяемый явным флагом (**I4-D21**) |
| Оставить тесты итерации 3 на `BundledPuzzles` до 4D | Меньше правок в 4B | Удаление каталога в 4D перестало бы быть механическим и смешалось бы с переписыванием восьми тестов (**I4-D22**) |
| Разрешить `latitude`/`temperature` в паке v1 с общим правилом «3 %» | Больше свободы автору | Относительный порог вырождается около нуля и бессмыслен на интервальной шкале: правило пропускало бы неоднозначные головоломки (**I4-D24**) |
| Выводить профиль сложности неравенствами `d₀ ≤ d₁ ≤ d₂ ∧ d₀ < d₂` | Короче кода, «выглядит как правило» | Расширяет утверждённый контракт: пропускает `[1,1,2]` и `[2,2,3]`, которых нет в `CONTENT_MODEL.md` §6. Перечень из двух профилей сравнивается напрямую (**I4-D25**) |
| Считать `mixed` джокером, снимающим требование различных категорий | Буквальное чтение фразы «`mixed` может соседствовать с любой» | Набор из двух `mixed` не имеет трёх категорий ни в каком прочтении; та же логика разрешила бы `mixed` открывать два набора подряд. Совместимость по темам ≠ разрешение на дубликат (**I4-D25**) |
| Сравнивать состав набора множествами: `old.filterNot { it in new }.all { isRetired(it) }` | Одна строка, читается как «все выбывшие отозваны» | На перестановке `[A,B,C] → [B,A,C]` разность пуста, `all { }` истинна, и подмена дня проходит молча. Правило послотовое и требует непустого списка изменившихся позиций (**I4-D4**) |

| Возвращать в рантайме точные коды схемы (`R02`, `R11`, `R03`) | Одинаковая диагностика с CI | Требует либо второй JSON Schema, написанной в Kotlin, либо nullable-DTO с ручной проверкой каждого поля. Обе формы расходятся с настоящей схемой при первой правке формата (**7.3**) |
| Проверять «дата не в будущем» по системным часам | Ничего не нужно передавать | Тест становится таймером: зелёный сегодня, красный через год. `--validation-date` передаётся явно (**5.2**) |

### Уточнения, сделанные при реализации PR 4A

Ни одно не меняет решений: каждое — выбор внутри уже утверждённых границ, зафиксированный здесь, чтобы не выясняться заново при чтении кода.

1. **Владение диагностиками между схемой и правилами `M` — точечное, а не по поддереву, и одностороннее.** Раздел 6 требует, чтобы специализированные пакетные ошибки не дублировались общим `R01`, но подавление обязано быть ровно по вопросу, а не по месту, и работать в обе стороны. `M03` владеет составом списка `files` (это массив, ровно два элемента, уникальны) и объявлением файла (элемент — объект, у него есть `path`, `path` проходит закрытый шаблон); `M06` — **значением** хеша, включая регистр. Всё остальное внутри `/files` — форма документа, и её владелец схема: элемент без обязательного `sha256`, `sha256` не строкой и лишнее поле в элементе не ловятся ни `M03` (он смотрит только на `path`), ни `M06` (он сравнивает хеш лишь тогда, когда тот уже строка), — подавление по всему поддереву пропускало бы их с кодом выхода 0.

   **Верхнюю границу числового поля схема задаёт только там, где она единственный владелец вопроса.** Где значение сверяется с чем-то настоящим — `schemaVersion` с `SUPPORTED_SCHEMA_VERSION` (`M01`), `retiredIn` с `contentVersion` (`R18C`), `setCount`/`puzzleCount` с фактическим числом элементов (`R21`), `setIndex` с `0..setCount−1` (`R19`), — границы в схеме нет. Выдуманное `maximum` там не просто дублировало бы правило: находка схемы блокирует семантические правила файла, поэтому точный `R18C` или `R19` заменился бы общим `R01`. Границы, у которых другого владельца нет (`difficulty` 1–3 по `CONTENT_MODEL.md` §4, длины строк, размеры массивов, `contentVersion`, `sortValue`), в схеме остаются.
2. **Подавление каскадов — тоже по вопросу.** При сработавшем `M03` список файлов недостоверен, поэтому `M04`, `M06` и `M08` не выполняются: сверять каталог не с чем. Файл, не прошедший схему, не проверяется семантическими правилами. Значение, названное кодом `R07`, `R08D` или `R08E`, исключается из проверки разрыва **попарно**, а не отменяет её для всей головоломки: разрыв — свойство пары, и пара, не содержащая ни одного диагностированного значения, остаётся самостоятельным нарушением `R08`. Находки, совпадающие по файлу, указателю и коду, схлопываются в одну — так календарно невозможная дата, увиденная и `format: date`, и семантическим слоем, остаётся одной ошибкой.
3. **`M02` проверяется в CLI обеими половинами, как и требует раздел 6.3.** Расхождение `packId` между файлами пакета и расхождение манифеста с **активным пакетом приложения** — два независимых предиката, и оба принадлежат CLI. Идентификатор активного пакета известен инструменту так же, как известна поддерживаемая версия формата: это константа проекта (`ACTIVE_PACK_ID = "core-ru"` рядом с `SUPPORTED_SCHEMA_VERSION = 1`), а не аргумент запуска. Самосогласованный пакет с чужим `packId` не импортируется приложением ни при каких условиях — все запросы импортёра pack-scoped, — поэтому пропускать его в CI значило бы обещать то, чего рантайм не выполнит.
4. **Отчёт `--sync-manifest` при `--format json` уходит в stderr.** stdout обязан оставаться разбираемым целиком: машиночитаемый вывод перестаёт быть машиночитаемым ровно тогда, когда его смешивают с человеческим.
5. **`--sync-manifest` применяет закрытый allow-list имён до любого обращения к диску.** Режим получает имена из данных, а не из кода, поэтому обязан проверять их сам: обычная валидация объявит `M03` уже **после** чтения, а «прочитали, но потом сообщили» защитой не является (**I4-D6**).

### Уточнения, сделанные при реализации PR 4B

Ни одно не меняет решений: каждое — выбор внутри уже утверждённых границ, зафиксированный здесь, чтобы не выясняться заново при чтении кода.

1. **`M05` отделён от `R01` двойным разбором, а не разбором дерева.** Байты сначала проверяются на «это вообще JSON» (`parseToJsonElement`), затем документ декодируется из **исходного текста**, а не из построенного дерева. Причина эмпирическая: дерево теряет различие «число» и «строка, похожая на число», поэтому `"difficulty": "1"` прошёл бы мимо `R01`. Двойной разбор платится один раз на импорт и покупает точность кода; отпечаток при этом считается по байтам, а не по тексту.

2. **Структурно испорченный элемент `files` даёт `R01`, а не `M03`.** `M03` владеет составом списка и **именем** объявленного файла; «`files` не массив», «элемент не объект», «элемент без `path`» — это невозможность построить DTO, и раздел 7.3 называет такой отказ `R01` одним кодом на все случаи. Безопасность от этого не страдает: имя проверяется шаблоном до любого обращения к ассетам, и `I4-R8` фиксирует ноль попыток чтения.

3. **Форма набора (ровно три `puzzleIds`) проверяется читателем кодом `R01`.** Тройка раскладывается по плоским полям `puzzle_id_1..3` ещё в заголовке, до валидатора, и список другой длины не должен превращаться в `IndexOutOfBoundsException`. «Неверная форма массива» — это `R01` по той же таблице 7.3.

4. **Колонка `runtime` в `expectations.json` заполнена целиком, и в трёх местах она разошлась с предсказаниями PR 4A.** Все три расхождения — следствия уже утверждённой модели, а не её изменения, и каждое сопровождается полем `runtimeWhy`:
   - `invalid/r11-empty-source-ids` → `[]` вместо `R01`. Фикстура содержит **пустой массив**, а не отсутствующее поле, поэтому DTO строится; пустой `sourceIds` защитным инвариантом не является (§7.3, п. 3). Соответствующее утверждение pytest-теста исправлено; правила CLI и колонка `cli` не тронуты;
   - `invalid/r01-schema-type` → `[]` вместо `R01`. `kotlinx-serialization` принимает закавыченное число в числовом поле независимо от `isLenient`, DTO строится, и `difficulty` равен `1`. Ловит это строгая схема в CI — ровно там, где §7.3 и оставляет точность;
   - фикстуры `M03` с двумя находками CLI → одна находка рантайма: читатель бросает первым же нарушением, а не собирает список.
   Генератор `rebuild.py` дополнен обеими колонками, поэтому пересборка фикстур больше не откатывает работу PR 4B.

5. **`buildFeatures { buildConfig = true }`** включён: единственный потребитель — провайдер `@VerifyBundleIntegrity`, отдающий `BuildConfig.DEBUG`. В тестах проверка целостности задаётся обычным параметром конструктора, без Robolectric.

6. **Отсутствующий файл пакета определяется по `FileNotFoundException`** — это единственный сигнал, отличающий `M04` («пакет неполон») от `AssetUnreadable` («устройство не отдало байты, повтор имеет смысл»). Импорт этого типа исключения — единственное вхождение подстроки `java.io.File` в `data/content`; настоящей работы с файловой системой (`java.io.File`, `FileInputStream`, `openFileInput`, абсолютные пути) там нет.

- **Настоящего контента и каталога `app/src/main/assets/content` не появилось**; CI не изменён.
- **`I4-V2` не реализован**: тексты `ContentUnusable`, скрытие кнопки «Повторить», `HomeStateMapper` и строки ресурсов — PR 4D.
